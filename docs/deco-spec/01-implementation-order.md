## 왜 이 순서인가

맵 파일 기준 단계별 상한(맵 116개, 장식 64개 이상): 지금 62.5% → 값 안 바뀌는 이벤트 무시 63.3% → 가시성 69.6% → 카메라·행성 73.1% → 깊이 78.6% → 반복·이미지 부가 82.7% → 마스크 86.2%. 절반 이상 맡는 맵은 38개 → 96개.

범위가 좁으면 손해일 수 있다(7777 소유 88/498개에서 373 → 346 FPS, 1판). 그래서 FPS는 범위가 넓은 맵에서 재고, 판정을 층마다 하지 않는다. 다만 비싼 층에 들어가기 전에 G1에서 "범위가 넓어지면 정말 오르는가"를 먼저 확인한다.

## G1: 규칙 정리와 가시성 (먼저, 여기서 일단 멈춤)

1. **값이 안 바뀌는 이벤트는 거부 사유에서 뺀다.** `DecoBake.Reasons`는 필드 사용만 본다. 대상 장식별로 실제 값이 바뀌는지 판단한다. 같은 값으로의 mask·depth·visible 설정이 다른 부수효과가 없는지 명세 4절 1번을 포함해 확인한다.
2. **`가시성/깊이 변경`을 둘로 나눈다.**
3. **가시성을 계단 채널로 표에 넣는다.** `rendererEnabled`와 실제 그리기 켜짐을 구분한다. `SetVisible`이 `spriteRenderer.enabled`를 바꾸는 것과 `CheckPlayerFrame`의 소유 렌더러 상태 검사가 충돌하지 않게 한다.
4. **준비를 시작하기 전에 맵 수준 판정을 끝낸다.** 지금은 준비를 다 한 뒤 거부되기도 하고, 거부된 맵의 끊김이 늘었다(HELLO 0 → 20번, DDONGSSADA 1 → 9번, 1판씩). 원인을 찾아 고친다. 거부된 맵은 기존 후보와 곡 전체 끊김이 같아야 한다.
5. **`FastMove.Orig`의 전체 복귀를 고친다.** 로그는 `original_guard running=True`다. 왜 원래 경로로 갔는지 트리거를 먼저 찾는다. 대상에 소유 장식이 없으면 복귀하지 않는다. 대상이 소유 장식이면 그 장식만 넘기는 길이 가능한지 본다.
6. **`LastPosition`이 끊기는 경우를 표에서 확인한다.** 명세 4절 2번. 기존 표가 틀리면 이 층에서 고친다.

**G1 합격 기준** (Exit, Windflower, HELLO, 회귀 확인 Arche)

- 표 지원 수와 실제 소유 수를 로그로 남기고 맵 파일 집계와의 차이를 설명한다.
- 전체 복귀 0번.
- 정지 프레임 3지점 이상 + 가시성 전환 직후 1지점 이상 + 다시 하기 뒤 1지점에서 채널 차이 `>3/255` 픽셀 0.
- 곡 전체 끊김이 기존 후보보다 늘지 않음.
- Exit 최악 10초와 곡 평균 FPS를 기존 후보(GpuDeco 거부 상태)와 같은 조건 ABBA로 비교.

**G1이 끝나면 멈추고 보고한다.** Exit에서 FPS가 오르지 않으면 원인(어느 단계 비용인지)을 보고하고 다음 층으로 가지 않는다.

## G2 이후 (G1 승인 뒤에만)

- **G2 카메라·행성 값:** `lockRotation`, `lockScale`, 행성 추종, Camera·CameraAspect 배치. 명세 2절의 프레임 입력을 GPU 평가에 넘긴다. Camera 배치의 `ScreenToWorldPoint`와 `clampToScreen` 갱신 시점(명세 4절 6번)을 재현한다.
- **G3 반복·이미지 부가:** `tile`, `originalSize`, `cropPivotOffset`. 텍스처 랩 공유 규칙(명세 4절 9번)에 주의한다.
- **G4 깊이 변경:** 설계부터 제출. 재계획 끊김 없이 구간 순서를 바꿀 방법과 동점 규칙의 관계를 다룬다.
- **G5 마스크:** 소비자·제공자를 원래 방식으로 둘 때와 직접 그릴 때의 비용을 먼저 비교한다.
- **마지막:** 범위가 넓어진 상태에서 전체 맵 전곡 끔/켬과 픽셀 대조. 그 뒤 칠하는 양과 오브젝트 제거를 검토한다.
