# 첫 열기 이미지 압축 지각 — 2026-11-04

압축할 예정인 이미지는 작업 스레드의 DXT 결과를 끝까지 기다린다. 아직 해독을 시작하지 못한 이미지도 소비 지점 앞으로 건너뛴 작업을 해제하고 다음 해독 대상으로 올린다. 새 사용자 설정은 없다. `LowCompressImages=false` 기본값과 `GpuDeco=0`은 유지한다. 압축 옵션 또는 PACL2 압축이 계획되지 않은 경로는 이 대기를 하지 않는다. 푸시·릴리스하지 않았다.

## 확인한 원인과 한계

- 기존 주석의 “포기한 이미지는 Unity가 압축”은 저사양 옵션에서 틀렸다. `TexCompress.ApplyPrefix`는 준비된 결과가 있는 텍스처만 Substitute한다. 직접 계측한 이전 방식 DD 첫/둘째 판의 지각 1135/392장은 **모두 RGBA32, isReadable=false**였다. 준비된 1525/2272장은 DXT였다. 압축 끔은 RGBA/ARGB/RGB만 남았다.
- 결과가 준비된 동일 텍스처를 `Reinitialize(DXT)`하므로 별도 원본 Texture2D를 만들어 남기는 구현은 아니다. 모든 판의 전체 Texture2D 수는 DD 3402로 같고, 추적 이미지의 CPU 읽기 가능 사본은 없었다. **드라이버 내부 복사·잔류 할당까지 부정하는 증거는 아니다.** Player의 Profiler는 추적 텍스처별 메모리를 0으로 보고했다. 따라서 추출 로그의 runtime_MB=0을 실제 GPU/CPU 메모리 0으로 해석하지 않는다.
- 이번 이전 방식 첫 판도 234.1 FPS였다. **과거 76 FPS는 재현하지 못했다.** nocap 931장·7391MB가 빠르고 base1 1658장·6801MB가 느렸던 원인은 지각 수나 전용 메모리 총량만으로 설명할 수 없다. 이미지별 실제 사용량·상주 집합·페이징 순서는 이번 수치로 확정하지 않는다. GPU timestamp는 경과 시간이며 GPU busy나 페이징의 직접 증거가 아니다.
- 압축 끔 두 판은 GPU 30.93/32.19ms로 느린 상태를 재현했다. 캐시가 있어도 압축을 사용하지 않으므로 첫/둘째 판 차이는 작았다. 압축 옵션이 꺼진 일반 사용자에게 이 수정이 압축을 몰래 켜지는 않는다. 이 경로의 큰 GPU 시간은 해결했다고 주장하지 않는다.
- 캐시는 3072MB 한도에 실제 도달했다(원래 3071MB, DD 수정 후 보관본 3068MB). `PersistentBlobCache.Write`는 용량 초과 때 LastWriteTime이 오래된 파일을 지운다. 읽기는 시간을 갱신하지 않아 LRU가 아니다. 다른 맵 뒤의 DD 캐시 누락을 일으킬 수 있는 **확인된 메커니즘**이지만, 과거 gq 판별 어떤 파일이 밀렸는지 복원하지 못했다. 상한을 늘려 증상을 가리지는 않았다.

## 재현·보존

`python tools/optimization/cold-open-runs.py --maps dd wf ar --modes wait --label 새이름`은 원래 `%LOCALAPPDATA%/StutterFix/asset-cache`를 이름 변경해 보관하고, 각 맵/조건의 새 캐시를 별도 이름으로 보관한 뒤 finally에서 원래 것을 복원한다. Research·runs 등 다른 하위 폴더는 변경하지 않는다. 각 게임은 작업 루트의 `run_locked.py … wt-partial … --probe`로 실행한다. `coldopen legacy`는 시험 빌드에만 있는 이전 분기 대조다. 일반 Player에는 진단 클래스가 없다.

[원시 추출·실행 단계](evidence/cold-open/summary.json), 전체 로그 `E:/StutterFixWork/night-results/cold*.log`. `cold-open-report.py`로 실패와 느린 판을 포함해 다시 추출할 수 있다. 원래 캐시 복원 메시지를 확인했다. 최종 설치 복원 검사는 B 종료 뒤 다시 기록한다.
