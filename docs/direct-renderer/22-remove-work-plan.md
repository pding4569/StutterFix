# 일 자체를 없애는 구조 (2026-11-17, 사용자 승인)

직통 렌더러(관찰형)는 게임이 유니티 오브젝트에 쓰는 것을 C# 에서 하나하나 따라 해야 해서 원본을 넘지 못했다
(HELLO 77%, Exit 64%, WF 70%, 7777 54%, Arche 40%). 방향: 맵 내용(장식·타일)의 겉모습을 우리가 곡 시간으로
직접 계산해 렌더러로 바로 보내고, 유니티 오브젝트 쓰기·스크립트·감시를 없앤다.

## 단계
- R1 타일 겉모습: scrFloor.Update/LateUpdate·FloorMeshRenderer 의 겉모습 쓰기(색·아이콘·반짝임·트랙 스타일)를 곡 시간·타일 상태의 함수로 계산해 렌더러 상수로 직접. 게임 진행에 쓰이는 값(타일 위치·각도·판정 상태)은 그대로 유지. 목표 맵 Exit·7777.
- R2 장식: GpuDeco 굽기 표(00-deco-spec.md 의 매 프레임 식)로 장식 pose·색·보임을 계산해 렌더러에 직접. 유니티 Transform 쓰기·DOTween 장식 트윈·TightLate 제거. 히트박스·글자·오브젝트·파티클·혼합 모드는 기존 경로. 목표 맵 HELLO·WF·Arche.
- R3 렌더러 감시 최소화: 소유 대상은 감시·Refresh·포즈 읽기 제외. 남는 감시는 행성·캔버스·파티클 등.
- 검증: `drfull constcheck`(소유 상수 대 원본이 썼을 값), 재생 뒤 픽셀(`pp-*-st`), 그림자 모드(일부 프레임만 원본 스크립트를 돌려 값 비교), 장식은 decobake verify 기준(시작 1프레임·0.01px).

## 주의 (과거 실패)
- deco-v2: 자체 셰이더 합치기에서 픽셀 >3/255 어긋남 → 이번엔 원본 셰이더(직통 렌더러) 사용.
- GpuDeco 그리기는 3440 WF 에서 GPU 두 배(원인 미확인) → 그리기는 직통 렌더러로.
- 보임 콜백(OnBecameVisible/isVisible)에 묶인 게임 갱신은 Visibility 대행 유지.

## 근거 3 (11-17): 새 렌더러는 일을 없애는 데 방해가 된다
같은 계획(3440, seek, 12초), 타일 Update/LateUpdate + scrDecorationManager.LateUpdate 를 끈 상한:
| 맵 | 원본 | 원본 렌더러 + 스크립트 끔 | 새 렌더러 + 스크립트 끔 | 천장(맵 안 그림) |
|---|---|---|---|---|
| HELLO 50초 | 약 200 | **275.2** (3.63ms) | 195.2 (5.19ms) | 401.5 (2.49ms) |
| Exit 88초 | 약 343 | **403.7** (2.47ms) | 307.5 (3.29ms) | 531.0 (1.88ms) |
- 쓰기가 없어도 새 렌더러(감시 IL·PreCull·렌더 스레드 기다림)가 원본 유니티 그리기보다 HELLO 1.56ms, Exit 0.82ms 더 든다.
- 원본 유니티의 맵 그리기 메인 스레드 비용은 HELLO 1.14ms, Exit 0.59ms(천장과의 차이)뿐이다.
- **결정: 렌더러는 원본 유니티 그대로 두고, 게임 스크립트의 일을 줄인다.** 그리기가 원본이라 픽셀 검증이 쉽다(같은 값이면 같은 그림).

## 근거 4 (11-17 오후): 원본 렌더러에서 무엇을 없앨 수 있나 (HELLO 50초, 3440, 이미지 1536 판 포함)
나눠 끈 상한(원본 렌더러, 12초, presentpath gputime 켠 채):
| 판 | FPS | 합계 | 그리기 마무리 | Update | LateUpdate |
|---|---|---|---|---|---|
| 원본 | 208.2 | 4.80 | 1.77 | 1.33 | 0.74 |
| 타일 스크립트 끔 | 210.4 | 4.75 | 1.78 | 1.28 | 0.74 |
| 장식 LateUpdate 끔 | 264.2 | 3.78 | 1.25 | 1.24 | 0.41 |
Exit: 원본 341.1, 타일 끔 357.6(+5%), 타일+장식 끔 403.7.
- **주의: 장식 끔 상한은 부풀려졌다.** 토글 뒤 파이프라인 통계: 삼각형 16,378→13,991(-15%), 픽셀 셰이더 8.94억→8.24억(-8%). 멈춘 장식이 화면 밖으로 빠져 그릴 것이 준다.
- 엔진 프로파일 차이(원본-장식 끔, ms/프레임): 장식 스크립트 0.35, 카메라 그리기 0.46, 출력 대기 0.26. 그리기 쪽 일부는 위의 그릴 것 감소 몫.
- TightLate 가 맡는 장식 프레임당 130개 중 위치가 실제로 바뀌는 비율 99%(같은 값 건너뛰기 켜도 208.6→207.6). 마스크·히트박스·메시로 원래 경로 105개/프레임. → 남은 장식 일은 대부분 진짜 변화다.
- **측정 비용**: presentpath gputime 을 창 안에서 끄면 같은 원본이 230 FPS(켠 판 208). 판끼리 비교는 유효하나 절대값은 낮게 나온다.

## 근거 5: GpuDeco GPU 비용 (같은 정지 장면, 메인 카메라 GPU)
| 상태 | 카메라 GPU | 비고 |

| 모드1 읽고 전부 버림 / 모드3 바로 버림 | 4.57 / 4.56 | (모드1 은 컴파일러가 읽기를 지웠을 수 있음) |

| 버리기 끔(sfnodiscard) | 8.74 | |
| 색만(sfflat) / SF_SIMPLE | 8.11 / 8.02 | 둘 다 버리기 없음 |
| 이미지 효과 단계 | 0.43 (전부 같음) | |
- 결론: 추가 비용은 섞기(ROP) 단계. 원본 Sprites/Tile 은 버리기 없이 전부 섞는데도 싸다. 원인 미확인(진짜 GPU 프로파일러 필요). RenderDoc 은 doorstop(UMM)이 안 불려 실패(rd-run4.py).
- `sfdebug`/`sfflat` 를 한 번 바꾸면 보통 모드가 6.70→7.78ms 로 느려진 채 남는다(sfnodiscard·sfsimple 은 안 그럼). 한 판에 섞지 말 것.
- Windflower 는 GpuDeco 배열 2.8GB + VRAM 7.7/7.9GB → 판마다 212/158/119 FPS 로 흔들림(끔 217/223 안정). VRAM 예산 없이 배열을 만들면 안 된다.
- NoFx 는 장식까지 숨기는 모드라 필터 분리 시험으로 쓸 수 없다.
