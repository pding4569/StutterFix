## 결론과 열린 문제
1. **GpuDeco 켬(3.0.0 기본)이 곡 시작 직후와 일부 구간에 큰 끊김을 만든다.** GpuDeco 를 끄면 두 맵 모두 끊김 0. 전곡 FPS 로 본 GpuDeco 의 이득은 HELLO 에서 없음(켬 270 대 끔 279, 같은 빌드 한 판씩), Arche 에서 +7%(492 대 461) 정도라 "끊김 제거가 FPS 보다 우선"이라는 목표와 충돌한다. 이식한 2.8.2 수정 때문이 아니다(이식 전 빌드에도 같은 끊김).
2. HELLO 곡 5.1초 99+80ms: `[모니터]` 분류 "게임 처리"(gpu 0.6ms, cpu 99ms → 메인 스레드가 엔진 안에서 쓴 시간). `GpuLiveFrame` 은 6ms 미만(느린 프레임 로그 0줄)이라 우리 쪽 디스패치 코드가 아니다. `GpuDecoImages=0`·`GpuDecoDetach=false` 로도 그대로. GpuDeco 그리기 셰이더(GpuDecoBatch/Blend, 키워드 3종)를 `ShaderVariantCollection.WarmUp` 으로 준비 단계에 미리 만들어도(1.2ms) 그대로 → 셰이더 만들기가 원인이 아닐 가능성이 크다(되돌림). `profsamp`(1kHz, 네이티브 풀기)로는 시작 직후 두 프레임이 표본에 잡히지 않아 위치 미확인. 다음 후보: 첫 그리기 프레임의 엔진 안쪽(컴퓨트 버퍼·구성 변경)을 PerfView ThreadTime + etwstall 로 보기(관리자 필요).
3. Arche 11.3초 190ms, 48.6~49.6초 "게임 바깥" 클러스터는 GpuDeco 끔에서 사라짐. 같은 계열(첫 사용·VRAM 이동)로 보이나 미조사.
4. Windflower 전곡 로그에 `GpuDeco 준비 예외: image collapse texture coverage incomplete` 와 `DivideByZeroException`(Blur_Movie, 원래 게임 버그) 579줄. 준비 예외는 GpuDeco 가 스스로 물러난 경우로 보이며(끊김 0) 원인 미조사.
5. 결정 필요(사용자): 3.0.0 에서 GpuDeco 기본을 어떻게 할지. 하드 요건(모드발 끊김 0)을 지키려면 끔이 맞고, 끊김을 고친 뒤 켜는 것이 목표.
