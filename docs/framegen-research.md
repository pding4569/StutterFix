# 프레임 보간·생성 가능성 조사 (2026-10-06~07)

1~10장은 클라우드에서 코드·자료·시뮬레이션으로 조사한 내용이다. 11장은 개발 PC의 실제 출력·게임 측정이다.

결론 먼저: **"두 프레임 사이를 만드는 진짜 보간"은 이 게임에 안 맞는다. 대신 "카메라 움직임만 앞당겨 그리는 재투영(타임워프)"은 이 모드가 가진 부품으로 시험해 볼 만하다.**
쓸모가 있는 사람은 **CPU 가 느려 곡 중 FPS 가 모니터 주사율보다 한참 낮은 사용자**뿐이다. 개발 PC(곡 중 200~400 FPS, 164Hz)에는 필요 없다.

## 1. 방식별 정리

| 방식 | 하는 일 | 입력 지연 | 이 게임에서 |
|---|---|---|---|
| **A. 보간** (DLSS FG, FSR 3 FG, AFMF, Lossless Scaling) | 프레임 N 과 N+1 사이를 만든다 | **+1프레임 이상** (N+1 을 기다려야 함) | 리듬 게임에 치명적. 아래 2장 |
| **B. 외삽** | 지난 프레임들로 다음 프레임을 예측 | 늘지 않음 | 빠르게 도는 행성 둘레가 깨지기 쉬움 |
| **C. 재투영 (타임워프)** | 마지막 프레임을 **카메라가 움직인 만큼만** 옮기고 돌리고 확대해 한 번 더 낸다 | 늘지 않음 | 시험해 볼 만함. 아래 4장 |
| **D. 바깥 도구** (NVIDIA Smooth Motion, AMD AFMF, Lossless Scaling) | A 를 드라이버·앱이 함 | 늘어남 | 사용자가 알아서. 모드는 켜져 있으면 알려 주기만 |

## 2. A(보간)가 안 맞는 이유

- **지연**: N+1 을 다 그린 뒤에야 사이 프레임을 낼 수 있어 화면이 최소 한 프레임 늦다. 60 FPS 바탕이면 약 +17ms. 얼불춤은 화면을 보고 박자를 맞추는 게임이라, 오프셋을 다시 맞춰도 손맛이 달라진다.
- **FSR 3 프레임 생성은 DirectX 12·Vulkan 전용**이다(AMD 문서). 이 게임은 D3D11 로 돈다(D3D12 는 곡 중 60~80ms 멈춤이 있어 CLAUDE.md 에서 버렸다).
- **DLSS 프레임 생성**은 게임이 모션 벡터·깊이를 넘겨줘야 하고 NVIDIA 통합이 필요하다. 모드로는 안 된다.
- **직접 만든 광학 흐름(화면만 보고 움직임 추정)**: D3D11 컴퓨트 셰이더로 만들 수는 있지만, 2D 스프라이트가 빠르게 돌고 번쩍이는 이 게임에서는 깨짐이 많고 무겁다.

## 3. 게임 쪽 사정

- 이 게임은 2D 이고 **모션 벡터를 만들지 않는다**(유니티 기본 렌더 파이프라인의 스프라이트는 모션 벡터를 쓰지 않음 `[확인]`).
- 대신 **움직임이 대부분 계산으로 정해져 있다**: 카메라는 맵 이벤트(위치·회전·확대·이징)와 곡 시간으로, 행성은 BPM 과 각도로 위치가 정해진다. 장식 이동도 표(트윈)로 정해져 있다.
  → 화면을 보고 추측할 필요 없이 **"다음 순간 카메라가 어디 있을지"를 게임 상태에서 정확히 알 수 있다.** 이것이 C 를 고르는 이유.
- 플레이 중 게임 화면은 카메라 3개를 `scrCamera.camRT` 한 장에 그리고 사각형(quad)으로 낸다. **UI 는 따로 화면에 그린다.** 그래서 게임 화면 그림만 옮기고 UI 는 그대로 둘 수 있다.

## 4. C(재투영)를 이 모드로 만드는 법

### 이미 있는 부품

| 부품 | 어디 | 쓰임 |
|---|---|---|
| 스왑체인 찾기 | `GfxProbe.MainSwapChain` | 생성한 프레임을 화면에 낼 곳 |
| 유니티 그래픽 스레드에서 `Present` 하기 | `WindowGhost.PresentOnce` → `GL.IssuePluginEvent` → `sfnative` | 유니티 프레임 사이에 프레임을 하나 더 냄. Flip 방식에서 그리기 대상이 떨어지는 문제를 되돌리는 처리까지 이미 있음 |
| 게임 화면 그림 | `scrCamera.camRT` (`LowEnd`·`Fsr`·`HalfRender` 가 다룸) | 옮길 원본 |
| 2D 그리기 셰이더 묶기 | `fsr/` (AssetBundle) | 옮기기·회전·확대 셰이더 |

### 흐름 (안)

1. 유니티 프레임이 끝날 때 camRT 와 그때의 카메라 상태(위치·회전·확대)를 기억한다.
2. 다음 유니티 프레임이 늦어질 것 같으면(직전 프레임 시간 > 주사율 간격), 주사율 간격의 중간쯤에 그래픽 스레드에서:
   - 그 순간의 카메라 상태를 **곡 시간으로 계산**(맵 카메라 이벤트를 이징까지 따라감, 또는 직전 두 프레임으로 짧게 외삽),
   - camRT 를 차이만큼 옮기고 돌리고 확대해 백 버퍼에 그리고, **UI 는 마지막 것을 그대로 덮고**,
   - `Present`.
3. 가장자리에 빈 곳이 생기므로 camRT 를 화면보다 조금 크게(여백 5~10%) 그린다. 슈퍼샘플링·렌더 배율 코드와 같이 쓸 수 있다.

### 한계 (보이는 것)

- **카메라만 맞고 화면 속 물체는 멈춰 있다.** 행성 회전, 장식 이동, 타일 효과는 생성 프레임에서 안 움직인다. 카메라가 행성을 따라가는 이 게임 특성상 화면 전체가 부드러워 보이는 효과는 있겠지만, 행성 자체는 진짜 프레임에서만 움직인다.
  → 개선안: 행성만 따로 그려 생성 프레임에 정확한 위치로 얹기(행성 위치는 계산 가능). 일이 커서 2단계.
- 번쩍·필터 같은 화면 효과는 마지막 프레임 것이 그대로 남는다.
- 판정·입력은 바뀌지 않는다(게임 로직은 진짜 프레임에서만 돈다).

## 5. 시험 계획 (PC 에서, 작은 것부터)

1. **필요한 사람이 있는지부터**: 약한 PC(또는 개발 PC 에서 CPU 를 일부러 묶어 곡 중 50~70 FPS)로 무거운 맵을 돌려, 사람이 "끊겨 보인다"고 느끼는지.
2. **가장 싼 시험**: 생성 프레임 = 마지막 그림을 카메라 이동만큼 옮기기(회전·확대 없이). PresentMon 으로 화면에 나온 간격이 고르게 됐는지, 입력 지연(프레임 시작 → 화면)이 늘지 않았는지.
3. 눈으로 보기: 행성이 진짜 프레임에서만 움직이는 게 거슬리는지. 거슬리면 2단계(행성 따로) 또는 중단.

## 6. 얼불춤 전용으로 새로 만들기: "그리기만 하는 프레임"

이 게임은 화면이 곡 시간으로 거의 다 정해지므로, 그림을 옮겨 붙이는(재투영) 대신 **그 순간의 진짜 장면을 그리되, 비싼 게임 로직은 건너뛴 프레임**을 끼울 수 있다.

- 진짜 프레임: 게임 로직 전부(입력·판정·효과 시작·장식 스크립트·박자 알림) + 그리기.
- 끼우는 프레임: **계산으로 정해지는 것만 그 시각으로 옮기고**(카메라, 행성 회전, 진행 중인 애니메이션 표: 모드가 이미 `DecoAnim`·`FloorAnim` 으로 직접 돌리는 것들) **그리기만** 한다. 효과 시작·판정·장식 스크립트는 다음 진짜 프레임에서.
- 방법 후보: PlayerLoop 에서 무거운 스크립트 단계를 번갈아 건너뛰기(입력·판정은 매 프레임 유지), 또는 진짜 프레임 사이에 `Camera.Render` + 그래픽 스레드 `Present`(4장 부품).

### 2배가 되나

**병목이 어디냐에 달려 있고, 재 보기 전에는 모른다.**

| 프레임 시간을 먹는 곳 | 끼우는 프레임의 이득 |
|---|---|
| 게임 로직 (Update·LateUpdate 스크립트, 효과 시작, 장식 갱신) | **크다.** 로직이 프레임의 2/3 면 끼우는 프레임은 1/3 비용 → 보이는 FPS 최대 약 2배 |
| 그리기 준비 (컬링, 배치, FinishFrameRendering) | 거의 없다. 끼우는 프레임도 똑같이 그려야 함 |
| GPU | 없다. 오히려 GPU 일이 늘어남 |

- 모드에는 이미 끊긴 프레임의 엔진 단계를 나누는 `PhaseWatch` 가 있다. **0단계: 무거운 맵에서 평균 프레임의 단계별 비율을 잰다.** 로직 비율이 크면 진행, 그리기가 크면 그만둔다.
- 재투영(4장)은 그림을 옮기는 것이라 늘 "보이는 FPS 2배"가 되지만 새 정보가 없다. 이 방식은 진짜 장면이라 더 낫지만, 이득은 맵마다 다르다.

### 대가 (원래 게임과 달라지는 것)

- 효과·색 바꾸기·장식 스크립트가 시작되는 순간이 최대 한 프레임 늦을 수 있다(진짜 프레임에서만 시작). 판정은 그대로.
- 그래서 "원래 게임과 같음" 원칙의 최적화 쪽이 아니라 **실험 기능**이다. 기본 꺼짐, 끄면 완전히 원래대로.

## 7. 배수 고르기 (Lossless Scaling 처럼 2·3·4배)

4장(재투영)과 6장(그리기만 하는 프레임) 둘 다 **진짜 프레임 하나 뒤에 N-1 개를 끼우는 방식으로 늘릴 수 있다.** 설정은 "배수 2/3/4" 또는 "목표 = 모니터 주사율(자동)".

| | Lossless Scaling (보간) | 모드 재투영 | 모드 그리기만 하는 프레임 |
|---|---|---|---|
| 끼우는 프레임 만드는 법 | 두 그림 사이를 AI·광학 흐름으로 추측 | 마지막 그림을 카메라만큼 옮김 | 그 시각의 장면을 진짜로 그림(로직 건너뜀) |
| 입력 지연 | 늘어남 (다음 프레임을 기다림) | **안 늘어남** | **안 늘어남** |
| 화면 속 물체 | 추측이라 깨짐이 생길 수 있음 | 카메라만 맞고 행성·장식은 진짜 프레임에서만 움직임 | **전부 맞음** |
| 비용 | GPU | 아주 쌈 | 그리기 한 번만큼 (로직이 병목일 때만 이득) |
| 배수 | 2·3·4배 등 | 2·3·4배 쉬움 | 그리기 비용이 허락하는 만큼 |

- **배수 위 한계는 모니터 주사율이다.** 164Hz 모니터에서 진짜 60 FPS 면 2배(120) 또는 2.7배(164)까지가 의미 있고, 그 위는 화면에 안 나온다. 진짜 FPS 가 이미 주사율보다 높은 PC(개발 PC 곡 중 200~400)에는 쓸모가 없다.
- 프레임을 고른 간격으로 내는 것(페이싱)이 중요하다. 그래픽 스레드 `Present` 타이밍을 주사율 간격에 맞추고, PresentMon 으로 화면에 나온 간격을 잰다.
- 재투영과 그리기만 하는 프레임을 섞을 수 있다: 끼우는 프레임마다 행성만 진짜로 다시 그리고 나머지는 옮기기.

## 8. 정리

- 보간(A)은 지연 때문에 하지 않는다.
- 재투영(C)은 고사양 페이지가 아니라 **저사양 페이지의 실험 기능**이 맞다(느린 PC 를 위한 것). 기본 꺼짐.
- 바깥 도구(D)는 모드가 켜져 있는지 알아채 모니터·로그에 표시만 한다.

출처: FSR 3 프레임 생성 = DirectX 12·Vulkan 전용 (AMD GPUOpen FidelityFX SDK 문서, FSR 3.1 소개).

## 9. 실행 계획 (2026-10-06 결정: 최적화 다음 단계로 진행)

방식: **지연을 늘리지 않는 쪽**(재투영 → 그리기만 하는 프레임). 두 그림 사이를 기다리는 보간은 하지 않는다.
모니터 표시는 "진짜 FPS / 표시 FPS" 를 따로.

| 단계 | 누가 | 할 일 | 끝 기준 |
|---|---|---|---|
| 0 | Claude (PC) | 무거운 맵 곡 중 평균 프레임 단계별 비율(로직/그리기/GPU), CPU 를 묶은 60 FPS 상태 만들기 | 비율 표 |
| 1a | Codex | 게임 밖 시험 프로그램(유니티와 같은 Flip + 대기 객체 스왑체인)에서: 텍스처를 옮기기·회전·확대해 백 버퍼에 그리는 D3D11 셰이더, 주사율 간격에 맞춘 `Present` 타이밍(배수 2/3/4) | PresentMon 화면 간격 고름 |
| 1b | Claude (PC) | 모드 쪽: 진짜 프레임 끝에 camRT·카메라 상태 저장, **UI 를 게임 화면과 따로 얻는 방법** 찾기(가장 어려운 부분) | UI 가 따로 담긴 그림 |
| 2 | Claude | 1a 를 sfnative 에 넣고 모드에 연결, 실험 설정(기본 꺼짐) | 2배에서 화면 간격 고름, 지연(프레임 시작→화면) 그대로 |
| 3 | 둘 | 3·4배, 자동(주사율에 맞춤), 끄면 완전히 원래대로 | |
| 4 | Claude | 행성만 진짜로 다시 그리기 또는 그리기만 하는 프레임 | 행성이 끼운 프레임에서도 움직임 |

나누는 규칙: Codex 는 시험 프로그램 폴더(또는 별도 브랜치)만 고친다. 같은 파일을 동시에 고치지 않는다.

## 10. 시뮬레이션 결과 (2026-10-06, 클라우드, `tools/framegensim/sim.py`)

게임 없이 얼불춤 비슷한 2D 장면(타일 길, 한 박에 180도 도는 행성 둘, 행성을 부드럽게 따라가는 카메라 + 박마다 확대, 따로 움직이는 장식)을 만들고,
약한 PC 처럼 흔들리는 진짜 프레임(가끔 20~50ms 긴 프레임)에서 164Hz 모니터에 각 방식이 내는 그림을 그 순간의 정답과 비교했다.
**모델이라 실제 게임 숫자가 아니다.** 방식끼리의 차이를 보는 용도.

기본 60 FPS (프레임 중앙값 16.9ms):

| 방식 | 행성 나이 평균/95% (ms) | 행성 위치 오차 평균/95% (px) | 화면 오차 | 움직임 들쭉날쭉 (정답 0.66) |
|---|---|---|---|---|
| none (지금) | 27.6 / 49.6 | 4.4 / 10.9 | 4.30 | 1.85 |
| reproj (카메라만 옮김) | 27.6 / 49.6 | 3.7 / 11.6 | 2.15 | 1.40 |
| **reproj+pl (옮김 + 행성만 다시)** | **1.0 / 1.0** | **0.1 / 0.5** | 1.28 | **0.66** |
| interp (보간, 완벽하다고 가정) | 35.3 / 49.6 | 5.6 / 13.2 | 5.30 | 0.92 |
| render (그리기만 하는 프레임) | 2.0 / 2.0 | 0.3 / 0.8 | 0.37 | 0.66 |

기본 30 FPS: none 행성 나이 51ms·들쭉날쭉 2.65 / reproj 51ms·1.92 / reproj+pl 1ms·0.66 / interp 68ms·1.05.
기본 100 FPS: none 18ms·1.76 / reproj 18ms·1.51 / reproj+pl 1ms·0.66 / interp 22ms·1.36.

읽는 법과 결론:
- **보간(interp)은 완벽하게 만들어도 행성 나이가 지금보다 늘어난다**(60 FPS 에서 27.6 → 35.3ms, 30 FPS 에서 51 → 68ms). 움직임은 부드러워지지만 박자를 보는 화면이 더 늦다. 리듬 게임에서 하지 않는 이유가 숫자로도 나온다.
- **카메라만 옮기기(reproj)는 화면 전체 오차는 절반으로 줄지만 행성은 그대로 늦다.** 화면이 부드럽게 흐르는데 행성만 뚝뚝 끊기는 모양이 된다.
- **옮기기 + 행성만 다시 그리기(reproj+pl)가 핵심이다.** 행성 나이가 1ms 로 떨어지고(지금보다 26ms 빠름) 움직임이 정답과 같아진다. 남는 오차는 타일 효과·장식이 진짜 프레임에서만 움직이는 것.
- render(그리기만 하는 프레임)가 가장 좋지만 그 순간 장면 전체를 그릴 여유가 있을 때만(로직이 병목인 맵).
- → 9장 계획의 4단계(행성만 다시 그리기)를 **2단계와 묶어 처음부터** 하는 것이 맞다. 카메라만 옮기는 것은 중간 확인용.

가정(실제와 다를 수 있는 것): 끼운 프레임을 만드는 데 1ms, 보간은 품질 손실 없음, 화면은 매 주사율 칸마다 새 그림(VRR·찢어짐 없음), UI 는 다루지 않음.

## 11. PC 구현·측정 (2026-10-07, `codex/framegen`)

이번 범위는 9장 **1a → 0단계**다. 구현은 `tools/framegenlab/`에만 두었다. 정식 모드의 설정·렌더링·버전은 바꾸지 않았다.
목표는 10장 결론대로 **행성 없는 지난 그림을 현재 카메라로 옮기고, 행성 둘만 현재 시각으로 그리기**다.
실제 게임의 카메라·행성 상태를 복원하는 1b/2단계는 아직이다.

### 1a: 게임 밖 D3D11 출력

직접 만든 타일 길·장식·행성 장면을 쓴다. 지난 원본 텍스처는 15% 여백을 두고, 이동·회전·확대를 셰이더로 합성한다.
행성은 원본에 넣지 않으므로 지난 행성 그림이 남지 않는다. UI를 흉내 낸 줄은 재투영 뒤에 고정해서 그린다.
`none / reproj / hybrid`를 비교할 수 있다. 진짜 프레임 N+1을 기다리지 않고 현재까지 얻은 원본만 쓴다.

FlipDiscard, 백 버퍼 2개, 프레임 대기 객체, 최대 대기 1개, `Present(1,0)`.
고해상도 대기 타이머로 목표 주기를 기다리고, 늦어진 슬롯은 건너뛴다. 미뤄진 출력을 몰아서 내지 않는다.
**보통 대기 타이머는 여기서 맞지 않았다**: 144Hz/2배/5초 시험에서 404회 출력·316칸 놓침. 고해상도 타이머 뒤 같은 15초 조건에서 2,160회 출력·놓침 0.
유니티의 기존 Present(0)·그래픽 스레드 큐에 넣었을 때는 다시 검증해야 한다.

매 실행 전에 GPU 셰이더의 UV 변환을 독립 CPU 계산과 32가지 카메라·512점 대조했다. **모두 허용 오차 1/255 이내**.
이는 좌표 변환 확인이며 실제 게임의 카메라 상태 복원·UI 분리·입력 지연을 검증한 것은 아니다.

이 실행의 모니터는 **144Hz**였다. 과거 문서의 164/165Hz 숫자를 쓰지 않았다. 1280×720 창, 배수마다 15초, 시작·끝 1초 제외:

|---|---:|---:|---|---:|---|
| 2 | 72 | 144.0 | 6.95 / 7.23 / 7.47ms | 1,866 | 모두 1칸 |

**측정 수단은 DXGI `GetFrameStatistics`**다. PresentCount·PresentRefreshCount·SyncRefreshCount·SyncQPCTime을 기록하고,
PresentCount가 연속인 쌍만 간격을 비교했다. 관찰에서 빠진 번호는 각각 2/5/21개로 별도 기록했다(모두 드롭이었다고 가정하지 않는다).
원본 60 FPS에서 2배(120)를 요청하면 144Hz 고정 주사율 칸과 나누어떨어지지 않으므로 1칸/2칸이 섞이는 것이 정상이다.
3·4배는 모니터 한도에서 잘린다. 표시 횟수와 원본 갱신 횟수를 구분한다.
추가 15초 대조: 원본 60 FPS만 출력하면 2/3칸(467/311쌍), 2배 요청에서는 1/2칸(629/312쌍)이 관찰됐다.
2배에서는 관찰에서 빠진 Present 번호가 309개이므로 간격 역수 108.1을 전체 표시 FPS로 단정하지 않는다.
출력 시작 QPC→DXGI 표시 시각은 관찰된 표본 평균 4.88→4.69ms(95% 7.97→7.30ms).
이는 독립 장면의 출력 지연으로, 게임 입력 지연이나 통합 뒤 지연이 늘지 않았다는 증거는 아니다.

**PresentMon 기준은 아직 통과로 처리하지 않는다.** 관리자 실행, 이름/PID 지정, 필터 없이, ASCII 출력 경로,
2.5.1/공식 2.6.0, 별도 콘솔, GPU·입력 추적 제외까지 시험했지만 실시간 표시 CSV가 생기지 않았다.
한편 logman의 DXGI 전용 5초 ETL에는 이벤트 14,793개가 있었고, PresentMon은 이 ETL을 표시·GPU 추적 없이 오프라인으로 읽어 Present 2,518개를 CSV로 만들었다.
WPR GPU + DesktopComposition(DWM·Win32k 포함)으로 2/3/4배를 각각 8초 기록해도, 표시 추적을 켠 오프라인 분석에서는 CSV가 생기지 않았다.
GPU 전용 WPR ETL은 표시·GPU 추적을 끄면 Present CSV로 읽혔다. WPR 종료 시 `-skipPdbGen`을 쓰고 PowerShell 5의 native stderr를 오류 로그로 보존해야 한다.
PowerShell의 `ErrorActionPreference=Stop`으로 native stderr를 중단시키면 WPR 종료가 끊어져 기록이 남을 수 있다. 자기 기록은 종료·해제 완료를 확인했다.
따라서 이벤트 자체가 없는 것으로 단정하지 않는다. **실시간 표시 추적이 끝나지 않는 원인은 미확정**이다.
DXGI 표시 검증은 성공했지만 PresentMon 표시/GPU 검증은 미완료이며, 게임의 실제 입력 지연도 아직 재지 않았다.

### 0단계: 실제 맵 CPU 구성

게임 화면에서 맵을 열고 자동 플레이, 새 게임으로 판마다 시작. 3440×1440, 144Hz, 수직동기 0, 기존 그래픽 작업 설정과 함께 쓰던 모드를 유지했다.
자동 시험의 `wait 45` 명령을 썼다. 명령 사이 대기도 있으므로 곡의 정확한 0~45초 표본이라고 읽지 않는다.
측정 전용 PlayerAuto를 쓴다. `MeasureBuild=false`를 유지하고 자주 불리는 함수·설정 함수를 감싸지 않았다.
PlayerLoop 경계 182곳에서 타임스탬프와 숫자 배열만 더한다. 시작 5초는 제외하고, 곡 중 큰 프레임은 포함한다.
맨 끝의 바깥 구간도 합쳐 **단계 합 / 프레임 전체 = 100.000%**인지 검사했다. 종료할 때만 로그를 만든다.
측정 소스는 `out/measure/`의 사본으로 만들며 정식 빌드·테스터 ZIP에 포함하지 않는다. 해제할 때 자기 Marker만 제거한다.

## 12. 수직동기 0·실제 게임 상태 캡처 (2026-10-07, `codex/framegen`)

이번 범위는 **독립 시험 프로그램의 비동기 출력 → 1b 실험**이다. 정식 기능·버전·게임 렌더링 경로는 바꾸지 않는다.
측정 DLL은 `build_measure.ps1 -Probe Capture`로 만든 소스 사본에만 코드를 주입한다. 이번 실험을 정식 빌드나 테스터 ZIP에 넣지 않는다.
기존 테스터 ZIP은 보존하며, `pack.ps1`은 이번 GPU 측정 옵션이 들어간 바이너리의 포장을 거부한다.

### 12.1. 수직동기 끈 독립 출력

3440×1440 전체 화면 창, RTX 4060 Ti, 현재 모니터 144Hz. `Present(0, DXGI_PRESENT_ALLOW_TEARING)`.
ALLOW_TEARING 지원을 확인하고 스왑체인 생성 때 같은 플래그를 넣었다. FlipDiscard·버퍼 2장·대기 객체·최대 대기 1개는 유지했다.
`--sync 0`에서는 목표 출력을 주사율에서 자르지 않는다. 원본은 400/200/100 FPS의 시간표로 갱신하고, 나머지는 **카메라 재투영 + 현재 행성 둘 그리기(hybrid)**다.
각 조건 **15초 전체**를 사용하며 시작·끝을 제외하지 않았다. `run_unsynced.py`가 1초 단위 출력·원본 횟수도 남긴다.

아래 출력 FPS는 **성공한 Present 횟수 / 15초**다. 흔히 표시 FPS라고 부르는 출력률이지만, 모니터에 완전한 프레임으로 실제 표시된 수는 **확인 안 됨**.
수직동기 0에서 DXGI 표시 통계 표본은 12조건 모두 0개였다. 144Hz보다 많은 출력이 완전한 화면으로 모두 표시됐다고 해석하지 않는다.
11장의 PresentMon 표시 추적 문제도 해결된 것으로 처리하지 않는다.

GPU 시간은 CPU 제출 시간이 아니라 D3D11 timestamp 3개와 disjoint/frequency로 잰다.
128개 질의 묶음을 먼저 만들고, 프레임 중에는 `GetData(DONOTFLUSH)`로 완료된 값만 읽는다. 미완료 질의는 기다리지 않는다.
측정 뒤 한 번 Flush하고 남은 값만 회수한다. 12조건 모두 질의 빠짐·disjoint 오류 0, 유효 표본은 전체 출력 수와 같았다.
생성 프레임의 전체 draw 구간을 재므로 재투영·행성·고정 UI 띠가 포함된다. Present/대기·CPU 비용은 포함되지 않는다.
실제 게임 GPU 비용·입력 지연·전력은 **확인 안 됨**. 합성 장면에는 게임의 필터·많은 장식이 없다.

### 12.3. UI를 따로 얻기: 일부 성공, 통합 기준은 미완료

재생 진입 뒤 8초에 camRT·전체 화면을 한 번씩 읽고 실제 그림을 비교했다. 초기 시험의 2초 캡처는 아직 시작 안내 구간이어서 UI/장면 검증 표본으로 쓰지 않았다.
재생 중 camRT는 **3440×1440 ARGB32**이며 게임 장면·필터를 담고, 전체 화면에는 그 위로 진행률·콤보·키 표시·모니터 HUD가 더해졌다.
관찰한 카메라 구성:

| 카메라 | depth | cullingMask | 출력 |
|---|---:|---:|---|
| BGStaticCam | -1.63 | 2048 | camRT |
| BGMovingCam | -1.11 | 1024 | camRT |
| Camera(본 화면) | -1.00 | 652183 | camRT |
| OverlayCam | -1.63 | 1048576 | 화면 |

**이름·depth만으로 그리는 순서를 단정하지 않는다.** 마지막 판 첫 프레임만 Overlay→본 카메라였고 이후 4,668프레임은 본 카메라→Overlay였다.
지금 조건에서 Overlay가 항상 지난 camRT를 낸다는 가정은 맞지 않았다. 다른 설정/게임 상태의 순서는 확인 안 됨.

화면 위 UI의 루트 Canvas **14개**는 ScreenSpaceOverlay였고 layer **0과 5**를 함께 썼다(게임 UI와 다른 모드 UI 포함).
WorldSpace Canvas도 있었다. 레이어 5만 따로 그려서는 모든 HUD를 얻지 못하며, WorldSpace Canvas를 모두 HUD로 분류하면 맵 글자 장식도 섞일 수 있다.
ScreenSpaceOverlay는 카메라를 지정하지 않고 화면에 그리므로, 본 카메라의 `targetTexture`만 바꾸는 것으로 UI 텍스처가 생기지 않는다.

실험으로 활성 Overlay 루트만 임시 ScreenSpaceCamera로 바꾸고 전용 카메라·layer 31·투명 ARGB32 RT에 한 번 그렸다.
카메라·planeDistance·원래 레이어·RectTransform 값을 저장하고 finally에서 돌려놓았다. layer 31에 기존 scene Renderer가 있으면 실험을 중단한다.
**별도 `overlay-ui.png`에 게임 장면 없이 진행률·콤보·키 표시·판정 막대 등이 담긴 것을 눈으로 확인했다.**
이전 UI 조사 판의 RGBA 검증: 총 4,953,600픽셀 중 alpha 0 = 4,691,523, alpha 255 = 151,212, 중간 alpha = 110,865.
검정 바탕으로 장면을 덮은 그림이 아니라 투명 UI 텍스처를 얻었다.

복원 검증 마지막 판: 루트 Canvas 14개·레이어 858개·RectTransform 630개. Canvas 모드/카메라/planeDistance 차이 0, 레이어 차이 0.
그러나 **RectTransform 값 76개는 성분을 정확히 비교하면 차이가 남았다**. 로그에서 예를 들면 anchored y 63.8→63.7999878, -62→-62.0000038.
anchoredPosition을 다시 넣을 때의 반올림뿐 아니라 레이아웃 재계산도 끼어 있다. 원래 localPosition 직접 복원과 레이아웃 콜백 뒤 재복원으로도 완전한 비트 일치를 얻지 못했다.
따라서 **이 임시 전환 방식을 정식 렌더 경로로 채택하지 않는다**. 전체 UI 원본과 정확히 합성되는지, 다음 프레임 레이아웃까지 완전히 같아지는지, WorldSpace UI 분리와 스텐실·마스크·다른 모드 호환은 **확인 안 됨**.
캡처·PNG 저장·UI 시험 프레임에 약 1초의 진단 끊김이 생겼다. 이 시간을 생성 프레임 비용으로 읽지 않는다. 파일 쓰기/ReadPixels를 매 프레임 돌리는 방식은 쓰지 않는다.

다음 방법 후보(아직 확인 안 됨):

- 기존 Overlay Canvas를 그대로 화면에 그리게 두고, 생성한 게임 그림만 UI 아래에서 합성하기. UI 상태를 바꾸지 않는 장점이 있지만 추가 Present에도 UI를 유지하는 연결 지점이 필요하다.
- GUI의 실제 그리기 명령을 별도 RT로 보내거나 CanvasRenderer의 메시·재질을 별도로 복사해서 그리기. Canvas 모드/Transform을 건드리지 않고 마스크·클리핑·그리기 순서까지 보존할 수 있는지 검증해야 한다.
- 실험 진입 때 한 번만 전용 UI 카메라로 분리하고 종료 때 복원하기. 매 프레임 Canvas 전환은 피하지만 원래 HUD와 화면/레이아웃이 같다는 대조가 먼저다.

결론은 **카메라·행성 상태 읽기 성공, Overlay UI 투명 그림 얻기 성공, 완전한 UI 분리·복원과 실시간 연결은 미완료**다.
게임의 렌더링을 건너뛰거나 프레임을 끼우는 기능은 이번 실험에 없다. 원본 설치 DLL·설정은 매 실행 뒤 복구했다.
공개 요약은 `tools/framegenlab/validation-12-2026-10-07.json`, 원본 로그·CSV·그림은 무시되는 `results/`에만 둔다.

설치 DLL·Settings.xml·기존 테스터 ZIP SHA256은 실험 전과 일치했다. 연구 바이너리 포장 거부도 확인했다.

## 13. 게임 안 카메라 재투영 + 실제 행성 다시 그리기 (2026-10-07)

### 13.1 연결한 것과 실험 범위

`tools/framegenlab/InGameProbe.cs`와 `native/framegen.cpp`를 **연구용 소스 사본 빌드에만** 연결했다.
설정 `FrameGenExperiment` 기본값은 **0(끔)**, 연구 DLL의 UMM 설정창/F8에서 끔/2배/4배를 고른다.
정식 설정창·정식 프로젝트의 Compile 목록·원래 `native/sfnative.dll`을 바꾸지 않았다.
정식 빌드·테스터 ZIP에 이 기능을 넣지 않으며 기존 ZIP을 보존한다.

진짜 장면 프레임에서는 두 행성의 원래 Renderer를 그리는 동안만 숨겨 camRT를 갱신한다.
프레임 끝에 게임의 Overlay 카메라와 같은 출력 재질을 별도 RT에 그려 **UI 없는 최종 색의 게임 그림**을 저장한다.
camRT 픽셀을 그대로 최종 화면과 비교하면 화면 출력 재질/방향 차이까지 UI로 잘못 잡히기 때문이다.
생성 프레임에서는 배경 둘·본 카메라의 무거운 장면 렌더링을 건너뛴다.
EOF에서 읽은 **현재 카메라 위치·회전·orthographicSize**로 저장한 그림의 UV를 옮기고,
**원래 행성 둘의 현재 Transform·Renderer·재질**을 별도 카메라로 다시 그린다. 궤도를 추측하거나 게임 IL을 복사하지 않는다.

행성은 검정/흰 바탕 **ARGBHalf** 두 패스로 그려 `검정 결과 + 장면 × (흰 결과 − 검정 결과)`로 합친다.
8비트 흰 바탕은 가산 효과가 1에서 잘릴 수 있어 최종 측정 전에 HDR 버퍼로 바꿨다.
행성 전용 레이어는 Render 호출 안에서만 빌리고 finally에서 원래 레이어·forceRenderingOff·카메라 enabled를 복원한다.
다른 Renderer가 그 레이어를 쓰면 기능을 중단한다. Canvas 모드·RectTransform은 건드리지 않는다.

UI는 사용자 허용대로 **진짜 프레임의 픽셀을 그대로 덮는다**. 같은 프레임의 UI 없는 그림과 최종 화면이
2.5/255보다 다른 픽셀에 저장한 최종 화면을 쓴다. 반투명 UI 밑의 장면도 그 픽셀에서는 진짜 프레임 것으로 고정된다.
UI를 매번 투명 텍스처로 정확히 분리한 것은 아니다. 희미한 픽셀·마스크·모든 WorldSpace UI·필터/스킨의 완전 일치는 **확인 안 됨**.
화면 밖에서 새로 드러난 장식·카메라 펄스의 비선형 효과·행성에 걸린 화면 필터는 이 재투영만으로 복원하지 못한다.

출력은 Unity 렌더 스레드의 sfnative 콜백에서 합성한 뒤 네이티브 Present 연결을 통해 **동기 0**으로 넘긴다.
같은 프레임을 추가로 Present해서 수만 부풀리지 않는다. 각 출력은 Unity 프레임 번호와 일대일로 대조했다.
실제 엔진은 **6000.3.21f1**이었다. 기존 GfxProbe의 6000.3.10f1 주소 조회는 거부돼 최초 판을 제외했다.
최종 연결은 숨은 임시 DXGI 스왑체인에서 얻은 Present 함수표를 통해 실제 게임 창의 스왑체인을 발견한다.
엔진 내부 주소를 쓰지 않는다. 해제 때 자신의 연결만 되돌리고 전용 카메라·RT·명령 버퍼를 해제한다.

### 13.2 FPS와 시간의 뜻

이 단계에서는 **입력·판정·카메라·행성 로직을 모든 출력/Unity 틱에서 실행**한다.
‘진짜 FPS’는 무거운 게임 장면을 새로 렌더링한 횟수이며, 모든 게임 로직 틱의 횟수와 구분한다.
따라서 2배/4배는 **출력 / 장면 렌더링 비율**이다. 끔 대비 출력률이 2/4배가 되거나 원본 FPS가 유지된다는 뜻은 아니다.
메인 스레드가 멈춘 동안에도 독립적으로 출력하는 단계는 아직 구현하지 않았다.

3440×1440, D3D11, Gamma, FullScreenWindow, 144Hz, 게임 수직동기 0·목표 10000·앞서 준비하는 프레임 2.
각 조건마다 게임을 새로 켰으며 기존 플레이 설정을 유지하고 `LowHalfRender=false`, 연구 설정만 바꿨다.
공통 **곡 5~45초(40초)**를 분석한다. `wait 55`로 끝보다 여유 있게 기록하고 실제 음악 시각으로 자른다.
메뉴/카운트다운의 conductor는 아직 이전 시각을 가지고 있으므로 음악 시작 때 시각이 다시 0으로 내려간 마지막 구간만 쓴다.
구간 안 Present/Unity 번호의 누락·중복, 2/4프레임 원본 간격 불일치, 실패 HRESULT, 생성 GPU 쿼리 누락이 있으면 표를 거절한다.

‘출력 수’는 **성공한 Present 제출/s**다. 물리적 표시 FPS·드롭·입력 지연은 **확인 안 됨**.
GPU 시간은 생성 프레임의 **행성 두 패스 + 네이티브 재투영/UI 합성**을 timestamp/disjoint로 잰 평균이다.
게임 로직·UI의 기존 렌더링·Present 대기까지 포함한 전체 생성 프레임 CPU 시간은 아니다.
쿼리는 DONOTFLUSH로 나중에 회수하며, 곡 중 CSV 쓰기/이미지 읽기/GPU 결과 대기는 없다.
곡 끝의 CSV 저장·최대 2초 쿼리 회수는 측정 구간 밖이다. `--capture` 판은 성능 표에서 제외한다.

**예측한 카메라를 다음 진짜 출력에서 뒤로 바로잡는 움직임이 한 원인으로 확인됐다.** 알려진 두 카메라 사이 보간 후보에서 이 단순 이동 표본의 되돌림을 없앴지만, 사용자가 보고한 전체 흔들림이 완전히 해결됐는지는 확인 안 됨이다. 후보의 `prediction_*` 통계는 기존 예측식을 실제 원본 상태에 다시 적용한 반사실 값이며, 지연된 표시 카메라의 오차로 사용하지 않는다. 3440×1440 지원 모드는 여전히 현재 화면 목록에 없다.

연구 선택 guard 추가 뒤 일반 빌드를 다시 확인했다. 새 꺼짐 판의 네 상태 모두 runtime 초기화 False·native 연결 0·생성 0이었다. 새 2배 모니터 판은 실제 출력 계수 비율 2.000배, 원본/출력/둘 다/끔 전환·오류 0·연구 폴더 없음이었다. 설치 파일은 각 시험 뒤 원본으로 복원했다. 이 모니터 시험은 성능 표본과 구분한다.
