# 프레임 보간·생성 가능성 조사 (2026-10-06, 클라우드, 코드·자료만 봄. 게임에서 재지 않음)

결론 먼저: **"두 프레임 사이를 만드는 진짜 보간"은 이 게임에 안 맞는다. 대신 "카메라 움직임만 앞당겨 그리는 재투영(타임워프)"은 이 모드가 가진 부품으로 시험해 볼 만하다.**
쓸모가 있는 사람은 **CPU 가 느려 곡 중 FPS 가 모니터 주사율보다 한참 낮은 사용자**뿐이다. 개발 PC(곡 중 200~400 FPS, 164Hz)에는 필요 없다.

## 1. 방식별 정리

| 방식 | 하는 일 | 입력 지연 | 이 게임에서 |
|---|---|---|---|
| **A. 보간** (DLSS FG, FSR 3 FG, AFMF, Lossless Scaling) | 프레임 N 과 N+1 사이를 만든다 | **+1프레임 이상** (N+1 을 기다려야 함) | 리듬 게임에 치명적. 아래 2장 |
| **B. 외삽** | 지난 프레임들로 다음 프레임을 예측 | 늘지 않음 | 빠르게 도는 행성 둘레가 깨지기 쉬움 |
| **C. 재투영 (타임워프)** | 마지막 프레임을 **카메라가 움직인 만큼만** 옮기고 돌리고 확대해 한 번 더 낸다 | 늘지 않음 | 시험해 볼 만함. 아래 4장 |
| **D. 바깥 도구** (NVIDIA Smooth Motion, AMD AFMF, Lossless Scaling) | A 를 드라이버·앱이 함 | 늘어남 | 사용자가 알아서. 모드는 켜져 있으면 알려 주기만 |

## 2. A(보간)가 안 맞는 이유

- **지연**: N+1 을 다 그린 뒤에야 사이 프레임을 낼 수 있어 화면이 최소 한 프레임 늦다. 60 FPS 바탕이면 약 +17ms. 얼불춤은 화면을 보고 박자를 맞추는 게임이라, 오프셋을 다시 맞춰도 손맛이 달라진다.
- **FSR 3 프레임 생성은 DirectX 12·Vulkan 전용**이다(AMD 문서). 이 게임은 D3D11 로 돈다(D3D12 는 곡 중 60~80ms 멈춤이 있어 CLAUDE.md 에서 버렸다).
- **DLSS 프레임 생성**은 게임이 모션 벡터·깊이를 넘겨줘야 하고 NVIDIA 통합이 필요하다. 모드로는 안 된다.
- **직접 만든 광학 흐름(화면만 보고 움직임 추정)**: D3D11 컴퓨트 셰이더로 만들 수는 있지만, 2D 스프라이트가 빠르게 돌고 번쩍이는 이 게임에서는 깨짐이 많고 무겁다.

## 3. 게임 쪽 사정

- 이 게임은 2D 이고 **모션 벡터를 만들지 않는다**(유니티 기본 렌더 파이프라인의 스프라이트는 모션 벡터를 쓰지 않음 `[확인]`).
- 대신 **움직임이 대부분 계산으로 정해져 있다**: 카메라는 맵 이벤트(위치·회전·확대·이징)와 곡 시간으로, 행성은 BPM 과 각도로 위치가 정해진다. 장식 이동도 표(트윈)로 정해져 있다.
  → 화면을 보고 추측할 필요 없이 **"다음 순간 카메라가 어디 있을지"를 게임 상태에서 정확히 알 수 있다.** 이것이 C 를 고르는 이유.
- 플레이 중 게임 화면은 카메라 3개를 `scrCamera.camRT` 한 장에 그리고 사각형(quad)으로 낸다. **UI 는 따로 화면에 그린다.** 그래서 게임 화면 그림만 옮기고 UI 는 그대로 둘 수 있다.

## 4. C(재투영)를 이 모드로 만드는 법

### 이미 있는 부품

| 부품 | 어디 | 쓰임 |
|---|---|---|
| 스왑체인 찾기 | `GfxProbe.MainSwapChain` | 생성한 프레임을 화면에 낼 곳 |
| 유니티 그래픽 스레드에서 `Present` 하기 | `WindowGhost.PresentOnce` → `GL.IssuePluginEvent` → `sfnative` | 유니티 프레임 사이에 프레임을 하나 더 냄. Flip 방식에서 그리기 대상이 떨어지는 문제를 되돌리는 처리까지 이미 있음 |
| 게임 화면 그림 | `scrCamera.camRT` (`LowEnd`·`Fsr`·`HalfRender` 가 다룸) | 옮길 원본 |
| 2D 그리기 셰이더 묶기 | `fsr/` (AssetBundle) | 옮기기·회전·확대 셰이더 |

### 흐름 (안)

1. 유니티 프레임이 끝날 때 camRT 와 그때의 카메라 상태(위치·회전·확대)를 기억한다.
2. 다음 유니티 프레임이 늦어질 것 같으면(직전 프레임 시간 > 주사율 간격), 주사율 간격의 중간쯤에 그래픽 스레드에서:
   - 그 순간의 카메라 상태를 **곡 시간으로 계산**(맵 카메라 이벤트를 이징까지 따라감, 또는 직전 두 프레임으로 짧게 외삽),
   - camRT 를 차이만큼 옮기고 돌리고 확대해 백 버퍼에 그리고, **UI 는 마지막 것을 그대로 덮고**,
   - `Present`.
3. 가장자리에 빈 곳이 생기므로 camRT 를 화면보다 조금 크게(여백 5~10%) 그린다. 슈퍼샘플링·렌더 배율 코드와 같이 쓸 수 있다.

### 한계 (보이는 것)

- **카메라만 맞고 화면 속 물체는 멈춰 있다.** 행성 회전, 장식 이동, 타일 효과는 생성 프레임에서 안 움직인다. 카메라가 행성을 따라가는 이 게임 특성상 화면 전체가 부드러워 보이는 효과는 있겠지만, 행성 자체는 진짜 프레임에서만 움직인다.
  → 개선안: 행성만 따로 그려 생성 프레임에 정확한 위치로 얹기(행성 위치는 계산 가능). 일이 커서 2단계.
- 번쩍·필터 같은 화면 효과는 마지막 프레임 것이 그대로 남는다.
- 판정·입력은 바뀌지 않는다(게임 로직은 진짜 프레임에서만 돈다).

## 5. 시험 계획 (PC 에서, 작은 것부터)

1. **필요한 사람이 있는지부터**: 약한 PC(또는 개발 PC 에서 CPU 를 일부러 묶어 곡 중 50~70 FPS)로 무거운 맵을 돌려, 사람이 "끊겨 보인다"고 느끼는지.
2. **가장 싼 시험**: 생성 프레임 = 마지막 그림을 카메라 이동만큼 옮기기(회전·확대 없이). PresentMon 으로 화면에 나온 간격이 고르게 됐는지, 입력 지연(프레임 시작 → 화면)이 늘지 않았는지.
3. 눈으로 보기: 행성이 진짜 프레임에서만 움직이는 게 거슬리는지. 거슬리면 2단계(행성 따로) 또는 중단.

## 6. 정리

- 보간(A)은 지연 때문에 하지 않는다.
- 재투영(C)은 고사양 페이지가 아니라 **저사양 페이지의 실험 기능**이 맞다(느린 PC 를 위한 것). 기본 꺼짐.
- 바깥 도구(D)는 모드가 켜져 있는지 알아채 모니터·로그에 표시만 한다.

출처: FSR 3 프레임 생성 = DirectX 12·Vulkan 전용 (AMD GPUOpen FidelityFX SDK 문서, FSR 3.1 소개).
