# 11-07(토) 재개 계획: 모든 맵의 진짜 FPS 올리기

목표는 화면에 실제로 나가는 FPS다. 로직 FPS만 올리는 방법은 목표에서 뺀다. 이 문서의 후보는 전부 아직 시험 전이고, 상한은 계산값이다.

## 1. 지금 아는 것

- **막히는 곳:** 2560 효과 일부 끔 조건에서 메인 스레드 96%, 렌더 스레드 43%, 전체 CPU 60%, GPU 37%. 3440 165Hz + 효과 켬에서는 GPU 몫이 더 클 수 있어 아직 모른다.
- **DisplayPace 결론:** 사용자 실제 플레이에서 체감은 조금, 화면 흔들림은 더 심해짐. 진짜 FPS도 늘지 않는다. 기본 끔으로 두고 이 목표에서 뺀다. 흔들림의 원인이 그림 간격 불균일이라는 것은 코드 추정이다.
- **프레임 나눔 (추정):** DisplayPace 끔/켬의 메인 ms에서 계산. 그리기 비율은 120/FPS로 잡았다. 효과 조건이 정리되지 않은 값이다.

| 맵 | 프레임 전체 | 항상 드는 로직 | 그림 한 장마다 드는 몫 |
|---|---:|---:|---:|
| HELLO 2026 | 4.59ms | 약 1.1ms | 약 3.5ms |
| Exit | 3.31ms | 약 1.0ms | 약 2.3ms |
| Windflower | 4.59ms | 약 1.1ms | 약 3.5ms |

그림 한 장마다 드는 몫이 70~75%다. 여기에는 장식·트윈 갱신, 엔진 그리기 준비, presentation 대기가 함께 들어 있다.

## 2. 첫날: 측정 기준부터 고친다

지금까지 수치를 그대로 믿지 않는다. 11-05 10:37 뒤 시험은 필터·블룸·플래시·거울의 방·화면 흔들기가 꺼졌을 가능성이 높고, 대부분 2560 120Hz였다.

1. 시험 도구가 `EffectsOff`, `FiltersOff`, `NoFx`를 항상 명시하고, 판 시작 때 실제 값을 로그로 남기게 한다.
2. 기준 조건을 고정한다: 3440x1440 165Hz, 효과 켬, 플레이어용 빌드, 다른 모드 켬, 캐시 찬 상태. 조건이 다른 판은 합치지 않는다.
3. 이 조건에서 맵 6개(Exit, HELLO, DD, 7777, Windflower, Arche)의 메인·렌더·GPU·presentation 대기를 나눠 잰다.
4. JIT 인라인, 홀드 건너뛰기, 마스크 패치, GpuDeco를 이 조건에서 다시 잰다.

**3번 결과로 순서가 바뀐다.** GPU가 막히는 맵이 많으면 후보 C와 GPU 비용 줄이기가 먼저다.

## 3. 후보 (우선순위 순)

### A. presentation 대기 없애기 (가장 먼저)

- **근거:** 메인 스레드가 `TimeUpdate.WaitForLastPresentationAndUpdateTime` → `GfxDeviceD3D11::WaitForLastPresentationAndGetTimestamp`에서 기다린다. 11-05 표본 HELLO 17.0%(`data/profile/20261105-ss-hl-main.sym40.txt`), 11-03 표본에서 메인 대기 DD 15.7~48.7%, 7777 20%, Windflower 12%. 그 맵들의 대기가 모두 이 호출인지는 DD만 확인했다.
- **보조 증거:** `MaxQueuedFrames` 2→4 단판 HELLO 226 FPS(기준 193~208), Arche 변화 없음. ABBA 전이다.
- **상한:** HELLO 약 +20%. Exit·Arche는 대기가 2%대라 거의 없다.
- **시험 순서:**
  1. `MaxQueuedFrames` 3·4 ABBA.
  2. 대기 함수만 건너뛰는 엔진 패치. 플레이어 루프에서 단계를 통째로 빼면 시간 갱신까지 사라지므로 빼지 않는다.
  3. 대기가 줄어든 뒤 FPS와 PresentMon 지연을 함께 본다.
- **위험:** 곡 시계·판정에 쓰이는 시간 갱신과 같은 단계다. 시험 전에 사용자에게 먼저 보고한다. 메인이 앞서 달리면 화면 지연이 늘 수 있다.
- **미해결 모순:** 같은 재생에서 메인 CPU 시간은 96~100%로 나왔다(다른 맵, 1초 표본). 이 대기가 회전 대기인지 확인한다.

### B. 그리기 준비를 메인 밖으로: D3D12 재시험

- **근거:** 작업 스레드가 놀고 있고, D3D11은 split·native가 지원되지 않아 되돌려졌다(11-05 로그). legacy를 끄면 Arche가 101→74라 이 방향의 효과는 실제로 있다.
- **이전 실패:** 10월 D3D12는 곡 중 60~80ms 멈춤. 엔진이 6000.3.10에서 6000.3.25로 바뀌었고 모드 코드도 달라져 다시 볼 가치가 있다.
- **시험:** `-force-d3d12` + `split`·`native` 조합을 맵 6개 곡 전체로. 평균이 아니라 끊김부터 본다. 멈춤이 그대로면 바로 닫는다.
- **상한:** 그림 한 장 몫 중 엔진 그리기 준비만큼. 미측정.
- **빠른 확인 하나:** Vulkan은 맵 필터 셰이더가 포함돼 있는지 에셋만 먼저 본다. 없으면 시험하지 않는다.

### C. 게임 2개 번갈아 그리기 (사용자 아이디어, 유일하게 배수가 보이는 후보)

- **측정된 것:** 각자 전부 계산할 때 합계 1.56배(맵 1개, 2560 창 모드). 번갈아 그리기의 상한에 가깝다. 합성은 아직 없다.
- **구조:** 두 프로세스가 같은 입력과 곡 시계로 돌고, 반 프레임 어긋나게 그린다. B의 그림을 공유 텍스처로 A에 넘겨 A가 출력한다. 판정은 A만 하고 결과를 B로 보낸다.
- **1일 시제품으로 가를 것:**
  1. 3440 + 효과 켬에서 합계가 몇 배인가.
  2. 두 게임 그림이 얼마나 어긋나는가(같은 곡 시각 그림 비교).
  3. 공유 텍스처 비용과 출력 간격이 고른가.
- **닫는 기준:** 합계 1.3배 미만이거나, 그림 어긋남을 못 없애면 닫는다.
- **큰 걸림돌:** 메모리·VRAM 2배(이미지 큰 맵은 안 됨), 맵 열기 2번, 판정 동기화. 사용자 PC 6코어에서 3개는 어렵다(2개에서 이미 전체 CPU 90%).
- **장식 계산만 넘기는 방식은 뺀다.** 계산이 아니라 쓰기가 비용이라는 `DecoEngine` 기록이 있다.

### D. 메모리 쪽: 대용량 페이지

- **근거:** 메인 스레드는 포인터를 많이 따라간다(Transform 수만~14만). 모든 맵에 적용된다. 효과 크기를 뒷받침할 측정은 없다.
- **시험:** 재로그인 뒤 `SeLockMemoryPrivilege` 확인, 초기 단계에서 할당 함수를 가로채 Mono·Unity 힙을 대용량 페이지로. 먼저 TLB 미스 비중을 알 방법이 있으면 그것부터 본다.
- **한계:** 배포할 때 사용자마다 권한이 필요하다.

### E. 엔진 핫패스 묶음 패치

- **근거:** 프로파일이 평평해서 한 방은 없지만 마스크 패치가 Exit +11.8%를 냈다. 후보: 마스크 외 `memcpy_repmovs` 호출자, `ShaderPropertySheet::FindPropertyIndex`(렌더 스레드), `TransformChangeDispatch`, Mono 래퍼(표본 7~8%).
- **조건:** 각각 ABBA에서 +3% 이상만 남긴다. 게임 업데이트마다 재맞춤이 필요하고 바이트 대조로 스스로 꺼져야 한다.

### F. 장식 많은 맵 전용: 프리팹 줄이기, GpuDeco 맵별

- **프리팹:** 이미지 장식 하나가 활성 오브젝트 약 5개, 전체 9개다. 안 쓰는 자식을 줄이면 Transform 비용이 줄 수 있다. 미측정.
- **GpuDeco:** Arche 최악 10초 102→322가 지금까지 가장 큰 진짜 이득이다. 켜는 조건 4회차가 모두 기각된 상태라, 측정 기준을 바꾼 뒤 다시 본다.
- 모든 맵용은 아니지만 Arche를 풀 유일한 길이다.

### G. 사용자 PC 설정 (모드로 배포 안 됨)

NVIDIA 전원 "최대 성능", Threaded Optimization, HAGS 끔. 사용자가 직접 바꿔 비교한다. 메인 스레드가 막는 맵은 효과가 작을 것으로 예상하지만 재본 적이 없다.

## 4. 다시 하지 않을 것

DisplayPace를 진짜 FPS로 세기, 위치 직접 쓰기, 선행 메모리 읽기, 코어 고정, 코어 안 재우기, DXVK, 계층 나누기, deco-v2 슬라이스, D3D11에서 split·native(지원 안 됨), 부팅 옵션 묶음.

## 5. 정직한 기대치

"모든 맵 2배"로 가는 확인된 길은 아직 없다. 단일 후보 상한은 A 약 +20%, C 약 1.5배다. 전부 성공해도 합이 곱으로 쌓인다는 보장이 없다. 첫날 측정에서 3440 효과 켬의 병목이 달라지면 이 순서도 바뀐다.

## 6. 토요일 전에 필요한 것

- **코덱스:** 주간 93%, 리셋은 11-09(월) 11:50. 토·일은 쓸 수 있는 양이 적어 시험 자동화와 측정 위주로 간다.
- **PresentMon:** 관리자 에이전트를 사용자가 켜야 지연을 잰다.
- **재로그인:** 대용량 페이지 권한 적용에 필요하다.
- **설치 상태:** 플레이어용 빌드 + `DisplayPace` 켬인 채로 있다. 평소 플레이용으로 되돌릴지 사용자 결정이 필요하다.
- **설정 확인:** 효과 끄기 목록(필터·블룸·플래시·거울의 방·화면 흔들기)이 비워진 경위를 사용자에게 확인한다.
