- **Windflower:** turbo 이득이 판에 따라 0~4%다.
- **제품 반영 전 남은 일:** 렌더러 플래그를 끌 때 되돌리기, 모든 렌더러 훑기를 곡 시작이 아니라 맵 불러오기에서 하기, 일시정지 때 PausePlanets 카메라 다시 켜기.

## 6-3. GPU 병목 조사 (11-08 아침)

GPU에서 막히는 맵(HELLO·7777·DD·Windflower)을 나눠 봤다.

- **효과 전체 끄기(노이펙, 장식 포함):** GPU 프레임이 HELLO 5.33→1.00, 7777 5.83→0.68, Windflower 5.17→0.52ms로 떨어졌다.
- **효과 종류별 끄기:** 편집기 구간 찾아가기와 게임 화면 재생 둘 다에서 적용되지 않았다(필터 목록이 그대로). 결과를 버렸다.
- **한 판 안에서 묶음 숨기기(`hidegroup`):** HELLO 46~62초에 장식을 숨기면 5.57→1.11ms, 타일(`scrFloor`)을 숨기면 5.30→1.28ms다.
- **덧칠 조사(`gpucensus`, HELLO 50초):** 메인 카메라 덧칠 합계가 화면 198.6장이다. 그중 189.3장이 `Sprites/Tile` 셰이더이고, 대부분이 같은 원 그림(`pt2_circle1.png`, 3072x3072, 밉맵 없음) 장식 약 300개가 각각 화면 전체를 칠한 것이다.
- **시도 1, 알파 0 픽셀 버리기:** `Sprites/Tile`을 복제하고 알파가 정확히 0이면 버리는 셰이더를 만들었다. 정점 4개·픽셀 4개 변형 모두 버리기 두 줄을 빼면 원본과 명령어가 같다(역어셈블 대조). 섞기 One/OneMinusSrcAlpha·스텐실 미사용이라 결과는 같다.
  - ABBA 결과: HELLO 165.4→164.3, 7777 169.6→169.2로 이득이 없어 기각하고 되돌렸다.
  - 해석: 섞기(ROP)가 병목이 아니다.
- **결론:** 비용은 큰 텍스처(밉맵 없음)를 화면 전체에 300번 읽고 칠하는 셰이딩·텍스처 쪽이다. 바이트까지 같은 결과를 유지하는 방법으로는 줄일 수 없다. 줄이려면 밉맵 생성이나 큰 이미지 해상도 낮추기(이미 VRAM용으로 있는 이미지 줄이기와 같은 종류)처럼 픽셀이 바뀌는 방법뿐이고, 사용자 결정이 필요하다.
- **7777:** 배경 카메라 필터 10개(`AAA_SuperComputer` 0.97ms 등)와 메인 카메라 3.8ms다. 같은 이유로 무손실 여지가 작다.

## 6-4. 화면 크기 맞추기·스텐실 거르기 (11-08 낮, 기각)

- **장식별 텍스처 대 화면 크기(`texdensity` 진단):** 화면을 덮는 큰 장식은 대부분 비율 0.03~0.6이다. 즉 텍스처가 5~30배 **확대**되어 그려진다(HELLO 52초 원 장식 150개 0.06~0.22, 60초 빛 장식 106개 0.25~0.76, 7777도 비슷).
  - 축소가 아니므로 텍스처 캐시 문제가 아니고, 해상도를 맞춰 줄여도 GPU 이득이 없다.
  - 비용은 칠하는 픽셀 수 자체다(HELLO 52초 약 7.4억 픽셀/프레임).
- **원 그림의 실제 투명 면적:** `pt2_circle1.png`는 알파>0 픽셀이 3.5%, 64픽셀 블록 덮개 25.4%다. `pt2_lights.png`는 27%다.
- **스텐실 거르기:**
  - 방법: 장식 직전에 알파가 있는 블록에만 스텐실 비트를 세우고, 장식은 그 비트에서만 그린 뒤 지운다. 장식 셰이더는 원본과 명령어가 같은 복제본이다(8개 프로그램 일치).
  - 결과(ABBA, HELLO 50~62초, 측정용으로 마스크 안전장치 무시): 64격자는 FPS 179 → 136, GPU 5.18 → 6.76ms. 256격자는 FPS 179 → 123, GPU 5.13 → 7.46ms.
  - 원인: 확대된 그림에서 덮개 블록이 화면 수백 픽셀이 되어 거의 다 덮였다. 촘촘하게 하면 표시·지우기 메시 비용이 이득보다 컸다. 기각하고 되돌렸다.
- **결론:** 바이트까지 같은 결과로 GPU 칠하기를 줄이는 방법(섞기 생략, 스텐실 거르기, 해상도 맞추기)은 모두 이득이 없거나 손해였다. 남은 방법은 장식 메시를 그림 모양에 맞게 줄이는 것뿐이다. 이 방법은 예전에 최대 3/255 픽셀 차이로 기각했다.

## 6-5. 스텐실 동작 확인 (`stencilprobe`)

화면 버퍼는 `D32_SFloat_S8_UInt`라 스텐실이 있다. `Sprites/Tile` 장식 2,247개를 전부 스텐실로 걸러도(덮개 없음) HELLO GPU가 약 1ms만 줄었다. 장식을 숨기면 4ms 넘게 준다. 거른 픽셀도 래스터화 비용은 남으므로, 픽셀 단위 거르기(섞기 생략, 스텐실)로는 한계가 분명하다. 줄이려면 그리는 도형 자체를 작게 해야 한다(그림 모양 메시, 예전에 최대 3/255 차이로 기각).

## 6-2. 되돌린 것

- **필터 직통 처리의 승인 확인:** Gemini v14가 없앴던 것을 되돌렸다(`claude/v14-product`). 원래는 시험 명령(`filteridentity on` → `approve`)으로 필터 출력과 직통 복사를 픽셀까지 대조해 통과한 필터·화면 조건에서만 건너뛴다. 새로 추가된 후보 5종(Blur_Radial, Blur_Radial_Fast, Blur_Movie, Color_Noise, EXTRA_Rotation)은 대조된 적이 없다. 위 측정들은 기준판과 묶음판에 같은 코드가 들어 있어 비교에는 영향이 없다.
