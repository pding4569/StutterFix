# 상식 밖 최적화 설계 (2026-11-07)

모두 아직 만들지 않았다. 상한은 v14 측정(3440x1440 165Hz, 효과 켬, 설정마다 한 판)에서 계산했다. 무손실은 "같은 입력이면 픽셀이 바이트까지 같다"는 뜻으로만 쓴다.

## 지금 프레임이 어디에 쓰이나 (v14)

| 맵 | 막히는 곳 | 프레임 | 큰 덩어리 |
|---|---|---:|---|
| Exit (CPU 묶음) | 메인 스레드 | 3.50ms | Update 1.31, 그리기 마무리 0.93, LateUpdate 0.53, 오디오 0.19, UI 0.14 |
| Windflower | GPU | 6.29ms | 그리기 마무리 2.57 중 GPU 대기 1.48. 메인 카메라 전체 화면 필터 5개 + 깊이 텍스처, 카메라 4개 |
| Arche (GpuDeco) | 메인+GPU | 4.70ms | 그리기 마무리 1.95 중 GPU 대기 1.10, Update 1.17, LateUpdate 0.59 |

Exit의 Update 1.31ms는 호출 수가 아니다. Update를 가진 활성 스크립트는 약 430개뿐이다. 무거운 몇 개(효과 실행, DOTween, 장식 관리자, 다른 모드 오버레이)가 시간을 쓴다.

## 1. 쌍둥이 게임 실제 프레임 끼워넣기

**한 줄:** 게임을 두 개 띄운다. B가 반 프레임 늦은 시각을 진짜로 렌더하고, A의 화면 출력 사이에 그 그림을 끼워 넣는다. 보간이 아니라 진짜 프레임이다.

- **근거:** 게임 2개 동시 실행에서 각 78%, 합계 1.56배(2022 맵, 2560 창 모드). 메인 스레드가 막히는 맵이면 전부 적용된다.
- **상한:** Exit 286 → 약 445 FPS. GPU에서 막히는 Windflower는 GPU를 나눠 쓰므로 이득이 없다.
- **구조:**
  1. A(주인)가 입력·판정·소리를 맡고, 매 프레임 {곡 시계 기준점, 입력 이벤트, 판정 결과, 행성 상태 해시}를 공유 메모리에 쓴다.
  2. B는 소리를 끄고 같은 맵을 연다. B의 곡 시계를 A 기준점 + 반 프레임으로 바꾸고, 판정은 A의 결과를 그대로 재생한다(스스로 판정하지 않음).
  3. B의 화면 출력 연결(sfnative)이 백 버퍼를 공유 D3D11 텍스처(NT 핸들, keyed mutex)로 복사하고 출력은 하지 않는다.
  4. A의 출력 연결이 자기 프레임과 B의 프레임을 번갈아 낸다. 프레임 생성 연구에서 만든 "추가 출력" 경로를 그대로 쓴다.
- **어려운 곳:**
  - 카메라 부드럽게 따라가기가 프레임 시간(dt)에 따라 궤적이 조금 달라질 수 있다. A와 B 그림이 번갈아 흔들리는지 재야 한다.
  - DOTween처럼 dt를 누적하는 애니메이션도 같은 문제가 있다. 곡 시각으로 구운 GpuDeco·DecoAnim은 괜찮다.
  - 메모리·VRAM이 2배다. Arche는 VRAM이 빠듯하다.
- **첫 시제품:** B만 그리고 A는 B의 그림만 내보내서 공유 텍스처 경로를 확인한다. 그다음 번갈아 내보내며 실제 출력 FPS와 A/B 그림 차이를 잰다.

## 2. GPU에서 막히는 맵: 바이트까지 같은 GPU 절감

먼저 `gpuprobe`로 카메라·필터별 GPU 시간을 잰다(진행 중). 어디에 쓰는지 모르고 고르지 않는다.

- **2a. 불투명 텍셀 깊이 선행 패스 (GpuDeco):**
  - 보통 블렌드에서 알파가 정확히 1인 텍셀은 결과가 아래와 상관없이 그 색이다. 그러니 그 아래 장식의 픽셀은 그리지 않아도 결과가 같다.
  - 앞에서 뒤로 알파 1 텍셀만 깊이를 쓰고, 본 패스는 깊이 검사로 가려진 픽셀을 GPU가 일찍 버리게 한다.
  - 겹침이 많은 Arche에 유리하다.
  - 걸림돌: 사이에 낀 Unity 렌더러가 같은 깊이 버퍼에 걸리지 않게 해야 한다.
- **2b. 블렌드 장식의 부분 화면 복사:**
  - BlendModes 장식은 통합 화면 복사(`unifiedGrabEnabled`)가 꺼져 있으면, 장식마다 3440x1440 전체(약 20MB)를 복사할 수 있다.
  - 장식이 실제로 읽는 화면 영역만 복사해도, 셰이더가 읽는 픽셀은 같다.
  - 실제 복사 횟수부터 확인한다.
- **2c. 필터 사슬 합치기:**
  - 픽셀 하나씩만 보는 필터(밝기·대비·채도·색·테두리 가림)를 한 패스로 합친다.
  - 패스 사이 8비트 반올림을 셰이더 안에서 똑같이 흉내 내야 바이트가 같다. 이웃 픽셀을 읽는 흐림 필터는 합치지 않는다.
- **2d. GpuDeco 픽셀 셰이더를 원래 스프라이트 셰이더만큼 싸게:**
  - v14에서 Windflower·Arche의 GPU 대기가 늘었다.
  - 직접 텍스처 52장 사이를 픽셀마다 탐색하는 경로를 줄인다. 큰 장식은 원래 렌더러에 남기는 것도 방법이다.
  - 먼저 v13과 v14 GPU 시간을 비교해 늘어난 곳을 찾는다.

## 3. 범용 같은 값 쓰기 제거

- **한 줄:** 게임이 엔진에 쓰는 값 가운데 직전과 같은 값을 엔진에 닿기 전에 버린다.
- **근거:** 지금까지의 큰 이득이 대부분 이런 것이었다(같은 글자, 같은 그림자 색, 같은 홀드, 같은 회전). 하나하나 손으로 찾았다.
- **방법:**
  - 자주 불리는 엔진 쓰기 함수(위치·회전·크기·색·재질 값)를 전부 감싸고, 객체별 마지막 값과 같으면 건너뛴다.
  - 같은 대상을 엔진 쪽(애니메이터·물리·UI 배치)이 바꾸는 경우는 감시 대상에서 뺀다. FloorFix 실패(다른 코드가 그사이 값을 바꿈)를 되풀이하지 않으려면 쓰기 경로를 빠짐없이 덮어야 한다.
- **첫 단계:** 맵마다 "같은 값 쓰기" 비율을 센다. 비율이 낮으면 접는다.

## 4. GpuFloor: 타일도 GPU로

- **한 줄:** GpuDeco가 장식에서 한 일을 타일에 한다.
- **근거:** Exit에서 보이는 렌더러 약 420개 중 타일 MeshRenderer가 234개다. 타일마다 재질이 따로라 묶이지 않는다. 타일 이동·색·LateUpdate가 Update와 LateUpdate에 있다.
- **상한:** 그리기 마무리 0.93ms와 LateUpdate 일부. 측정 전이다.
- **걸림돌:** 예전 타일 굽기 지원 0/15,001의 원인부터 다시 봐야 한다.

## 5. 엔진 자신의 "바뀜" 표시로 카메라 하나를 통째로 건너뛰기

- **방법:** 배경 카메라처럼 매 프레임 같은 그림을 그리는 카메라가 있다. 그 카메라가 보는 렌더러의 변환·재질·켜짐이 하나도 안 바뀌었다는 것을 엔진 내부 표시(TransformChangeDispatch, PDB로 위치 확인)로 증명하면, 지난 결과를 그대로 쓴다.
- **차이:** 증명이 없으면 쓰지 않으므로 BgCamCache(손실로 버림)와 다르다.

## 6. D3D12 + native 그래픽 작업

그리기 준비를 작업 스레드로 옮긴다. 10월의 곡 중 멈춤이 엔진 6000.3.25에서도 남아 있는지 끊김부터 본다.

## 7. Mono에 LLVM AOT 붙이기 (먼 길)

게임의 Mono에는 AOT 로더와 컴파일러가 들어 있다(`mono_main`, `--aot`, `mono_aot_register_module`). LLVM은 없다. Unity의 Mono 소스를 같은 버전으로 LLVM과 함께 빌드해 Assembly-CSharp·StutterFix를 미리 컴파일하는 방법이다. 관리 코드가 빨라지는 만큼 이득이고, 맵마다 5~15%로 추정한다. 런타임 GUID가 맞아야 해서 버전 맞추기가 가장 큰 일이다. LLVM 없는 AOT는 지금 JIT과 같은 코드를 만들어 이득이 없다.

## 8. 가장 큰 그림: 자체 렌더러

Unity는 로직과 UI만 돌리고, 게임 세계(타일·장식·행성·입자)는 모드의 네이티브 렌더러가 다른 스레드에서 그린다. 그리기 마무리와 LateUpdate의 대부분이 메인에서 빠진다. GpuDeco가 1단계, GpuFloor가 2단계다. 필터는 Unity 재질을 CommandBuffer로 그대로 쓴다.

## 순서

1. `gpuprobe`로 Windflower·Arche GPU 시간을 나눠 v14 퇴보 원인을 찾고, GpuDeco GPU 비용을 줄인다(2d, 2a).
2. 쌍둥이 게임 시제품 1단계(B 그림만 A로 내보내기).
3. 같은 값 쓰기 비율 세기(3).
