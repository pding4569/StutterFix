# ADOFAI 렌더러 (통합 장식 렌더러) 설계

2026-11-08 사용자 결정: 단계별로 나누지 않고 하나의 렌더러로 한 번에 만든다. 기반은 GpuDeco(이미 장식 표, GPU 위치 계산, 원래 그리기 순서를 지키는 구간 그리기가 있음)다.

## 근거 (3440x1440 165Hz, 효과 켬)

- **CPU 쪽:** 확정 묶음 뒤 Exit 외 맵은 GPU를 기다린다. HELLO 그리기 단계 1.06 → 2.29ms다.
- **GPU 쪽:** HELLO 52초 메인 카메라 덧칠이 화면 198.6장이고, 그중 189.3장이 `Sprites/Tile` 장식이다. 확대 배율 0.06~0.22(5~16배 확대)인 원 그림 150개가 화면 전체를 칠한다.
- **무손실 방법 결과:** 섞기 생략 0%, 스텐실 -1ms(덮개 비용 포함 시 손해), 그림 모양 도형 손해(180.7 → 158). 클립 거리 전부 자름은 -2.2ms다.
- **스크린 공간 LOD 상한(측정용, 순서 틀림):** 확대 4배 이상 489개를 1/4 해상도로 그리면 FPS +12~19%다.
- **GpuDeco 현재:** HELLO에서 맡는 장식 1,014/2,531개이고, 오히려 느리다(181 → 151 FPS, GPU 5.20 → 6.05ms). 셰이더가 텍스처 52장을 픽셀마다 분기로 찾는다.
- **HELLO 거부 상위:** 카메라 따라 움직이는 화면 투영·시차 화면 고정 834, 마스크 384/231, 이미지 아닌 장식 105.

## 한 번에 넣는 네 부분

### A. 셰이더 비용을 원래 스프라이트 이하로
- **텍스처를 전부 배열로:** 모든 장식 텍스처를 크기 등급별 `Texture2DArray`에 넣는다(비압축은 임의 크기 허용, 큰 것은 등급별 배열).
- **직접 텍스처 제거:** 직접 텍스처 48장 경로를 없앤다.
- **단일 샘플:** 쿼드마다 배열 번호·층을 `nointerpolation`으로 넘겨 픽셀 셰이더는 분기 없이 `SampleLevel` 한 번만 한다.
- **목표:** HELLO GpuDeco 켬 GPU ≤ 끔 GPU다.

### B. 스크린 공간 LOD (화면 확대 배율 기반 저해상도)
- **배율 계산:** 매 프레임 구간마다 항목의 화면 확대 배율(화면 픽셀/텍스처 픽셀)의 최솟값을 GPU 계산 결과에서 얻는다(위치 계산 compute에 추가, 비동기 읽기 1프레임 늦음 허용).
- **등급:** 최솟값이 4 이상이면 1/4, 2 이상이면 1/2 해상도 등급이다.
- **저해상도 그리기:** 등급 구간은 본 카메라 그리기 전(CameraEvent.BeforeForwardAlpha) CommandBuffer로 구간 메시를 등급 RT에 그린다.
- **제자리 합치기:** 구간 렌더러는 같은 재질(정렬 동점 순서 유지)에 MaterialPropertyBlock으로 합치기 모드를 켜고, 메시를 화면 사각형으로 바꿔 등급 RT를 미리 곱한 알파로 합친다.
- **화질 기준:** 같은 프레임 비교(framecmp)에서 3/255 넘는 픽셀 비율과 최대 차이를 기록하고 등급 기준을 조정한다.

### C. 맡는 범위 넓히기
- **시차·화면 고정·카메라 따라 움직이는 장식:** 매 프레임 카메라 위치·크기·회전을 상수로 넘겨 GPU에서 같은 식(`scrParallax.SetTrans`, 화면 고정 투영)으로 계산한다. 게임 코드 식은 디컴파일로 맞춘다.
- **마스크 장식:** 마스크 묶음 단위로 스텐실을 쓴다. 이번 범위에서 못 하면 장벽으로 남긴다.
- **글자·파티클·오브젝트:** 장벽으로 남긴다(CPU 그대로). 구간 사이를 끊을 뿐이다.

### D. 검증과 측정
- **성능:** 맵 6개(Exit, HELLO, DD, 7777, Windflower, Arche)를 판마다 게임을 새로 켜는 ABBA로 잰다.
- **화질:** HELLO 52·54초, Arche, Windflower에서 같은 프레임 비교를 한다.
- **기본값:** 끔으로 둔다. 사용자 결정 뒤 켠다.

## 작업 트리

브랜치는 `claude/adofai-renderer`다(`claude/v14-product`에서 갈라짐). 측정 진단(`texdensity`, `lodprobe`, `framecmp`)은 그대로 쓴다.

| 시험 | FPS (판별) | 판단 |
|---|---|---|

| A. DIRECT_FEW(구간이 쓰는 직접 텍스처만 8칸) | 141.5/142.2/140.9 → 147.7/147.3/148.0 (+4.4%) | 채택 후보. 275구간 중 234구간이 씀 |
| B. 구간 LOD(q=1.5, 화면 전체 합치기) | LOD끔 147.2/147.1/148.0 → 138.8/139.3/137.5 | 손해. 아래 이유 |
| GpuDeco 끔(원래 그리기) | 170.9/170.5/171.2 | GpuDeco는 HELLO에서 아직 -14% |
| 화질 (LOD 켬 대 끔, 같은 프레임) | 52초 최대 22/255 PSNR 51dB, 54초 최대 22/255 PSNR 49.7dB | 눈으로는 같음 |

- **LOD가 손해인 이유:** HELLO의 무거운 원 그림 `pt2_circle1` 150개(화면 150장 분량)는 그리기 순서 141종에 흩어져 있고, 그 순서 사이에 다른 렌더러 42개가 끼어 있다. 순서를 지키려면 구간마다 화면 전체를 한 번씩 합쳐야 해서, 아낀 덧칠만큼 다시 칠한다. 측정용 lodprobe의 +12~19%는 순서를 무시하고 한 번에 합친 상한이다.
- **도형 가설 기각:** 장식 스프라이트는 모두 정점 4개 사각형(도형/사각형 넓이 1.000)이라 GpuDeco와 원래 그리기의 도형이 같다.
- **그림 모양 도형(128칸):** FPS는 168.2 → 145~146으로 손해다. 다만 GPU 대기(FinishFrameRendering)는 2.46 → 1.43ms로 줄고 CPU(Update 등)가 늘었다. GPU는 가벼워졌고 정점 수 때문에 CPU 병목이 된 것으로 본다.
- **gpuprobe의 frame 값:** CPU가 병목이면 GPU 쉬는 시간까지 들어가므로 순수 GPU 바쁨 시간이 아니다.

## 다른 방법: 원래 렌더러 묶음 LOD (`RunLod`, 측정용 `runlod`)

### 병목 다시 찾기 (HELLO 46~58초, 판마다 새로 켬)
- **해상도 절반:** 176.7 → 225.9 FPS(+28%), present 대기 1.23 → 0ms. GPU 병목이 맞다. FrameTiming의 GPU 값(1.5ms)은 틀렸다.
- **원 그림 숨기기:** `pt2_circle1` 151개를 숨기면 177.4 → 228.6 FPS. 흐린 원·먼지 그림은 변화 없음. 주범은 원 그림이다.
- **도형을 깎아도 안 됐던 이유:** 원이 10배 넘게 확대돼 화면에 보이는 부분이 고리의 불투명한 띠 안이다.
- **GpuDeco LOD가 실패한 이유:** 원은 월드 크기가 25를 넘어 GpuDeco가 맡지 않는다("oversized-world-quad").
- **그리기 순서상의 묶음(`runprobe`):** 4배 넘게 확대된 장식 163~177개가 연속 묶음 11~14개로 몰려 있다(길이 56, 52, 34…).

### 방법
1. **묶음 찾기:** 본 카메라 컬링 직전(Camera.onPreCull)에 보이는 후보 장식을 유니티 투명 정렬(큐·정렬층·순서·먼 것부터·셰이더 ID·재질 ID)로 줄 세운다. 그리고 연속으로 붙은 "4배 넘게 확대된 이미지 장식" 묶음을 찾는다.
2. **장벽:** 두 후보 사이 키 범위에 보이는 다른 렌더러가 있으면 묶음을 끊는다. 장벽은 정렬 키로 미리 정리해 둔다.
3. **이득 조건:** 아낀 화면 층(넓이 합×15/16 - 합칠 사각형 넓이)이 1보다 클 때만 묶는다.
4. **저해상도 그리기:** 묶음 장식은 층 31로 옮겨 본 카메라에서 빼고, 투명 그리기 직전 CommandBuffer.DrawRenderer로 1/4 해상도 그림에 원래 순서대로 그린다.
5. **제자리 합치기:** 묶음 첫 장식의 정렬층·순서·거리를 가진 사각형 하나가, 묶음이 덮는 화면 범위만 미리 곱한 알파로 합친다(`StutterFix/RunLodComposite`).
6. **보임 추적:** 후보와 장벽의 보임은 OnBecameVisible/Invisible 알림으로 추적한다. 매 프레임 비용은 0.1~0.7ms다.
7. **쉬는 모드:** 아낀 화면 층의 이동 평균이 작으면 30프레임에 한 번만 살펴본다. 켤 때는 이동 평균이 3 이상이고 쉬는 동안의 GPU 대기(present wait)가 0.3ms 이상이어야 한다(GPU 병목일 때만).
8. **장식이 많은 맵:** 후보가 8,000개를 넘으면 끈다(Arche 28,828개).

### 제품 전 남은 일
- **정리:** Main.Unload 정리, 맵을 바꿀 때 다시 모으기가 필요하다.
- **시작 비용:** 처음 모을 때 FindObjectsByType로 렌더러 4~13만 개를 훑는 비용(곡 시작 때 한 번)을 재야 한다. 컴포넌트를 붙이는 비용도 있다.
- **1프레임 늦음:** 보임 알림은 1프레임 늦다. 새로 보인 장벽이 묶음 사이에 끼면 그 프레임만 순서가 틀릴 수 있다.
- **층 31:** 장식 GameObject의 층을 31로 바꾼다. 충돌체가 있는 장식은 후보에서 뺐다.
- **동점 장식:** 정렬 키가 같은 장식끼리의 순서는 셰이더 ID와 재질 ID 규칙을 따랐다.
- **현재 상태:** AUTOTEST 빌드에만 있고 기본값은 꺼짐이다.
