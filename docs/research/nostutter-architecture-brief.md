# StutterFix GPU 장식: "끊김 0" 구조 연구 요청 (Claude·Codex·Gemini 공통 문서)

## 0. 요구 (협상 불가)
얼불춤(A Dance of Fire and Ice, Unity 6000.3 Mono, D3D11, Windows) 모드 StutterFix 의 **GPU 장식**은 장식 2만 8천 개짜리 맵(Arche)에서 FPS 를 올린다.
그러나 **켜고 끄는 순간의 한 프레임 멈춤(수십~수백 ms)이 하나라도 있으면 상용화할 수 없다.** 목표: 모드가 만드는 프레임 멈춤 **0** (최대 프레임 증가 8ms 미만).
대상 순간: (1) 곡 시작 (2) **곡 중간 시작(에디터 재생·체크포인트)** (3) 다시 하기 (4) 죽음 (5) 완주 (6) 맵 처음 열기.

## 1. 현재 구조 (한 줄 요약)
게임은 장식(`scrVisualDecoration`)마다 GameObject+SpriteRenderer 를 두고, 효과(`ffxMoveDecorationsPlus` 등)가 장식마다 DOTween 으로 위치·회전·크기·색·불투명도를 움직인다.
모드는 장식 28,523개를 **GPU 가 소유**하게 한다: 장식마다 16채널(위치XY·오프셋·회전·크기XY·색RGBA·불투명도·시차 4)을 `LiveChannel{start,change,end,sourceIndex}` 로 들고, 컴퓨트 커널(`EvaluateCollapse`)이 프레임마다 값을 계산해 큰 정점 버퍼에 쓰고,
순서가 이어지는 장식 묶음(약 537개 "구간")을 프록시 MeshRenderer 로 한 번에 그린다. 소유한 장식의 원래 SpriteRenderer 는 꺼 둔다(`forceRenderingOff=true`, `enabled=false`).
효과가 시작되면 모드 후크가 그 장식의 "시계(source: 이징·길이·진행)"를 GPU 에 올린다(CPU DOTween 은 만들지 않음).
비소유 장식(반복 타일 110개 등)은 원래 렌더러가 그리며 "정렬 장벽"이 된다. 곡 중 깊이가 바뀌면 구간을 독립 렌더러로 바꾸는 동적 처리가 있다.

## 2. 멈춤의 정체 (Arche 3440x1440, 측정)
켜기(`StartPlayer`): 약 190ms(게임 시작 150ms) = 소유분류 10 + 외부꺼짐읽기 5 + **초기상태캡처 44**(장식 28.5k개 × 16값 읽기, SetMasterSlotStatic) + **이미지캡처·더티올리기 55**(이미지 장식 약 5천 개 `RefreshGpuImageGeometry`) + **원본렌더러끄기 16**(28.5k × forceRenderingOff/enabled) + 첫디스패치 15 + 알파갱신 15 + 통합 켜기 15~50.
끄기(`StopGpuLive`): 다시 하기·완주 때 41~97ms = 장식마다 GPU 현재값 16채널 평가 → CPU 객체에 되돌려 쓰기(BakeWrite) + 원본 렌더러 복원 + 진행 중 효과(Rec) 다시 CPU 로 돌려주기.
맵 처음 열기: 준비 5.9초 + 관리 힙 정리 0.8초. 다시 하기 준비 0.23초(재사용), 쓰레기 23MB.
이미 한 것: 켜기를 "시작 키 누르기 전(Start 상태)" 화면으로 옮김(게임 화면 경로), 죽음·완주 때 되돌리기를 다음 전환으로 미룸, 네이티브 DOTween 이어받기(중간 시작 때 게임이 만든 트윈을 GPU 가 넘겨받음).
남은 것: **에디터/중간 시작의 190ms**(게임이 시작 지점까지 효과를 한 프레임에 되감아 적용한 뒤에야 현재 상태를 읽어 넘겨받을 수 있음), 다시 하기를 누르는 순간 62ms.

## 3. 시도했고 안 된 것 (반복하지 말 것)
- 따라잡기(되감기) 60프레임 동안 DecoAnim 을 허용: 원본 Goto 의미와 어긋나 GPU 장식이 시작되지 않고 화면이 44.5% 달랐음.
- 따라잡는 중 바로 켜기: 이어받기 거절 + 원본 코드 경로로 새 효과가 가서 GPU 가 꺼짐(FPS 198, 켜기 대기하면 321). → 되감기 4프레임만 구분하는 시험 중.
- 활성화 분할(A: 읽기 전용 미리 준비 + 서명 검사, B: 구간 단위 전환; Codex 구현, 기본 꺼짐): 움직이는 애니메이션이 있는 시점(중간 시작)에는 못 쓴다.
- 장식 "굽기(bake)": 곡 시각 기반으로 표에서 값을 계산하는 방식은 지원률 약 82%, 곡 시계 흔들림 오차 → 소유 넘기기 방식으로 정착. 타일 굽기는 0%.

## 4. 사용자(나로컴)가 제안한 방향 (이걸 진지하게 검토해 달라)
"맵을 열 때 전부 로딩해서 표에 만들어 두고, 시작/중간 시작/다시 하기에서는 표에서 가져오기만 하면 즉시 되어야 한다."
이를 구체화한 후보:
- **A. 지속 소유(Persistent ownership):** GPU 가 맵을 연 순간부터 나갈 때까지 장식을 소유한다. 다시 하기 = 초기 채널 배열을 한 번 업로드(미리 만들어 둔 배열 복사), 죽음·완주 = 아무것도 안 함. CPU 객체 복원은 맵을 떠날 때만(전환 중).
  게임 코드(히트박스, 텍스트 장식, 편집기 선택, 다른 모드)가 장식 CPU 상태를 읽는 곳과의 호환이 관건.
- **B. 표 기반 임의 시점 상태(Table-driven state at time T):** 장식 이벤트(`LevelEvent` 타임라인)를 맵 열 때 GPU 버퍼(구간별 키프레임/세그먼트)로 올려 두고, 컴퓨트가 곡 시각 T 에서 16채널 값을 직접 계산한다.
  그러면 중간 시작도 "T 만 정하면" 되고 게임의 되감기·네이티브 트윈 이어받기·초기상태 읽기가 필요 없다. 지원되지 않는 효과 종류는 하이브리드(해당 장식만 CPU 처리).
- **C. O(1) 전환:** 원본 28.5k 렌더러를 하나씩 끄는 16ms 대신, 한 번의 연산으로 원본을 숨기는 방법(카메라 culling mask 의 레이어 전환, 장식 루트 비활성화 등)이 가능한지.
- **D. CPU 작업 자체를 빠르게:** 초기상태 읽기·이미지 기하 새로고침을 작업 스레드(관리 필드만 읽으므로 가능?)나 변경 추적으로 줄이기.

## 5. 지켜야 할 것
- 화면은 원래 게임과 같아야 한다(같은 판 GPU 켠/끈 비교에서 8 넘게 다른 픽셀 0.59% 이하가 기준).
- 실패하면 원본으로 안전하게 돌아가는 길 유지. 윈도우 전용 허용. Unity 6000.3(Mono, netstandard2.1), D3D11, 컴퓨트 셰이더 가능.
- 게임 DLL·디컴파일 코드를 저장소에 넣지 않는다.

## 6. 연구 질문
1. A·B·C·D 각각이 **가능한가** (게임 코드 근거, 예상 멈춤, 위험). 가장 작은 변경으로 "끊김 0"에 닿는 조합은?
2. B 에서 지원되지 않는 효과(약 18%)는 어떤 종류이고 하이브리드로 정확한가? 곡 시각 T 의 정의(`songposition_minusi`, pitch, dspTime, 되감기)는?
3. A 에서 게임 코드가 장식 CPU 상태를 읽는 곳 전수 목록과 대응.
4. 가장 위험한 가정과, 게임 없이 오프라인으로 검증할 수 있는 부분(마이크로벤치, 시뮬레이터).
5. 구현 순서와 단계별 시험 방법.
