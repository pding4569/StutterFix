# Codex 임무 bake-8: 굽기 표로 장식을 실제로 구동하는 "채택(adopt)" 모드 1단계 (기본 꺼짐, 개발 전용)

## 배경 (사용자 결정: "최대한 최적화하는 방향")
굽기 그림자 모드는 실측으로 지원 81.95%(23,631/28,835), 시작 위상 98.7% ±1프레임, 시간 오차 6~13ms(120Hz 표시 프레임 8.3ms 안팎, 원본 자체 곡 시계 지터 수준), `evalActive` 초반 p99 0.0006ms/무거운 구간 중앙 0.91ms 를 보였다(`docs/optimization-36.md` 끝). 사용자가 **표시 프레임(ms) 기준**을 받아들였다 → 이제 굽기 표로 장식을 **실제로 구동**해 원본의 기록(`Rec`) 생성·교체·갱신 비용을 없애본다. 기대: Arche 258~278초 장식 CPU 약 5.5ms 중 2~3ms 절감(약 95 → 최대 ~125 FPS 추정, 측정 전). GPU 바닥(draw 약 1,840개, 5.7ms)은 별개.

## 설계 요구
1. `decobake adopt on|off|state`(개발 전용 `#if DEV || AUTOTEST`, Player 제외, 기본 꺼짐, `Main.Unload`/`off` 에서 반드시 되돌림). `ready` 상태(표 준비 완료, 같은 세대)에서만 켠다.
2. **소유 장식 집합 O** = 굽기 지원 장식(지원 23,631). O 에 속한 장식의 `ffxMoveDecorationsPlus` 효과 대상은 **원본 경로가 Rec/트윈을 만들지 않게** 한다. 이미 모드가 가진 `DecoAnim`/`FastMove` 의 장식별 생성 지점에서 per-target 으로 건너뛴다(한 효과가 O 와 O 밖 장식을 함께 대상으로 하면 O 밖만 원본으로 처리). 효과의 부수 동작(완료 콜백, 태그 이벤트 트리거, 사운드/조건 등)이 있으면 그 장식·효과는 O 에서 제외(굽기 지원 판정이 이미 일부 걸러 줌; 남는 갈래는 지원 안 함 사유로 세고 문서화).
3. **구동**: 매 프레임 `DecoAnim` 갱신과 같은 위치(기존 `UpdatePrefix`)에서 `tb`(DecoBakeCore.SongClock)를 전진시키고 `ActiveEvaluator`(evalActive)로 **그 순간 활성/방금 끝난 구간이 있는 O 장식의 채널만** 평가해, 원본 `DecoAnim.Step` 이 하는 것과 **같은 setter 경로**(위치→`pivotPosVec`/`UpdatePosition`/batch 쓰기, 회전, 크기, 색, 불투명도, 시차)로 쓴다. 값 쓰기 규칙(같은 값이면 건너뜀, 마무리 `TightLate`/`ColorFast` 경로, Dormancy/InvisibleSkip 와의 상호작용)은 `DecoAnim*.cs` 를 읽고 그대로 따라 한다. 기존 최적화(TightLate, ColorFast, EulerMemo, Dormancy, InvisibleSkip, 투명 장식 위치 반영 미루기)와 충돌하지 않게, 깨지는 조합은 코드로 찾아 문서에.
4. **상태 전이**: 되감기/seek/재시작/일시정지/재개/맵 전환/모드 내리기에서 `tb` 가 재동기될 때, O 장식 **전체를 현재 시각 값으로 한 번 재평가·쓰기(resync)** 한다(무상태 평가기의 이점). resync 비용(프레임 하나에 O 전체)을 계측하고 필요하면 여러 프레임에 나눠 안전하게(나누는 동안 원본 값과의 불일치가 보이지 않게 가려질 순서 설계). 끝난 효과의 끝값은 정확히 한 번 보장.
5. **안전장치**: (a) 평가·쓰기 중 예외/비정상(유한하지 않은 값) → 즉시 adopt 해제하고 resync 후 원본 경로로 복귀(그 시점까지 진행 중이던 효과는 끝값으로 완료), 로그, `Resilience` 에 기능 이름으로 실패 집계. (b) 매 N 프레임 소수 표본 장식을 원본 규칙과 비교하는 자체 검증은 **adopt 상태에서는 원본 Rec 가 없으니** 대신 "표 평가값 == 마지막으로 쓴 값" 일관성만. (c) 다른 모드가 장식 setter 를 패치하는 경우(Quartz 등, `Compat`)는 adopt 거부.
6. **측정 계측**(adopt 켬/끔 비교용): 프레임당 adopt 구동 시간(평균/p99/최악), 소유 장식 수, 건너뛴 Rec 생성 수, 기존 `[장식 이동]`/`[엔진 단계]`/`FuseLate` 카운터와 맞는 이름으로 로그. 끔 판에서는 비용 0.
7. **검증 도구**(adopt 효과 비교): 같은 곡 구간을 adopt 끔/켬으로 각각 재생해 **같은 곡 시각의 장식 상태**를 비교하는 `decobake adoptsig <이름>`(이미 있는 `decosig` 계열 `StateDump` 참고; 정확 해시가 아니라 **허용 오차 비교**: 위치 0.01px·크기 상대 1e-4·색 1/255·불투명도 1/255, 시간 정렬은 곡 시각 ±1표시프레임을 고려해 표본 시각마다 근방 최소 오차 사용) + 두 서명 파일 비교 스크립트 `tools/optimization/adoptsig-compare.py`(불일치 장식·채널·시각 상위 20 출력). 장식 서명 대상은 지원 O 전체.
8. 빌드 3종(`-c Release`; `-p:Edition=Player`; `-p:Edition=Player -p:AutoTestBuild=1`) 오류 0 + LoadCheck + fixture(adopt 로직의 오프라인 부분: resync, 완료값, 소유 집합 분할, 예외 복귀). Player 제외, `Module.ResolveSignature` 금지, 새 Harmony 패치는 이름+인자 수+호출 규약으로 정확히 하나(가능하면 기존 후크 재사용).
