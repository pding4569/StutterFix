결과: `docs/handoff/codex-alphadiscard-20261019-result.md` (**apply_patch 로 UTF-8 BOM, 쓴 뒤 `Get-Content -Encoding UTF8` 로 한글 확인**), 한국어, 추측은 "추정". 제품 C# 은 건드리지 말 것. 임시 Unity Editor 프로젝트와 `tools/gpuprobe/Gpu5Discard.cs`(`#if UNITY_EDITOR`, 제품 Compile 목록 밖)만. 환경: `docs/handoff/codex-gpu3-20261018-result.md`·`codex-tight-20261018-result.md` 의 Editor 6000.3.10f1 D3D11 fixture 방식을 재사용(`%TEMP%/stutterfix-gpu3-20261018/UnityFixture` 등).

## 배경 (Claude 실측)

Arche 곡 258~268초 본 카메라 GPU 3.7ms(3440×1440) 중 약 78%(2.9ms)가 **픽셀 수에 비례**(해상도 50% 시험으로 확인). 대부분 `Sprites/Tile` 셰이더의 큰 반투명 안개 스프라이트 수백 장이 겹쳐 그려진다(`fog.png` 682×682, `nes_large_fog.png` 1489×1489(게임이 긴 변 1024 로 줄여 올림), `nes_black_fog.png`, 경계 상자 합 = 화면 93배(상한)). 이미 폐기된 것(화면이 달라짐/0 byte 아님): 재질 공유, 아틀라스, Tight/격자 메시, alpha≤8 건너뛰기. 이 이미지들은 **알파가 정확히 0 인 픽셀이 많다**: fog.png 20%, nes_large_fog 원본 49%(1024 로 줄이면 약 49%), 반면 alpha≤8 은 58~73%.
아이디어: 프래그먼트 셰이더에서 `a == 0`(정확히 0)이면 `discard`(clip)하면 블렌딩(ROP 읽기-수정-쓰기)·텍스처 이후 연산이 줄어 GPU 시간이 준다. 화면 결과는 이론상 **비트 동일**: 게임의 `Sprites/Tile` 은 스프라이트용 `Blend One OneMinusSrcAlpha`(프리멀티플라이드; 확인할 것)에 프래그먼트에서 `rgb *= a` 하는 구조일 가능성이 높아, `a==0` 이면 출력 색 (0,0,0,0)이고 블렌드 결과는 `dest*(1-0)+0 = dest` 로 목적지가 그대로다(부동소수점/고정소수점 ROP 에서 정확히 0 을 곱한 더하기는 정확).

## 할 일

1. **게임 `Sprites/Tile` 의 실제 렌더 상태·셰이더 동작 확인**: 이미 있는 `docs/handoff/codex-gpufree-20261019-evidence-shaders.txt`(D3D11 디스어셈블리 `Sprites_Tile-0..7.asm`: VS 는 모델·뷰·프로젝션 변환 + `color*cb0[2]`, `uv*cb0[3]`)와 `codex-gpufree-20261019-evidence.json` 의 렌더 상태(Blend, ZWrite Off, ZTest LEqual, Stencil, Cull)에서 **픽셀 셰이더**(ps_4_0)가 하는 일을 읽어 정리: 텍스처 샘플, 색 곱, `rgb*=a`(premultiply)가 있는지, 알파 계산(`a = tex.a * color.a`), `_MainTex` 외 다른 입력, 키워드 변형(`SetPointSamplingVariant` 등)이 PS 를 어떻게 바꾸는지(8개 프로그램 = VS/PS × 4 변형). 그 PS 와 같은 계산을 하는 **Editor 용 대체 셰이더 HLSL**(Sprites/Default 와 거의 같을 것)을 만들고 `discard` 변형을 추가.
2. **비트 동일성 증명**: 독립 Editor D3D11 fixture 로 "discard 없는 셰이더 vs 있는 셰이더"를 실제 안개 PNG(원본과 긴 변 1024 RGBA32 둘 다)로 겹쳐 그려(1장, 3장, 100장 겹침; 회전·스케일·반전·Bilinear/Point·색 곱(color.a<1)·RT 3440×1440 과 1720×720·여러 해상도) RGBA 4채널 byte 비교 → 불일치 0 이어야 한다. 알파 0 인데 `rgb` 가 0 이 아닌 입력 텍셀(투명 영역의 RGB), 알파 0 이지만 `color.a` 곱 전/후 위치에서 판정하는 경우(텍스처 알파 0 vs 곱한 뒤 0)를 모두 시험: discard 조건은 **셰이더가 최종으로 출력하는 알파가 0 이고 출력 rgb 도 0 인 경우만**(= 블렌드가 목적지를 안 바꾸는 경우)으로 정확히 정의할 것 — 프리멀티플라이드가 아닌 블렌드(`SrcAlpha OneMinusSrcAlpha`)·가산(`One One`) 블렌드에서는 `a==0` 이어도 `rgb≠0` 이 목적지를 바꿀 수 있으므로 조건을 `(out.a == 0 && all(out.rgb == 0))` 로. 양성 대조(조건을 느슨하게 해서 일부러 틀리게) 가 검출되는지도.
3. **GPU 시간 측정(핵심)**: 같은 fixture 에서 D3D11 타임스탬프 쿼리(`tools/gpuprobe/query.cpp` / `gpuprobe.dll` 방식 또는 Editor 의 `FrameTimingManager`/`CommandBuffer` 타임스탬프 — 기존 `Gpu3Fixture.cs` 사용법 참고)로 안개 N장(N=50/100/200)을 화면 크기로 겹쳐 그릴 때의 GPU ms: (a) 원래, (b) discard 변형, 안개 3종 × RT 크기 2종(3440×1440, 1720×720), 반복 수십 프레임, 예열, 순서 교차(ABBA)로 드리프트 확인. 안개 스프라이트는 실제 Arche 와 비슷하게 큰 크기(화면의 0.5~3배 면적, 알파 0 영역 비율은 실제 이미지 것)로. 보고: 평균 ms·절약 ms·절약 %, 해상도 모델 `C(s)=A+B·s²` 대비(B≈2.9ms)로 실제 Arche 본 카메라에서의 예상 절약 ms(안개 비중 가정을 명시: census 에서 `Sprites/Tile` 후보 중 안개 draw 의 `aabb_pixels` 합 / 전체 — `%LOCALAPPDATA%\StutterFix\gpu-census-*.tsv`).
   절약이 0.3ms 미만이면 "이득 없음"으로 명확히 결론 내리고 4번은 하지 말 것.
4. **(절약이 크면만) 게임 적용 설계**: 런타임 셰이더 컴파일이 불가하므로 Editor 에서 빌드한 **AssetBundle**(UnityEngine.AssetBundleModule 이 Managed 에 있음)에 `Sprites/Tile` 동치 셰이더(+discard)를 담아 모드가 로드하는 구조: (a) 게임의 정확한 PS 를 HLSL 로 재현해 게임 안에서 원래 재질 vs 대체 재질을 같은 입력으로 RT 에 그려 바이트 비교하는 방법(자동 시험 명령 설계), (b) 351개 재질의 셰이더를 어떻게 바꾸나(`Material.shader = ours` 는 프로퍼티·키워드·renderQueue 를 보존; `scrDecorationManager.tileShader` 정적 변경; `SetBlendMode`/`SetPointSamplingVariant` 호출과의 상호작용; 새 재질이 생기는 곳), (c) 번들 파일 배포(모드 폴더 리소스)와 D3D11 외 API 대비(그 경우는 원래 셰이더로), (d) 위험·복구(Unload 시 원래 셰이더로 되돌림, 번들 로드 실패 시 아무 것도 안 함). 구현은 하지 말고 설계와 작업량 추정만.

빌드 셋은 제품 변경이 없으니 확인만. Unity Editor 는 시험 시간 동안 CPU/GPU 를 쓰므로 Claude 의 게임 측정과 겹치지 않게, 작업 시작 시 `Get-Process "A Dance of Fire and Ice"` 로 게임이 떠 있지 않은지 확인하고 떠 있으면 기다릴 것(최대 10분 후 진행).
