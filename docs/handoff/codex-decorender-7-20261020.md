## 알아낸 규칙 (sortprobe, `docs/optimization-36.md` 끝 참고)
같은 `(sortingLayerID, sortingOrder)` 안 그리기 순서 = (렌더 큐, 카메라 거리 z, **재질 인스턴스 ID**). 재질이 다르면 메시/스프라이트 구분 없이 재질 ID 규칙(98~100%), 재질이 같으면 메시가 스프라이트 뒤. 새로 만든 재질은 ID 가 항상 맨 끝이라 그룹 메시 하나가 순서에서 한 자리만 차지하고, 같은 키의 비관리 장식이 그 안쪽에 끼면 틀렸다(이게 지금까지 가져갈 수 있는 장식이 6~108개로 줄어든 이유).

## 새 아이디어 — 재질 빌려 쓰기
그룹 메시의 재질로 **그 구간 장식의 "자기 재질 인스턴스"를 그대로 빌려 쓴다**(장식마다 재질 인스턴스가 따로 있다). 그러면 그룹 메시의 순서 자리 = 그 장식의 재질 ID 자리라서 정확히 그 장식이 있던 자리에 놓인다. 빌려 준 장식의 SpriteRenderer 는 `forceRenderingOff=true` 라 그려지지 않고, 같은 재질이라도 큐·거리가 같으면 메시가 스프라이트 뒤라서(어차피 안 그려짐) 문제 없다.
- 빌린 재질의 `_MainTex` 를 아틀라스로 바꾼다(그 장식은 안 그려지고 재질 인스턴스는 그 장식 전용이므로 다른 곳에 영향 없음. 원래 `_MainTex` 를 저장해 `off`/복귀 때 복원). 정점 UV 는 아틀라스 좌표. `RepeatX/Y=1`, 그 밖 속성 그대로.
- **연속 구간(run)**: 같은 키의 모든 렌더러(관리 후보·비관리 장식·타일 등, 안 그려지는 것(`forceRenderingOff`·알파 0·비활성) 포함)를 (렌더 큐, z 거리, 재질 인스턴스 ID) 로 정렬한 줄에서, **관리 후보 장식끼리 이어지는 최대 연속 구간**마다 그룹 메시 하나를 만든다. 구간 안의 장식 순서 = 같은 정렬. 구간 안에서 아틀라스 페이지가 바뀌면 거기서 구간을 나눈다(옆에 붙어 있으니 순서 보존). 구간 사이에 비관리 렌더러가 하나라도 끼면 구간을 끊는다. 메시의 sortingLayerID/sortingOrder/Unity layer/월드 z/큐는 구간 장식과 같게.
- **방향**: 재질 ID 오름차순이 뒤→앞인지 내림차순인지는 sortprobe 의 `trials.csv`(`before_back_to_front` 열과 `mat=` 값)로 확정해서 코드에 넣고 로그에 적는다(그룹 순서 규칙 방향).
- 관리 후보: 지난번과 같다(움직이는 장식, Sprites/Tile 기본값 조건, Clamp, ≤2048, 마스크/히트박스 아님, 점샘플링 아님 등) + 이번엔 `shared-order` 제외 규칙을 없애고 위 run 규칙이 순서를 보장한다. 안 그려지는 장식(알파 0 등)도 run 정렬에는 포함하지만 정점은 그 프레임 안 내보낸다.
- 복귀: 구간 안 장식이 sprite/material/sorting/마스크가 바뀌면(기존 변화 감지) 그 **장식만** 구간에서 빼고(원래 SpriteRenderer 복원, 빌려 준 재질이었다면 그 구간의 빌림을 다른 멤버 재질로 넘기거나 구간 재구성). 단순하게: 구간 재구성(그 구간만 다시 만듦)으로 처리.
## 통계/로그 (핵심 판단 자료)
`state` 와 `on` 로그에: 후보(움직이는) 장식 수, **run 수**, 가져간 장식 수, 평균 run 크기, run 크기 분포(1, 2~5, 6~20, 21+), 비관리 때문에 끊긴 횟수, 키 수. `changed-during-observation` 이 많은 건 항목별(sprite/material/sortingOrder/sortingLayer/mask/기타) 개수를 로그에 낸다(이 값 5,374개가 선택을 줄인다 — 원인이 무엇인지 알아야 한다). 이 통계가 "그룹 메시 개수 ≪ 장식 수"가 되는지가 이 방식의 성패다.
