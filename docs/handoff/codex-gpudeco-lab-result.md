# gpudeco 독립 랩 결과 — 자동 반복 2회차

**선택: Unity 6000.3.10f1의 기존 AssetBundle 경로를 유지한다. 직접 D3D11 실행에서 수치·Raw 메시 그리기·번들 생성/재로드가 통과했다. 실제 Arche export는 0개이고, 1,000구간 메시의 제출 2.723905ms는 목표 0.3ms를 초과했다. 게임 연결은 진행하지 않았다.**

근거: [구간 시험](../../tools/gpudeco-lab/evidence/runs.txt), [번들 시험](../../tools/gpudeco-lab/evidence/bundle.txt), [에디터 로그](../../tools/gpudeco-lab/evidence/bundle-r2-editor.txt). 에디터 **6000.3.10f1**, **RTX 4060 Ti / Direct3D11**이다. fsr/BuildFsr.cs.txt와 docs/shader-research.md의 기존 번들 구조를 재사용했다. 네이티브 DLL 변경은 없다.

## 실행과 원인 수정

- 첫 Start-Process 직접 호출은 샌드박스에서 Package Manager IPC 실패, 권한 검토 후에는 라이선스 exit 198이었다. 지시서와 같은 **직접 호출 + -batchmode -quit** 형태는 Successfully resolved entitlement details를 기록하고 실제 fixture에 진입했다. 로그인·라이선스 활성화·소프트웨어 설치는 하지 않았다. -quit 하나가 원인이라고 단정하지 않으며 성공한 전체 호출을 README에 남겼다.
- -nographics 실행은 Null Device여서 GPU fixture가 의도대로 거부했다. GPU 시험에는 이를 빼고 -force-d3d11을 썼다.
- 최초 이징 대조는 **101,475개, 최대 0.00165259838104, 평균 4.02213904572e-7, 2e-5 초과 526개**였다. [이징별 진단](../../tools/gpudeco-lab/evidence/smoke-r2.txt)에서 Circ 경계와 Elastic 위상에 집중됐다. 끝점/중간점 분기를 명시하고 HLSL asin 근사를 축소 구간 유리식으로 대체하고 precise를 적용했다. CPU 정답은 게임의 실제 DOTween.dll의 EaseManager.Evaluate다.
- 1,000개 Raw 버퍼의 복사가 맞아도 처음에는 그리기가 비었다. CPU 사본 폐기·submesh 바운드 명시·동기 셰이더 컴파일만으로는 해결되지 않았다. 같은 실행의 단일 메시 대조군은 1,573픽셀이었다. 분할 메시의 인덱스를 단일 대조군과 같은 **UInt32**로 바꾼 최종 실행에서 1,573픽셀·exit 0을 확인했다. 이 조합의 관측이며 Unity 전체의 UInt16 결함으로 일반화하지 않는다. 실패 증거는 runs-r1.txt~runs-r5.txt, 최종은 runs.txt다.
- 최초 번들은 생성됐으나 재로드에 실패했다. 일반적인 버전 호환 오류 옆에 **AssetBundleManifest의 AssetBundle module disabled** 로그가 있었다. prepare.ps1의 독립 프로젝트에 **기존 내장 AssetBundle 모듈 참조**를 명시하고 강제 재생성한 뒤 재로드·이징 대조가 통과했다. 실제 게임의 번들 호환성은 미검증이다.

## 비용과 이 경로의 한계

|경로|규모|GPU dispatch/프레임|CPU 제출 평균|동기 readback|
|---|---|---:|---:|---:|
|단일 Raw 메시|2,000장식 / 20,000표 구간|1|**0.005729ms** (200회)|**16.1773ms**|
|독립 메시 1,000개|동일 입력 / 2장식씩 분할|**1,001**|**2.723905ms** (100회)|**1.2961ms**|

각각 smoke-r3.txt와 runs.txt의 서로 다른 실행이다. 작은 합성 표본의 에디터 제출 시간이며 실게임 FPS/CPU 전체 비용/물리 GPU 실행 시간이 아니다. 드라이버 대기·밀어내기가 섞일 수 있다. **GPU timestamp는 미제공**이며 readback을 GPU 시간으로 바꾸어 쓰지 않는다. 그리기는 비용 창 밖에서 한 번 확인했으므로 렌더러 1,000개의 매 프레임 엔진 비용도 포함하지 않는다.

공개 Mesh 경로에서는 메시별 별도 Raw 버퍼를 얻는다. 이번 랩은 통합 버퍼에서 한 번 평가한 뒤, 미리 기록한 CommandBuffer의 **1,000개 CopyRun dispatch**로 각 메시 버퍼에 나눈다. CPU 정점 업로드/Transform 쓰기/프레임당 구간 재기록은 없지만, **제출 2.723905ms는 목표 0.3ms의 약 9.08배**이며 dispatch 한 번 조건도 충족하지 않는다. 이 구현을 성능 목표에 맞는 게임 경로로 연결하지 않는다. 모든 GPU 설계가 불가능하다는 결론은 아니다.

네이티브 sfnative.dll의 D3DCompile·렌더 스레드 D3D11 버퍼 접근은 번들 대안이다. 메시별 출력 분배·동기화·수명은 여전히 해결해야 하므로 네이티브 이동만으로 1,000개 제출 비용이 사라진다고 가정하지 않는다. 설계 비교만 남기고 구현하지 않았다. 공유 GPU 버퍼를 직접 그리는 셰이더/그리기 방식은 기존 게임 셰이더·재질·정렬 보존에 새 검증이 필요하다.

실제 export **0개**, 실제 소유율·시작 위상·prepare_ms·게임 G0/G1/G2는 **미측정**이다. 실제 데이터와 제출 비용의 선행 조건을 통과하기 전에는 게임 연결로 진행하지 않는다.
