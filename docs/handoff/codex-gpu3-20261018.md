## 사용자가 가져온 역분석 (Gemini 출처, 아래 1번만 Claude 가 IL 로 직접 확인함 — 나머지는 네가 검증)

1. **확인됨**: 장식마다 개별 Material 이 만들어지는 곳 — `scrVisualDecoration.SetBlendMode`(blendMode==None 일 때 `spriteRenderer.material.shader = scrDecorationManager.tileShader`), `scrVisualDecoration.SetSprite`(`spriteRenderer.material.SetPointSamplingVariant(!smoothing)`, 두 갈래), `ExitFix.LightOne`(ExitFix.cs ~374 `sr.material.SetPointSamplingVariant(!v.smoothing)`). 이 호출이 `renderer.material` getter 라서 렌더러마다 재질 인스턴스가 복제된다.
2. 주장(검증 필요): Arche 258~270초에 타일 3400~3699 의 광선은 타일당 50개가 depth 28..-21(sortingOrder -28..+21)로 깔려 있다. Unity 는 sortingOrder 순으로 먼저 그리므로 같은 sortingOrder(예 -28) 안에서 타일 3440(`nev_travel_90.png`)→3441(`180.png`)→3442(`30.png`)→3443(`150.png`) 순으로 `_MainTex` 가 매번 바뀐다. 보이는 장식 약 2,002개 기준: 현재(개별 재질) 2,002 묶음, 재질 공유만 적용하면 `_MainTex` 전환 때문에 약 953 묶음, 재질 공유+아틀라스(`nev_travel_*.png` 8종 + fog 계열 3종을 한 Texture2D 에)면 `_MainTex` 까지 같아져 수 묶음.
3. 사용자가 정한 동일성 조건: 투명 여백을 절대 자르지 않고 원본 width×height 와 pivot 을 1:1 유지(아틀라스에는 투명/extrude 패딩만 추가). 대상은 `tile == (1,1)`, `SetTextureScaleMultiplier` 안 씀(`!sizeUsed`), `blendMode == None`, `maskingType == None`, `smoothing == true` 인 `scrVisualDecoration` 뿐. Arche 258초·270초 구간에서 원래 화면과 아틀라스+재질공유 화면의 픽셀 대조(0 차이), 본 카메라 GPU 시간(지금 6.21ms), 258~274초 FPS 를 측정하는 것이 목표.

## 이미 알려진 큰 위험 (반드시 먼저 다룰 것)

**재질 공유는 이미 한 번 불합격했다**: `docs/optimization-36.md` "2026-10-17 후속: 21 대체"(279~403줄 근처). 반투명 3장이 같은 layer/order/distance 에 겹치게 두고 재질/렌더러 생성 순서를 바꾼 36조건 모두 실제로 재질이 공유됐고 30조건에서 픽셀이 달랐다. Unity 는 상위 정렬 기준이 같을 때 재질/셰이더 묶음과 내부 순서를 보장하지 않는다. 위 2번의 광선은 정확히 같은 sortingOrder 가 타일마다 겹치는 구조이므로 **같은 문제가 그대로 생긴다**. 옛 구현과 fixture 는 git 에 있다: `git show 30a5bc0 --stat`, 삭제는 `5d42c57`(DecorationMaterialPool.cs, tools/optimization/MaterialPoolFixture/ 등). `git show 5d42c57^:<경로>` 로 읽어라.

## 할 일

### A. 동률 정렬의 규칙 알아내기 (가장 중요)
옛 fixture 를 복원해(작업 트리 밖 임시 위치, 커밋 아님) 동률일 때 Unity 가 무엇으로 순서를 정하는지 실험으로 좁혀라: 렌더러 생성 순서? 재질 인스턴스 ID? 텍스처? 정렬 키 외 내부 id? 같은 재질+같은 텍스처(아틀라스)일 때는 어떤 순서(생성 순서 등)인지. 원래(개별 재질)의 동률 순서가 렌더러 생성 순서/Transform 순서로 결정되고, 공유+아틀라스에서도 같은 규칙이 되는지를 36조건 이상으로 대조(반투명 겹침, 알파 블렌드, 여러 층).
- 결론이 "원래도 생성 순서로 결정, 공유해도 같다"면 같은 fixture 로 0 차이를 증명하고 근거를 적어라.
- "원래는 재질 id 순서로 결정"이면 공유 후 순서가 달라지는 장식 쌍을 미리 찾아(같은 sortingLayer/order 에서 서로 겹치는 쌍 — bounds 겹침) 그 장식만 제외하는 정책을 설계하고 Arche 258·270초에서 제외 후 남는 개수를 센다. 이 개수로 위 2번의 "2,002→수 묶음"이 현실적인지 판단.

### B. 아틀라스 표본화 동일성
Sprites/Default·Tile 셰이더에서 원래 개별 텍스처 vs 아틀라스(extrude 패딩 n픽셀)의 픽셀 대조: Bilinear(smoothing==true), 회전/스케일 변환된 스프라이트, 가장자리, 투명 가장자리 번짐(premultiplied 여부), 텍스처 Clamp(게임이 `SetSprite` 에서 sprite.texture.wrapMode=Clamp 로 설정하는 것 — 아틀라스 텍스처에 대해서도 같은지), mipmap 유무, 이미지 크기 비2의 배수. 앞서 투명 여백 크롭이 Bilinear 에서 9~31픽셀 달랐던 이유(`docs/optimization-36.md` 434줄 근처 "12 투명 여백")와 같은 함정을 피하는 패딩/UV 조건을 실험으로 구하라. 실제 Arche 이미지(`nev_travel_*.png`, fog 계열)로 해 보고, 게임이 이미지를 DXT 압축/축소(긴 변 1024)해 올린 뒤의 텍스처를 아틀라스 입력으로 쓰는 경우와 원본 RGBA 인 경우를 구분하라(DXT 는 4×4 블록 경계 때문에 패딩 정렬 필요).

### C. 소비자 확인 (IL)
스프라이트 텍스처·rect·pivot·재질을 읽거나 쓰는 모든 게임·모드 코드를 IL 로 전수: `sprite.texture` 읽기(wrapMode 쓰기 등 — 아틀라스 텍스처에 쓰면 다른 장식에 영향), `spriteUnscaledSize`/`ResizeCollider`/`GetDecorationPixelsSizeInUnits`(sprite.rect 사용?), `SetPointSamplingVariant`(재질 키워드 — 공유 재질은 smoothing 같은 장식끼리만), `SetBlendMode`, 마스크, 스프라이트 교체 시점(SetSprite 가 장식 이동 효과로 바뀔 때 — 모드 LazySprite/FastMove/InvisibleSkip 과의 상호작용, ExitFix.LightOne 의 같은 재질 호출), 모드의 `ImagePrefetch`/`TexCompress`/`AssetDiskCache`(텍스처가 어디서 만들어지는지)와 충돌 여부. 장식 이동 효과가 이미지를 바꾸는(FastMove.ImageBlock) 경우 아틀라스 스프라이트 사이의 교체.
`Camera.onPreCull`/`Sprite` 동적 배치 가능 조건: 이 빌드에서 SpriteRenderer 동적 배치가 실제로 켜져 있는지(PlayerSettings dynamicBatching, `globalgamemanagers`/ProjectSettings 직렬화 또는 ProfilerRecorder "Batches Count"/"SetPass Calls Count"/"Draw Calls Count" 가 릴리스 플레이어에서 읽히는지 시도). 동적 배치가 꺼져 있으면 재질 공유만으로는 묶음이 줄지 않으므로 이 사실이 결과를 좌우한다 — **숫자로 확인하고 보고**.

### D. 연구용 프로토타입과 측정 (개발자용/자동 시험 전용, 기본 꺼짐)
A·B·C 가 모순 없이 통과할 때만. `DecoAtlasProbe`(새 파일): 대상 조건(위 3번)에 맞는 이미지 장식들의 SpriteRenderer 를 맵 연 뒤(재생 전) 공유 재질+아틀라스 스프라이트로 바꾸고(원래 스프라이트의 pixelsPerUnit/pivot/rect 크기 유지), 끄면 원래 스프라이트·재질로 복원(모드 끄기/맵 전환/재생 다시 시작에서도). 자동 시험 명령 `atlasprobe on|off|state`. 위험이 커서 일반 Player 에는 컴파일하지 않는다. 정확히 같은 곡 시각에서 원래 vs 프로토타입 `shot` 두 장을 뽑아 비교하는 스크립트(`tools/gpuprobe/` 또는 임시)도 만들어라(두 장은 같은 입력 상태여야 하므로 카메라/곡 시각 고정: 기존 `shotat`/`seek` 도구 확인).
Claude 가 게임에서 돌릴 명령 순서(Arche 258초·270초, gpuprobe state 전후, 픽셀 대조, FPS 258~274초)를 결과 파일에 적어라. 구현이 위험하거나 A 에서 차단되면 D 는 하지 말고 이유와 대안(예: 동률 제외 정책, 재질 공유만, 아틀라스 없이 배치 키만 같게 하는 방법)을 적어라.
