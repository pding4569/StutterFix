# StutterFix 인계 문서 (Claude → Gemini, 2026-11-06)

이 문서만 읽고 이어서 일할 수 있게 썼다. 사용자에게는 **한국어 존댓말**로 답한다.

## 0. 한 줄 요약

얼불춤(A Dance of Fire and Ice, Unity 6000.3.25f1, Mono, D3D11) 모드 StutterFix로 **모든 맵에서 화면에 실제로 나가는 FPS(진짜 FPS)**를 올려야 한다. 로직 FPS만 올리는 방법은 사용자가 원하지 않는다. 사용자는 2026-11-07(토)부터 다시 집중해서 돌린다. 그 전에 Gemini가 설계·분석을 먼저 해 보기를 원한다.

## 1. 반드시 지킬 규칙

1. **기본값을 임의로 켜지 않는다.** 대상: `DisplayPace`, `EngineMaskGrow`, `GpuDeco`, `MaxQueuedFrames`. 사용자 결정 사항이다.
2. **판정·입력·곡 시계에 닿는 변경은 이득과 관계없이 먼저 사용자에게 보고한다.** 아래 후보 A가 여기에 해당한다.
3. **푸시와 릴리스(3.0.0)는 하지 않는다.** 사용자가 "올려"라고 할 때만 한다. 로컬 커밋은 해도 된다.
4. **사용자가 게임 중일 때는 게임 실행·빌드·무거운 분석을 하지 않는다.** `E:\StutterFixWork\user_playing.flag`가 있으면 기다린다. 분석 스크립트를 게임과 함께 돌리면 끊김이 생긴다(측정 사례 있음).
5. **시험 뒤에는 반드시 복원한다.**
   - DLL: `E:\StutterFixWork\restore\StutterFix-rc-player.dll` → `D:\SteamLibrary\steamapps\common\A Dance of Fire and Ice\Mods\StutterFix\StutterFix.dll`
   - 부팅 설정: `restore\boot.config.bak` → `...\A Dance of Fire and Ice_Data\boot.config`
   - `Settings.xml`은 시험 도구가 덮어쓴 값을 되돌린다. 강제 종료하면 덮어쓴 값이 남는다.
   - 복원 뒤 SHA-256으로 대조한다.
6. **측정으로 확인된 것만 채택한다.**
   - 비교는 판마다 게임을 새로 켜는 ABBA로, 캐시가 찬 상태에서 한다.
   - 이미지 압축 캐시가 차가우면 같은 구간이 76~236 FPS로 갈린다.
   - 설정이 실제로 적용됐는지 로그에서 확인한다.
   - 끊김은 곡 전체로 본다.
   - 평균 FPS만 보지 말고, 상관을 인과로 읽지 않는다.
7. **`.claude/hooks/build-install.sh` 훅은 C:의 옛 복사본을 빌드해 설치한다.** 실제 작업 트리는 E:다. 손으로 빌드하고 설치한다.
8. **Hertz 시험 맵 이름은 어디에도 쓰지 않는다.** 사용자의 비공개 1000FPS 프로젝트도 언급하지 않는다.

## 3. 빌드와 시험

**빌드 (작업 트리에서, .NET SDK 8)**
- 플레이어용: `dotnet build -c Release -p:Edition=Player` → `bin\Player\StutterFix.dll`
- 자동 시험용: `-p:Edition=Player -p:AutoTestBuild=1` → `bin\PlayerAuto\StutterFix.dll`
- 출력 폴더는 빌드 로그에서 확인한다.

**시험 한 판:** steps JSON을 만들고 `python run_locked.py <steps.json> wt-partial <이름> --keys "FPS 구간,단계 실패" --tail 1`.
- 흐름: 자동 시험 DLL 설치 → 게임 실행 → `night-results\<이름>.log/.txt` 저장 → RC DLL 복원.
- JSON 예: `{"steps":[...],"settings":{"GpuDeco":0,"DisplayPace":false},"timeout_min":14,"tag":"이름"}`.

**자동 시험 명령 (모드 폴더 `autotest.txt`):**

| 명령 | 하는 일 |
|---|---|
| `open <맵 경로>` | 에디터로 맵 열기 |
| `seek <곡 초> 8` | 그 시점 조금 앞부터 재생 |
| `waitsongpos <초> <제한>` | 곡 시각까지 기다림 |
| `fpsmark start` / `fpsmark end <이름>` | 구간 FPS (로그 `[FPS 구간] 이름 : N FPS`) |
| `game <맵>` + `press` | 게임 화면에서 재생 |
| `waitend <초>` | 곡 끝까지 (로그 `[곡] 평균 ...`) |
| `wait N`, `auto on`, `fpscap 0`, `quit` | 기본 |
| `waitutc <ticks>` | 여러 프로세스 시작 맞추기 |

명령 하나당 제한은 180초다. 긴 대기는 나눈다.

**측정 기준 문제 (중요):** 11-05 10:37 뒤 시험은 `Settings.xml`의 `EffectsOff`에 `SetFilter,Bloom,Flash,HallOfMirrors,ShakeScreen`이 있었을 가능성이 높다. 시험 도구가 이 값을 덮어쓰지 않으므로 효과가 꺼진 채 잰 것이다. 대부분의 수치도 2560x1440 120Hz다. 사용자 실제 환경은 **3440x1440 165Hz, 효과 켬**이다. 앞으로는 `EffectsOff`, `FiltersOff`, `NoFx`를 settings에 항상 명시하고, 화면 조건을 로그(`[곡 시작] 화면:` 줄)로 확인한다.

**프레임 나눔 (추정, 메인 ms)**

| 맵 | 프레임 전체 | 매 프레임 로직 | 그림 한 장마다 드는 몫 |

**게임 구조:** 게임 핵심 로직(공·판정·컨트롤러)은 1~2%다. 비용은 맵 시스템(장식·트윈·타일 색·홀드)과 엔진 호출에 있다. Arche는 장식 2만 8,835개, 활성 Transform 약 14만, 메인 약 10ms이고 장식 갱신이 절반 가까이다.

**채택된 것 (제품 코드)**
- JIT 인라인: 곡 전체 +2~5.6%
- 홀드 건너뛰기: 값 대조 불일치 0
- Dormancy 수정: +1~2%
- 마스크 엔진 패치: Exit 단판 +11.8%, 기본 끔, RVA 0x1148649 바이트 대조 방식(`EnginePatch.cs`)

**DisplayPace (화면에 나갈 프레임만 그리기):** 로직 FPS만 2~3배로 오른다. 사용자 실제 플레이에서 체감은 조금, 화면 흔들림은 더 심했다. 진짜 FPS 목표에서 제외했다.

**GpuDeco:** Arche 최악 10초 102→322 FPS로 지금까지 가장 큰 진짜 이득이다. 다른 맵은 손해(Windflower 352→216)라 기본 끔이다. 켜는 조건 4회차 모두 기각됐다.

## 6. 다음 후보 (Gemini가 설계·검토할 것)

### A. presentation 대기 없애기 (1순위)

- **근거:** 메인 스레드가 플레이어 루프 `TimeUpdate.WaitForLastPresentationAndUpdateTime` → `GfxDeviceD3D11::WaitForLastPresentationAndGetTimestamp`에서 기다린다.
  - HELLO 표본 17.0% (`docs/render-system/data/profile/20261105-ss-hl-main.sym40.txt`)
  - DD는 메인 대기 표본 2,337개가 모두 이 호출 아래 (`docs/deco-spec/results/engine-extreme.md`)
  - 다른 맵의 메인 대기 비율: DD 15.7~48.7%, 7777 20%, Windflower 12%. 이 맵들이 같은 호출인지는 미확인이다.
- **보조 증거:** `MaxQueuedFrames` 2→4 단판 HELLO 226 FPS(기준 193~208), Arche 변화 없음. ABBA 전이다.
- **모순:** 스레드 CPU 시간 표본에서 메인은 96~100%였다(맵 2022, 1초 간격). 이 대기가 회전 대기인지, 맵마다 다른지 밝혀야 한다.
- **설계 질문:**
  1. 이 대기는 무엇을 위한 것인가. D3D11 플립 모델, 프레임 지연 대기 객체, 창 모드 합성 중 어디서 오는가.
  2. 플레이어 루프에서 단계를 빼면 시간 갱신도 사라진다. 대기 함수만 건너뛰는 엔진 패치 지점을 어떻게 잡을지.
  3. 앞서 달릴 때 화면 지연 증가를 어떻게 잴지. PresentMon은 관리자 권한이 필요하다.
  4. 독점 전체 화면은 예전에 FPS 209→187로 떨어졌다. 그 이유는.
- **위험:** 곡 시계와 같은 단계다. 시험 전에 사용자에게 보고한다.

### B. D3D12 + split/native 그래픽 작업 재시험

- D3D11에서는 split·native가 지원되지 않아 되돌려진다(로그로 확인). legacy를 끄면 Arche가 101→74로 떨어지므로 이 방향의 효과는 실제로 있다.
- 10월 D3D12 시험은 `ReserveScratchMemorySlow`로 곡 중 60~80ms 멈춤이 났다(CLAUDE.md "D3D12 곡 중 멈춤"). 엔진이 6000.3.10에서 6000.3.25로 바뀌었다.
- 끊김부터 보고, 멈춤이 남아 있으면 닫는다. Vulkan은 맵 필터 셰이더 포함 여부만 먼저 본다.

### C. 게임 2개 번갈아 그리기 (사용자 아이디어)

- **측정된 것:** 각자 전부 계산할 때 합 1.56배. 합성은 아직 없다.
- **구조 안:** 두 프로세스가 같은 입력·곡 시계로 반 프레임 어긋나게 그린다. B의 그림을 공유 D3D11 텍스처로 A에 넘겨 A가 출력한다. 판정은 A만 하고 결과를 B에 보낸다.
- **1일 시제품으로 가를 것:** 3440 + 효과 켬에서의 합계 배수, 두 그림의 어긋남, 출력 간격.
- **닫는 기준:** 1.3배 미만이거나 어긋남을 못 없애면 닫는다.
- **걸림돌:** 메모리·VRAM 2배, 판정 동기화, 6코어.
- **뺄 것:** 장식 계산만 넘기는 방식. 계산이 아니라 엔진 쓰기가 비용이다(`DecoEngine` Arche 3.04→3.02ms).
- **Gemini에게 가장 원하는 것:** 이 구조가 실제로 성립하는지 판단과 설계.

### D. 대용량 페이지

권한(`SeLockMemoryPrivilege`)은 부여했지만 재로그인 전이라 적용되지 않았다. Mono·Unity 힙 할당을 가로채는 방법과 효과 예측이 필요하다.

### E. 엔진 핫패스 패치

후보: `memcpy_repmovs` 호출자, `ShaderPropertySheet::FindPropertyIndex`, `TransformChangeDispatch`, Mono 래퍼(표본 7~8%). 각각 +3% 이상일 때만 남기고, 바이트 대조로 스스로 꺼지게 한다.

### F. 장식 많은 맵

프리팹 자식 줄이기(이미지 장식 하나에 GameObject 9개), GpuDeco를 맵에 따라 적용하는 조건.
