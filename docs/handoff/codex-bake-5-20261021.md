## 해야 할 것
1. **오차 원인 진단(코드 근거 + 출력 추가)**: `decobake verify` 에 상세 진단 추가(개발 전용): 오차 상위 3개 장식에 대해 (a) 그 장식의 효과 목록(T0=startTime−startEffectOffset, startTime, startEffectOffset, duration, 이징, 시작/끝값, 교체 여부), (b) 실제 Rec 가 처음 움직인 프레임·곡 시각, (c) 최대 오차 부근 12개 표본 행(프레임, 곡 시각 songposition_minusi, 실제값, 굽기값, 직전 프레임 dt), (d) 오차를 최소화하는 **상수 시간 오프셋**과 그때의 잔차(초 단위)를 계산해 출력. 이 오프셋이 `calibration_i`, `addoffset`, 카운트다운(`dspTimeSongPosZero`/`separateCountdownTime`), pitch, 에디터 재생 vs 게임 화면 경로 차이 중 어느 값과 같은지 코드(`scrConductor`, `ffxPlusBase.SetStartTime`, `scrVfxPlus.Update`)로 따져 적는다. 값(시작/끝, 상대 기준) 해석 오류 가능성(예: 위치 기준이 startPos 인지 pivotPosVec 인지, Tile 기준 원점)도 같이 점검.
2. **수정**: 진단으로 확정한 시간 대응(또는 값 해석)을 고쳐 같은 시험에서 오차가 기준(시작 위상 ≤1프레임, 위치 ≤0.01px)에 들어오게 한다. 확정 못 하면 "확정 못 함 + 다음에 필요한 관측"을 구체적으로 적고, 잘못 맞춘 보정값을 임의로 넣지 않는다. 오프라인 fixture 에 이 시간 대응 규칙을 반영.
3. **표본 확대**: `decosim capture <초> moving` 같은 옵션(또는 verify 대상 선택 규칙 개선)으로 캡처 구간에서 **실제로 움직이는(활성 Rec 있는) 장식**을 우선 표본으로 삼아 모든 채널(위치/회전/크기/색/불투명도/시차)의 n 이 0 이 아니게. 표본 수가 부족한 채널은 "관측 불가"로 명시. 캡처 구간은 Arche `seek 262 8` 뒤 `waitsongpos 264` 에서 12초(장식 이동이 몰린 구간).
4. **비용 정리**: (a) 수집을 메인 slice ≤ 16ms 로 쪼갠다(183ms 의 주범을 `bench` 에서 단계별로 분해: 장식 28,835 스냅샷, 효과 111,216 읽기, 태그 조회 중 무엇인지). (b) 표 payload 45.4MiB 의 내역(구간 858,286 × stride, 헤더, 인덱스)과 줄일 방법(stride, 채널 희소화). (c) eval: `bench` 의 eval 이 무엇인지 명확히 하고, **프레임 비용에 대응하는 값**(곡 시각 t 에서 활성/예약 구간이 있는 장식·채널만, 장식별 커서 사용)을 따로 재도록 `evalActive` 지표 추가. 목표 ≤0.5ms.
