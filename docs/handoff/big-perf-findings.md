# 큰 성능 임무 결과

측정: 2026-10-14~15. 임무: `mission-big-perf.md`. **새 성능 수정 채택 0개**. 원래 결과와 같은 JSON 할당 감소 후보를 만들고 네 맵 대조 및 Arche ABBA 4판을 했지만, 파일 읽기 개선이 0.165초이고 전체 열기는 개선되지 않아 임무의 작은 이득 제외 규칙대로 제거했다. 프레임 생성·셰이더·다른 모드 소스·Git 브랜치/커밋/푸시/릴리스는 건드리지 않았다.

## 조건과 해석

- 게임 실행과 종료는 `tools/sfmeasure/server.py`의 `sf_run`을 Python 3.12로 직접 호출했다. 매 판 새 게임을 실행했고 모든 판은 자동 시험의 `quit`으로 종료했다.
- 현재 사용자 설정과 다른 모드를 유지했다. 프레임 생성은 기존 설정에서 활성 상태였으며 새 최적화로 계산하지 않는다. 화면은 3440×1440, 165Hz, 수직동기 0, FullScreenWindow였다. 수치는 생성 출력 FPS가 아니라 기존 모니터가 잰 게임 프레임이다.
- 첫 4판은 사용자 자동 이미지 한도였다. 첫 Arche 곡 중 오프라인 JSON 검사를 함께 돌린 잘못이 있어 그 곡 중 수치는 순위에서 제외한다. 이후 오프라인 검사·빌드는 게임 종료 후에만 수행했고, 최종 4판은 이미지 한도를 3072로 고정했다.
- 기존 `[곡] ... 끊김`은 임계값·연속 프레임 묶기 규칙이 있다. **30ms 초과 프레임 수와 같지 않다.** 이를 보완한 `[임무30]`은 시작 연출 뒤의 모든 `ms > 30`을 개별 집계한다. 최대 512개의 위치를 저장하며 최종 판의 저장 누락도 검사한다.
- `[임무30]` 위치는 기존 TopFrame과 같은 `Time.unscaledTime - songStartT`다. 화면에 나온 곡 위치와 시작 대기만큼 차이 날 수 있다. CPU/GPU 표본은 비동기·이전 프레임 표본이 섞일 수 있어 하나의 수치만으로 원인을 확정하지 않는다.
- 맵 열림 시간은 **게임 화면에서 최초 재생 준비가 끝난 뒤 2초 대기 포함**이다. 실제 준비를 포함한 열기는 표의 수치에서 2초를 빼면 된다. 첫 키 누름 뒤 카운트다운·음악 offset은 비용에서 분리하며, 편집기 첫 Play의 동기 준비 시간을 별도로 잰다.
- 완주 시간은 `OnLandOnPortal`의 prefix→finalizer이며 다른 패치·곡 요약 로그도 포함한다. 다시 하기는 기존 `[재시작 시간]` 및 `[전환]`을 각각 기록한다. 두 값은 같은 범위가 아니므로 합산하지 않는다.

- Arche 최종 51.681ms는 271.334초, 효과 0.069ms다. 경쟁 부하가 있었던 첫 Arche 판(최악 21ms/끊김 0)은 최종 비교의 기준선으로 쓰지 않았다.
- Windflower는 첫 판 264.6초 42ms, 최종 판 263.426~264.553초 33.633·46.392·45.539ms로 같은 구간에서 다시 관측됐다. 기존 모니터는 게임 바깥 또는 GPU 쪽으로 분류했고 효과만으로 전체 시간을 설명하지 못한다. **VRAM 이동·드라이버·OS 중 어느 것인지 확정하지 않았다.** PerfView 없이 알 수 있는 범위까지만 기록한다.
- Timeline 첫 판 41.1초 34ms와 최종 판의 프레임은 서로 다른 위치다. 일회성 함수별 비용이나 특정 타일 이동 효과가 범인이라는 근거가 없다.
- 최종 모든 프레임 위치가 저장 한도 512개 이내여서 누락 0개다. 완주 훅은 4판 모두 기록됐고 단계 실패·시간 초과·강제 종료는 없었다. StutterFix/자동 시험 오류는 0이다. 기존 다른 모드의 초기화 메시지와 원래 게임 필터의 DivideByZeroException은 별도이며, 전체 게임 로그에 예외가 전혀 없다는 뜻이 아니다.

## 후보 순위와 처리 판단

초 단위 대기 → 50ms 초과 → 30ms 초과 순서로 정리했다. 이미 고친 기능은 새 원인/새 해결로 세지 않는다. 아래 대기는 기존 최적화를 켠 상태에서 **남은 관측 비용**이다.

| 순위 | 남은 관측 비용 | 코드 원인 확정 여부 | 처리 |
|---|---|---|---|
| 1 | Arche 최초 키 누름 준비까지 14.9초(안정화 대기 제외), 장식 28,835개 생성 단계 약 7초 | 이미지·배치 복제는 기존 해결. 그 외 Setup/엔진 생성 비용을 새로운 한 원인으로 분리하지 못함 | 새 우회/풀링을 넣지 않음. 객체 순서·Awake·다른 모드까지 같다는 보장이 부족함 |
| 2 | HELLO 최초 준비 11.1초, Windflower 9.2초 | 기존 이미지 해독·압축 경로의 잔여 시간. 새 원인 확정 안 됨 | 이미 고친 ImagePrefetch/압축을 이번 성과로 세지 않음 |

큰 최적화 1~3개를 채택한다는 목표는 달성하지 못했다. 안전한 후보 1묶음을 실제 구현·대조·측정했으나 임무의 작은 이득 제외 기준을 충족해 폐기했다. 따라서 **채택 0개, 새 사용자 성능 설정 0개**이며, 원인 미확인 항목을 해결 완료로 표시하지 않는다.

## JSON 후보의 4판 A/B와 폐기

변경 후보는 JSON 객체 사전의 초기 용량 16과 숫자를 임시 문자열 대신 span으로 해석하는 것 두 가지를 한 묶음으로 했다. 파서 인스턴스 안에서 설정을 고정했고 게임 이벤트·판정·효과·이미지에는 손대지 않았다.

| 순서 | 후보 | 맵 파일 읽기 | 그중 이벤트 변환 | 맵 열림(2초 포함) | 편집기 Play | 편집 복귀 |
|---|---|---:|---:|---:|---:|---:|
| A1 | 끔 | 2.413초 | 1.135초 | 16.9초 | 2.308초 | 2.377초 |
| B1 | 켬 | 2.276초 | 1.162초 | 17.7초 | 2.302초 | 2.503초 |
| B2 | 켬 | 2.209초 | 1.116초 | 16.6초 | 2.322초 | 2.374초 |
| A2 | 끔 | 2.401초 | 1.130초 | 16.9초 | 2.306초 | 2.371초 |
| 평균 A→B | | **2.407→2.243초** | 1.133→1.139초 | **16.90→17.15초** | 2.307→2.312초 | 2.374→2.439초 |

- Arche, 이미지 한도 3072, ABBA, **총 4판(A 2판/B 2판)**, 판마다 새 게임. 각 판은 게임 화면 10초·에디터 재생 약 8초의 짧은 구간이며 곡 전체 A/B가 아니다. StutterFix/자동 시험 오류 0, 모든 재생 구간 끊김 0. 후보를 채택하지 않으므로 곡 전체 개선 주장도 하지 않는다.
- 오프라인: 네 실제 맵 + 네 문화권 + 잘린/잘못된 입력에서 **3,486,094개 형식·값·키 순서·실수 비트 대조, 다름 0**. Mono에서도 네 맵 모두 형식·값·키 순서·실수 비트가 같았다.
- 초기 용량만의 오프라인 탐색: 원래 할당 361.8MB→312.3MB. 이 숫자는 .NET 8의 스레드 할당량이며 게임 Mono의 힙 증가량과 섞지 않는다.
- **제거 이유:** 파일 읽기는 0.165초 개선(0.3초 미만), 전체 열기 개선 없음, 끊김 변화 없음. 기본 끔 설정도 생산 코드에 남기지 않았다. `FastJson.cs`, `FastJsonParser.cs`, `StutterFix.cs`는 작업 전 바이트로 복구했다.
- `big-perf-evidence/rejected-json-alloc.patch`와 `rejected-json-check.zip`은 검토용 폐기 후보이며 현재 빌드에 포함되지 않는다. ZIP의 체크 도구를 재현하려면 포함된 후보 파서를 프로젝트 폴더에 두고 csproj의 Compile 경로를 해당 파일로 조정한다.

## 남긴 측정 코드와 오버헤드 검토

`AutoTest.cs`와 `PerfOverlay.cs`에 **AUTOTEST 조건부 코드만** 남겼다. 정식 DLL에 새 대조·측정 문자열/형식/메서드가 없는지 최종 확인한다.

- 30ms 집계: 이미 잰 ms에 분기 하나, 초과 때 고정 구조체 배열 쓰기. 곡 중 Stopwatch·문자열 생성·컬렉션 확장·로그 없음. 배열 512개는 모니터 생성 때 한 번 할당하고 모니터 파괴 때 해제한다.
- 단계 시간: 단계 시작/완료 때만 Stopwatch. 새 매 프레임 시계 읽기 없음. wait는 준비 명령과 스케줄러 경계의 차이로 표시 시간보다 짧게 기록될 수 있으며 성능 개선으로 세지 않는다.
- 완주 시간: OnLandOnPortal 한 곳만 초기화 때 패치, 완주 때만 시계 읽기. 곡 시작 때 수백 개 패치 설치 없음. 기존 `StutterFix` Harmony ID를 사용하므로 `Main.Unload → UninstallAll`의 기존 UnpatchAll에서 해제된다.
- 게임 함수가 던진 예외는 그대로 돌려준다. 결과 값·게임 상태·정적 이벤트·PlayerLoop는 바꾸지 않았다. 프레임 배열은 다음 곡 시작 때 카운터만 0으로 하고, 아직 유효한 부분만 읽는다.
