## Claude 의 설계 가설 (코드 근거로 검증·반박할 것)

"거부 없음"을 두 층으로 나눈다.
1. **상태 출처**: (T) 표로 예측 가능한 장식은 지금처럼 GPU 가 표를 평가. (L) 예측 불가(조건·수동·타격 이벤트, 히트박스, 행성 추종, 다른 모드의 setter 패치, 표에 없는 필드: 크롭·원래 크기·스무딩·마스크 종류 변경 등)는 게임이 CPU 로 계산한 최종 값을 그 장식만 프레임마다(또는 바뀔 때만) 같은 항목 버퍼에 올린다. 상태 때문에 거부되는 장식이 없어진다.
2. **그리기 기능**: 이미지 사각형(지금) + 반복/Tiled + 마스크(스텐실 제공자·소비자) + 깊이 변경(자리 미리 계획) + 혼합. 이미지가 아닌 장식(글자·파티클·오브젝트/프리팹)은 (a) 원래 렌더러를 '순서 있는 장벽'으로 두되 맵 전체 거부·최소 소유 수 조건을 없애거나, (b) 정적인 글자는 구워서 이미지 항목으로.
3. **LOD**: RunLod 후보도 GpuDeco 가 맡으려면 안쪽 LOD 가 RunLod 보다 싸야 한다(구간마다 RT 전환이 원인으로 추정 — 근거 확인).

## 써야 할 내용

1. **전수 표**: 코드에 있는 모든 거부·내리기·맵 전체 포기 경로(`Reasons.Add` 문자열 전부, GpuDecoScene/LiveDecoRenderer 의 reject 문자열 전부, 동점 정리, 직접 텍스처 한도 48, 화면 복사 묶음 내리기, 최소 소유 64, 활성화 거절·CPU 복귀 조건 전부)마다:
   게임이 실제로 하는 일(파일:줄) / 왜 지금 못 맡는지 / "거부 없음" 설계에서 어디로 가는지(T·L·그리기 기능·장벽) / 구현 크기(작음·중간·큼)와 위험 / 프레임당 비용 추정 근거.
2. **게임 쪽 전수**: 장식 종류 4가지와 장식을 건드리는 모든 이벤트·필드·컴포넌트를 나열하고 각각 GpuDeco 대응 유무. 명세 7절 "아직 안 읽은 것"도 메운다.
3. **가설 검증**: (L) 경로를 지금 구조(항목 버퍼 올리기 `WriteItemSlots`/UpBytes, 이어받기)로 만들 수 있는지, 항목당 비용, 게임이 값을 쓰는 시점과 우리가 읽는 시점(LateUpdate 뒤) 문제, 장식이 꺼졌다 켜질 때. 마스크: 게임 스텐실 규칙(SpriteMask 범위 front/back 정렬층, maskInteraction)과 구간 렌더러로 같은 결과를 내는 방법. 깊이 변경: DepthInstances 가 DD 3420개에서 기본 꺼짐인 이유와 남은 문제. Repeat: 7777 사슬 차이의 원인 후보(코드로 좁힐 수 있는 데까지).
4. **최적화가 확실한가**: 각 항목이 줄이는 것이 무엇인지(Update/LateUpdate 스크립트 시간, 렌더 준비 CPU, 그리기 호출, 덧칠) 구분하고, 지금 측정으로 이득을 말할 수 있는 것과 없는 것을 나눈다. Claude 가 추가로 재야 할 실험 목록(명령·설정 이름까지).
5. **구현 순서 제안**: 맵 6개의 거부 수와 위 비용을 근거로 1~N 단계. 각 단계의 합격 기준(소유 수, 같은 프레임 그림 비교, 원래 방식 대비 FPS).
