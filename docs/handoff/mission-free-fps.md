# 임무 3: 게임 코드를 고치지 않고 프레임을 올리는 방법을 모두 시도한다 (Codex 자율, 사용자 수면 중)

사용자가 자는 동안 돈다. 중간에 사용자에게 묻지 말고 판단한다. **프레임 보간(FrameGen*, framegen*.h)과 쉐이더 코드는 건드리지 않는다.**
"게임 자체를 최적화하지 않고도 FPS 를 올리는 방법"을 후보별로 시도하고, 되는 것은 구현·A/B, 안 되는 것도 왜 안 되는지 증거를 남긴다.
시간 상한: 총 약 3시간. 후보 하나에 40분을 넘기면 접고 다음으로 간다.

## 환경 주의

- 사용자의 모니터가 꺼져 있을 수 있다. 그러면 게임 해상도·주사율이 바뀐다(2560x1440 120Hz 등). **A/B 는 같은 세션 안에서 번갈아(ABBA) 잰다.** 판마다 실제 해상도·주사율(`[곡 시작] 화면:` 로그)을 기록하고 달라진 판끼리는 비교하지 않는다.
- 게임이 시작 120초 안에 안 뜨거나 화면이 멈춰 있으면(자동 시험 단계 실패) 그 후보를 접고 다음으로 넘어간다. 게임 프로세스를 강제로 죽이지 않는다(`sf_quit`/자동 시험 `quit` 만).
- 측정 맵: GPU 가 병목인 맵이 이득을 가장 잘 보여 준다. Windflower(이미지 많음), Arche(장식 많음), HELLO 2026(타일·필터), `C:/SFBundle/autotest/maps/h90000/h90000.adofai`(단순). **프레임 늘리기는 `FrameGenOutside=0` 으로 끄고 잰다**(보간과 섞이지 않게).
- 지표: 곡 중 평균 FPS(제한 없음, `fpscap 0`), GPU 평균 ms, 30ms 초과 프레임 수(`[임무30]`). 같은 조건 4판 이상.

## 시도 목록 (순서대로)

### 1. 배경 카메라 비용 측정 → 정적 배경 층 캐싱
게임은 카메라를 3개(정지 배경 `Bgcamstatic`, 움직이는 배경 `BGcam`, 본 `camobj`) 매 프레임 그리고 `camRT` 한 장에 합친다(`scrCamera`, AGENTS.md/게임 IL 확인).
1. 먼저 비용을 잰다: 자동 시험 명령으로 카메라 하나씩 `enabled=false`(또는 cullingMask=0)로 끄고 FPS·GPU ms 를 비교(화면은 틀려도 됨, 측정 전용). 각 카메라의 GPU 비중을 표로.
2. 정지 배경이 GPU 의 10% 이상이면 구현한다: 그 카메라의 입력(카메라 위치·줌·배경색·장식 변경)이 바뀌지 않은 프레임은 렌더를 건너뛰고 이전 결과를 재사용. 대조(건너뛴 화면 = 원래 화면, 바이트 비교, 차이 0)를 만든 뒤에만 켠다. 기본 끔 설정.
3. 10% 미만이면 구현하지 않고 수치만 적는다.

### 2. camRT 설정
게임이 `new RenderTexture(Screen.width, Screen.height, 24)` 로 camRT 를 만든다(`LowEnd.RTWidth/RTHeight` 가 이미 크기를 바꾸는 자리).
깊이 24 → 0/16, 색 형식(ARGB32 → 더 가벼운 형식)이 화면을 바꾸지 않는지(스프라이트 마스크는 스텐실을 쓴다) 대조하고, 바꿔서 FPS/GPU ms 변화를 잰다. 같은 화면이 아니면 접는다.

### 3. 카메라·품질 플래그
각 카메라의 `allowHDR`, `allowMSAA`, `allowDynamicResolution`, `useOcclusionCulling`, `forceIntoRenderTexture`, 사용 안 하는 오버레이 카메라, 파티클 `QualitySettings`(파티클 레이캐스트, 소프트 파티클), 텍스처 `anisotropicFiltering`/`masterTextureLimit`(화질이 같은지 확인 필요)을 현재 값과 함께 표로 만들고, 화면을 바꾸지 않는 것만 켜 본다.

### 4. 불필요한 렌더 호출 줄이기
`FrameScan`/`RenderWatch` 등 기존 진단으로 한 프레임의 카메라 수·드로 콜 수·SetPass 수를 센다. 같은 재질을 쓰는 스프라이트 배치가 깨지는 지점(재질 인스턴스 `Renderer.material` 호출, MaterialPropertyBlock)을 찾아 코드로 되돌릴 수 있는지 본다(예: `BlendModes` 쪽은 "블렌드 빠르게"가 이미 있음).

### 5. 필터 합치기 (타당성만)
연속된 단순 색 필터(밝기·대비·채도·노이즈)가 같은 프레임에 3개 이상 켜진 비율을 `filterstate` 로 센다. 합칠 수 있는 조합이 곡 중 자주(예: 30% 이상) 있으면 한 번의 Blit 로 처리하는 방법(결과 동일성 포함)을 설계만 `docs/handoff/free-fps-findings.md` 에 쓴다. 구현은 하지 않는다.

### 6. 안 되는 것도 증거를 남긴다
- VRS, 멀티스레드 렌더링, 다른 업스케일러(DLSS 등)가 이 게임(유니티 6000.3, D3D11, Mono)에서 모드로 가능한지 코드·설정(`boot.config` 옵션, 유니티 명령줄 플래그)으로 확인하고 불가하면 이유를 한 줄로.
- 유니티 명령줄/`boot.config` 숨은 옵션(AGENTS.md "D3D12 곡 중 멈춤 조사" 참고: `-force-gfx-jobs` 값 등)은 이미 시험한 것을 반복하지 않는다.

## 규칙

- 새로 거는 것(Harmony, 이벤트, 카메라 상태 변경)은 `Main.Unload` 에서 되돌린다. 기본값은 끔(이득이 확정되고 화면이 바이트까지 같으면 켬 가능, 단 그 근거를 문서에).
- 개발용 대조·측정은 `#if DEV || AUTOTEST` 안에서만. 정식 `-p:Edition=Player` 빌드에 안 들어가게 하고 빌드 두 가지(자동 시험·정식) 모두 오류 0.
- 커밋·푸시·릴리스 금지(작업 폴더에 둔다). 끝나면 게임 꺼짐 확인, Mods 에 **정식 DLL**(`bin/Player/StutterFix.dll`, `dotnet build -c Debug -p:Edition=Player` 결과, 현재 설치된 것과 같은 SHA-256 `cb634d73…`) 복원, Settings.xml 원래 값 복원.
- 결과는 `docs/handoff/free-fps-findings.md`: 후보별 표(시도, 전→후 수치와 판 수, 화면 동일 여부, 채택/기각 이유). 마지막 메시지에 상위 3줄 요약.
