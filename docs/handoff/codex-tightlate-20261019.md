# Codex 작업 A: 장식 LateUpdate 전용 빠른 길(TightLate) — 게임 실행·Mods 설치·커밋 금지

결과: `docs/handoff/codex-tightlate-20261019-result.md` (**UTF-8 BOM 으로, apply_patch 로 쓰기 — 지난 작업 결과 문서는 PowerShell 로 쓰다 한글이 '?' 로 깨졌다. 쓴 뒤 `Get-Content -Encoding UTF8` 로 한글이 남아 있는지 확인할 것**). 한국어, 추측은 "추정". 빌드 셋 오류 0(`dotnet build -c Debug -p:Edition=Player -p:AutoTestBuild=1`, `-p:Edition=Player`, 기본). 새 동작은 모드 폴더 파일 `tightlate-off` 로 끌 수 있고(DevPresentFlags 방식), 설정 필드가 필요하면 `Config` 에 비공개 항목으로. 기본값은 코드에서 **켬**으로 두되 검증 도구가 불일치를 세면 그 장식만 원래 길로 보내고 로그를 남긴다(스스로 끔 금지: 원인 확인용).

## 배경 (Claude 실측, Arche 곡 270초 구간, CPU 병목)

메인 10.47ms/프레임. 그중 `scrDecorationManager.LateUpdate` 1.9~2.4ms: 깨어 있는 장식 약 1,130~2,150개 각각 `LogicUpdate`→(보이면) `UpdatePosition`. 지난 두 시도가 실패했다 — 그 이유를 반드시 이해하고 설계에 반영:
- **FuseLate**(`git log --all -- FuseLate.cs`로 찾아 `git show <commit>:FuseLate.cs`, 결과 `docs/handoff/codex-fuselate-20261018-result.md`·`-il.txt` 남아 있음): `UpdatePosition` prefix 에서 조건 검사 + 엔진 쓰기 2개(`SetPositionAndRotation` + `localScale`)로 합쳐 150,713번 비트 비교 불일치 0이었지만 LateUpdate 가 2.39~2.48 → 2.65ms 로 **느려졌다**. 원인 추정: 장식마다 `ConditionalWeakTable` 조회·부모 변환 확인·프레임/카메라 캐시 비교 등 **관리 코드 검사 비용이 줄인 엔진 호출보다 컸다**.
- **작업 스레드**(`decojob`, `docs/handoff/codex-jobs-20261018-result.md`, `DecoJobShadow.cs` 에 `writetest` 포함): 장식 2,150개의 Transform 쓰기 3개(position·rotation·localScale)는 **메인 스레드에서 해도 0.204ms/프레임**(장식당 약 0.1µs), 작업 스레드는 0.188ms. 위치·크기는 계산값이 실제 Transform 과 **비트 동일**(2.9M), 회전은 Transform 설정자가 내부 정규화하므로 계산한 쿼터니언을 **같은 설정자로 쓰면** 같다(0 차이 확인). 순차/작업 계산 비트 일치 0 불일치. 그림자 계산 비용: 입력 모으기 0.11ms, 계산 0.18ms(작업 스레드 합).
→ 결론: 엔진 쓰기와 계산은 싸다(합 약 0.3~0.5ms/프레임). 비싼 것은 장식마다 도는 **관리 코드·네이티브 읽기 잡동사니**(`GetVisible`=`spriteRenderer.enabled`+`activeInHierarchy`, `UpdateShader`, 모드 패치 체인, `parallax.SetTrans` 의 `cachedTransform.position` 읽기·카메라 위치 읽기 등). 목표: 조건을 통과하는 장식은 **장식당 0.3µs 안팎의 아주 얇은 루프**(미리 계산·캐시한 값만 읽고, 프레임마다 바뀌는 필드와 카메라 값만 읽어 계산 후 엔진 쓰기 3개)로 처리해 LateUpdate 를 2.4ms → 1ms 이하로.

## 설계 지침

1. **정적 정보는 한 번만**: 장식이 처음 조건을 통과할 때(또는 장식 목록이 만들어질 때) 장식별 정적 값을 구조체 배열(SoA, 인덱스 = 배치 번호)로 캐시: pivotTrans/transform 참조(관리 객체 배열), 부모가 원점·무회전·단위 크기인지(부모는 곡 중 안 바뀜을 IL 로 증명하거나 곡 시작/장식 재설정 때 다시 검사), 플래그들(`stickToFloor`, `lockRotation`, `followPlanet`, `parallax.clampToScreen`, `dontAlterX/Y`, `isDecoration`, `hitbox`, 마스크 여부), `startRot`, `camScaleMultiplier`(카메라 크기에 의존하는지 `lockScale` 조건 확인 — 변하면 프레임당 값만 갱신), `textureScaleMultiplier`, `parallaxOffset`, `multiplier_x/y`. 장식마다 `Dictionary`/`ConditionalWeakTable` 를 프레임마다 조회하지 말 것(배열 인덱스로). 정적 값이 바뀔 수 있는 모든 게임 함수(`SetTextureScaleMultiplier`, `SetParallax`, `Setup`, `SetSprite`/`ResizeCollider`, `ffxMoveDecorationsPlus` 의 pivot·부모·parallax 변경 등)를 IL 전수(ILScan: `tools/ilscan`, `FIELDS=1`)로 찾아 그 호출 뒤에 그 장식의 캐시를 무효화(버전 번호 증가)하거나, 프레임마다 읽는 동적 필드(값 읽기만, 네이티브 아님)로 둘 것. 필드 읽기는 `AccessTools.FieldRefAccess`(현재 모드가 쓰는 방식) 또는 동일 속도의 방식. 관리 필드 읽기는 싸고 네이티브 호출(`transform.position`, `GetVisible()`, `Component` 비교(Unity null 검사 `==`) )은 비싸니 프레임마다 네이티브 호출은 엔진 쓰기 3개와 카메라 위치 1번 외에는 0으로.
2. **프레임마다 동적**: pivotPosVec, rotAngle, scaleVec(DecoAnim/DeferTransform 이 필드에 저장), `GetVisible` 상당 값은 네이티브 대신 **이미 모드가 가진 상태**(Dormancy 가 깨어 있음/잠듦 판정, `InvisibleSkip` 의 숨김 목록, 알파)로 판정하는 방법을 찾아 증명한다. 보임 판정이 어려우면 "깨어 있는(=Dormancy awake) 장식이면 보임" 같은 동치를 IL 로 증명(`Dormancy.IsDormant`: `disableShader && hitbox==0 && 정확히 scrVisualDecoration && !meshOn && !GetVisible()`; 깨어 있는데 `GetVisible()==false` 인 경우(메시 켜짐 등)는 빠른 길에서 제외).
3. **위치 `P`·시차**: `UpdatePosition` 은 `P = pivotPosVec (+행성/타일 이동 없음)` 로 `parallax.SetNewStartPosition(P)`, `posCamAtStart = P`, `SetTrans()`: `U = P + (cam.xy - P)⊙m` 식(연산 순서·Vector3→Vector2 변환은 FuseLate IL 근거 문서의 순서 그대로), `endPosition = U + O`(`O = parallaxOffset⊙camScale⊘texScale`), `position = (end.x, end.y, 기존 z)`. 관리 필드(`startPosition`, `posCamAtStart`, `endPosition`)를 원래와 똑같이 써 두어야 다른 코드(`GetPositionWithParallax`)가 읽을 때 같다. 카메라 위치는 매니저 LateUpdate 한 번에 한 번 읽는다(루프 안에서 카메라가 안 움직임은 IL 로 증명, FuseLate 결과 문서 참고).
4. **통합 방식**: `MoveApply.ManagerLateTranspiler`/`Dormancy.List` 가 이미 매니저 LateUpdate 의 순회 목록과 `LogicUpdate` 호출을 바꿔 끼운다(`MoveApply.LogicMaybe`, `Dormancy.List(awake 목록)`). 조건을 통과하는 장식은 별도 배치 목록으로 옮겨 **매니저 LateUpdate 앞(prefix)에서 한 번의 얇은 루프**로 처리하고 순회 목록(`Dormancy.List` 반환)에서 빼는 방식을 우선 검토(순회 순서가 장식 간 영향이 없음을 증명: 마스크/UpdateShader 가 다른 장식 Transform 을 읽는 장식은 배치에서 제외). 곡 중 장식이 배치↔일반 사이를 오갈 때(알파 0 ↔ 보임, `Dormancy` 깨움/재움, 효과가 마스크·부모·시차를 바꿈) 같은 프레임에 두 번 처리되거나 빠지지 않게. 편집기·재시작·곡 끝·모드 끄기에서의 정리와 `MoveApply.lateSkipped`(회전·크기 값만 저장한 장식 — `DeferTransform` 은 LateUpdate 가 `SetRotation(rotAngle)`·`SetScale(scaleVec)` 을 해 준다는 전제)와의 결합도 확인.
5. **검증 도구(필수)**: (a) `tightlate verify`: 배치로 처리한 장식 중 1/64 를 같은 프레임에 **원래 `UpdatePosition` 을 다시 실행**(이 prefix 만 우회; 원래 함수는 입력이 같으면 결과가 같으므로 재실행이 부작용 없음 — 근거를 적을 것)하고 전후 `position/rotation/localScale` + `parallax` 필드 + `rotAngle/scaleVec` 를 비트(±0 은 구분하되 `Transform.rotation` 은 같은 설정자를 쓰므로 비트 비교)로 비교, 불일치는 개수와 첫 예를 로그. (b) 곡 끝 장식 상태 대조는 기존 `decosig`(`TileSig.cs`)로 켬/끔 비교(Claude 가 실행). (c) `tightlate state`: 배치 크기, 프레임당 처리 수, 제외 이유별 개수, 무효화 횟수, 프레임당 배치 루프 시간(Stopwatch 1쌍만), 원래 매니저 LateUpdate 시간(`FuseProbe` 방식의 prefix/postfix 1쌍).
6. **성능 가정 확인**: 설계 단계에서 장식당 비용 예산을 적고(필드 읽기 N개, 네이티브 호출 4개 이하), 구현 뒤 `decojob writetest` 처럼 더미 오브젝트로 만든 **마이크로 벤치**(같은 루프를 더미 Transform 2,150개에)로 장식당 µs 를 재서 결과 문서에 적어라. 0.5µs 를 넘으면 원인을 찾아 줄여라.

## 하지 말 것
- 게임·다른 모드 동작 변경(결과는 비트 동일해야 한다). 불확실한 조건은 원래 길로 보낸다(제외).
- `StutterFix.cs` 의 해제 경로(UninstallAll)에 정리를 반드시 넣을 것(`Main.Unload`).
- 기존 `MoveApply`/`Dormancy`/`DecoAnim` 의 기존 최적화(DeferTransform, PairXY, LazySprite, Dormancy)를 깨지 않기. 기존 `decosig`/`late-verify` 도구가 계속 의미 있도록.

결과 문서에 Claude 가 게임에서 돌릴 순서(Arche 250~278초 A/B 판마다 새 프로세스, `tightlate state`/`verify`/`decosig` 비교, HELLO 전곡)도 적어라.
