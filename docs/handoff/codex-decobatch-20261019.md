# Codex 작업 G: DecoBatch 1단계 — 상주 배열(SoA) + 일괄 계산의 그림자 검증 (제품 동작 변경 0) — 게임 실행·Mods 설치·커밋 금지

결과: `docs/handoff/codex-decobatch-20261019-result.md` (**apply_patch 로 UTF-8 BOM, 쓴 뒤 `Get-Content -Encoding UTF8` 로 한글 확인**), 한국어, 추측은 "추정". 빌드 셋 오류 0. 새 코드는 `DecoBatchShadow.cs`(DEV/AUTOTEST 전용; FuseProbe/CpuBreak 와 같은 Compile 조건)와 필요하면 `native/sfnative` 의 새 export(기본은 기존 `sf_*` 이름 규칙, 빌드는 `native/build-sfnative.bat`; 네이티브를 건드리면 managed 내장 리소스까지 다시 빌드하는 절차는 `CLAUDE.md`/`native/` 참고, 설치 후 해시 검사). AutoTest.cs·csproj·StutterFix.cs 에는 최소 줄. 명령: `decobatch shadow begin|end|state`.

## 배경 (Claude 실측 — 이 작업의 이유)

Arche 곡 257.8~278.8초(CPU 병목) 프레임당: 모드 장식 애니메이션 `DecoAnim.UpdatePrefix` 1.91ms + 장식 관리자 LateUpdate 1.06ms(TightLate 적용 후). 프로덕션 경로 표본(`decosamp`): 위치 쌍 1,174번 0.60µs = 0.71ms, 색 1,064번 0.43µs = 0.46ms, 회전 1,182번 0.18µs = 0.22ms, 크기X 943번 0.16µs, 크기Y 943번 0.15µs, 정리(Compact) 0.25ms, 루프 뼈대 약 0.30ms. 값 계산(`Eval`) 자체는 호출당 0.055µs 로 싸다(관측 포함 값). 엔진 Transform 쓰기도 싸다(setter 3개 2,150개 0.2ms). **비싼 것은 기록 하나하나를 객체·함수 호출 사슬로 처리하는 관리 코드**다(Mono). 이미 실패한 부분 개선: GroupStep(묶음)·PosFast(SetPosition 생략)·FastLane(판정 캐시·인라인: 벤치도 더 느림)·TightLate 같은 값 건너뛰기. 마이크로 코드 줄이기는 한계다.
새 방향: 애니메이션 **상태를 구조체 배열(SoA)로 상주**시키고 프레임마다 **한 루프(관리 코드)나 한 번의 네이티브 호출**로 모든 기록을 진행·값 계산해 장식 필드에 쓴다(기록 객체·메서드 호출·델리게이트 사슬 없이). 이 작업은 그 가능성을 **제품 동작을 바꾸지 않고** 재는 그림자 검증이다.

## 현재 DecoAnim 의미 (코드: `DecoAnim.cs`, 설명 주석 상단)

기록(`Rec`)은 장식 `D`, 키(1 위치X, 2 위치Y, 5 회전, 7 크기X, 8 크기Y, 9 색, 10 불투명도, 3·4 피벗, 11~13 시차), `Dur`, `Pos`(float 누적), `E`(Ease), `Over`/`Period`, 값 `FStart/FEnd/FChange/FLast`(1,2,5,10), `VStart/VChange/VLast`(7,8: Vector2), `CStart/CChange/CLast`(9: Color). 프레임마다(`UpdatePrefix`) 만든 순서대로: `Startup(r)`(첫 갱신 때 시작값·변화량 읽기), `to = Pos + td`(float), 끝이면 `to = Dur` 와 done, `Apply`(값 = `FStart + FChange * e` — 키별 식은 `Apply` 참고: 크기는 성분별 `v.x = VStart.x + VChange.x * e` 후 다른 성분은 지금 `scaleVec` 에서 읽음, 색은 성분별), `OnUpdate`(설정 함수 호출; 보이는 장식의 회전·크기는 `MoveApply.DeferTransform` 이 참이면 필드(`rotAngle`/`scaleVec`)만 쓰고 LateUpdate(TightLate)에 맡김; 위치는 `StepPair`(X·Y 한 쌍을 한 번의 `setPos`)/`PositionUpdate`/`PosFast`), 끝나면 `OnComplete`(끝값 쓰기, `Running=false`). 이징 계산: `ZeroTween.Eval`(DOTween `EaseManager.Evaluate` 와 비트 동일 검증됨; Ease 분포: Linear 33%, OutCubic 46%, InCubic 21%, 그 외 소수).

## 할 일

1. **상주 SoA 미러(그림자)**: AUTOTEST 에서만, `DecoAnim` 의 기록이 시작(`Startup`/첫 `Step`)될 때 배열 슬롯을 할당하고(구조체 배열: 키, Ease 코드, Over, Period, Dur, Pos, FStart/FChange 또는 Vector2/Color 성분, 장식 인덱스), 끝/취소(`Running=false`, `Compact` 에서 목록 제거, `KillPrefix`/`CompletePrefix`/`KillAllPrefix`)에 슬롯을 비운다. 슬롯 재사용/스왑 제거(순서가 필요하면 순서 번호 유지). 장식은 장식 인덱스 → `scrDecoration` 참조 배열(관리 객체)로. 목표는 **프레임당 기록 수천 개에 대해 증분 유지 비용이 0.05ms 이하**. 유지 비용을 `state` 로 보고.
2. **일괄 계산 두 가지**(둘 다 작성):
   (a) **관리 코드 한 루프**: SoA 배열만 읽고 쓰는 얇은 루프. 지원 Ease(Linear, InQuad, OutQuad, InCubic, OutCubic 등 다항식 — `ZeroTween.Eval` 구현 참고)만 계산하고, 지원 밖(InExpo, Bounce, InOutCirc … 소수)·키 밖(3·4·11~13)은 "미지원 목록"으로 센다. 출력은 별도 NativeArray/배열(제품 필드에 쓰지 않음).
   (b) **네이티브 일괄 호출**: `sfnative` 에 새 export(예 `sf_decobatch_step(n, ease[], key[], dur[], pos[], start[], change[], over[], period[], outValue[], outDone[], td)`)를 추가해 같은 계산을 C++ 로. **부동소수점 비트 동일성**이 핵심: 컴파일 옵션(MSVC `/fp:strict`, FMA 사용 금지 `/arch:SSE2` 또는 `-ffp-contract=off`), 연산 순서(`time/=duration; return time*time*time` 같은 식을 DOTween 구현(DOTween.dll IL 은 이미 `ZeroTween` 이 옮긴 대로)과 정확히 같은 순서), 나눗셈·곱셈 float. P/Invoke 호출 비용(배열 고정: `fixed`/GCHandle, Unity Boehm GC 는 비이동이라 고정 불필요하나 확인)과 호출 한 번의 총 비용을 잰다. 지원 Ease 만 처리, 나머지는 managed 폴백 표시.
3. **비교**: 매 프레임 `DecoAnim.UpdatePrefix` 가 끝난 뒤(postfix 또는 기존 `UpdateCostProbe.FrameEnd` 자리 근처) 같은 입력(그 프레임 진행 전 `Pos`, `td`)으로 (a)·(b) 를 실행해 **실제 Rec 의 이번 프레임 결과(`FLast`/`VLast`/`CLast` 등과 done 판정, 새 `Pos`)와 비트 비교**(`SingleToInt32Bits`, ±0 구분)하고, 불일치는 개수·첫 예(키, Ease, Pos, Dur, 기대/실제)를 보고. 이를 위해 그림자 계산이 진행 전 `Pos` 를 알아야 하므로 `UpdatePrefix` 시작 시점(진행 전)에 SoA 의 `Pos` 스냅샷 또는 "SoA 가 따로 `Pos` 를 진행시키고 실제 Rec 의 진행 후 `Pos` 와 대조" 방식을 택해라(SoA 가 자기 `Pos` 를 진행시키고 매 프레임 실제 Rec.Pos 와 대조하는 쪽이 제품화에 가깝다).
4. **비용 측정**: 프레임당 (a) 루프 시간, (b) 네이티브 호출 시간(P/Invoke 포함), 증분 유지 시간, 출력→(미래의) 장식 필드 쓰기를 흉내 낸 비용(장식 인덱스 → `rotAngle`/`scaleVec`/`pivotPosVec` 필드 쓰기: `AccessTools.FieldRefAccess`/`DecoAnim` 이 이미 쓰는 `rotRef`/`scaleRef`/`pivotPosRef` 로 실제 필드를 쓰지 않고 더미 장식 위 시간만 재거나, 읽기 전용으로 필드 접근 비용만)을 Stopwatch 1쌍으로. **기대 효과 판정 기준**: 현재 `decosamp` 기준 회전·크기·위치 쌍의 합(1.67ms 중 위치·회전·크기 합 약 1.2ms)과 정리·뼈대 약 0.55ms 를 대체하는 데 총 0.3ms 이하이면 2단계(제품 구현) 가치가 큼.
5. **2단계(제품 구현) 설계(구현 금지)**: 어떤 기록을 일괄 처리 대상으로 삼을지(보이는 이미지 장식의 키 1·2·5·7·8, 지원 Ease; 숨김·투명·마스크·미지원 Ease·`Prof`·Dev `Shadow` 는 기존 경로) — 기존 경로와의 공존(같은 장식에 일괄/기존 기록이 섞이는 경우 순서·의존: 크기 Y 시작값은 크기 X 설정 뒤에 읽음, 위치 X·Y 가 서로의 성분을 읽음), 생명주기 이벤트(`KillPrefix`/`CompletePrefix`/`KillAllPrefix`/`NewRec` 재사용/`OnComplete`/Complete 시 끝값 쓰기, 곡 끝·재시작·모드 끄기·`ResetScene`)에서 SoA 슬롯과 `Rec` 의 일관성 유지 방법, 장식 필드 동기화 시점(지금 `DeferTransform` 이 하는 대로 `UpdatePrefix` 끝에서 필드가 최신이어야 TightLate/다른 코드가 읽는다), `MoveApply.lateSkipped` 등록(매 프레임 필요한 부수 효과), 색(9)·불투명도(10)는 setter 가 `ApplyColor`(엔진 호출)라 일괄 대상에서 제외(값 계산만 일괄로 하고 setter 는 기록별로 부르는 변형 평가).
   예상 이득 식과 위험, 작업량을 적어라.

Claude 가 게임에서 돌릴 순서(Arche 250~278초 `decobatch shadow begin/end/state`, `fuse`, 기존 `decosamp`)를 적어라. 이 판의 FPS 는 성능 근거로 쓰지 않는다.
