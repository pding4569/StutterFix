# 모드 자체 감사 (작업 6)

2026-10-14. 소스와 로컬 게임 DLL을 오프라인으로 조사했다. 게임 표본 **0판**. 비용 수치는 새로 측정하지 않았고, 삭제·게임 실행·설치·커밋·푸시는 하지 않았다. 현재 작업 트리는 `codex/shader`이며 기존 변경을 보존했다. `.git` 쓰기가 제한된 환경이라 fetch/새 브랜치는 수행하지 않았다. 이 문서는 삭제 승인이 아니라 Claude의 측정·판단을 위한 후보 목록이다.

## 먼저 볼 것

- **정식 빌드의 상시 계측**: `Main.OnUpdate`/`Tk`와 `FrameParts`는 Player에서도 Stopwatch를 호출한다. 개발 진단 형식이 DLL에 들어 있는 것과 실제로 패치가 설치되는 것을 구분해야 한다.
- **이동 패치 겹침**: `ffxMoveDecorationsPlus.StartEffect`에 EffectScan, ZeroTween, InstantMove, FastMove, DecoAnim 관련 경로, MoveApply 등이 결합한다. 처리 범위와 보조 함수 의존성 때문에 파일 단위 삭제는 위험하다.
- **설정이 꺼져도 패치는 남는다**: 대다수 Install은 설정을 보기 전에 패치를 설치하며 ApplyToggles가 실행 분기만 바꾼다. 기본 끔인 FilterIdentity도 OnRenderImage 진입 비용은 남는다.
- **PatchHot 시간은 모드 자체 시간이 아니다**: 원래 함수·다른 모드의 패치·중첩 호출까지 포함한다. 호출 빈도와 겹치는 패치 수로 후속 A/B 후보를 선정한다.

## 측정기와 해석

`PatchHot.cs`는 `#if DEV || AUTOTEST`와 csproj Compile 조건으로 정식 DLL에서 제외했다. AutoTest의 `patchhot on|state|off`도 같은 전처리 범위다. Hitch.Tick에서 곡 상태 전환 때만 실시간 시계를 갱신하며 Main.Unload에서 PatchHot.Off로 자기 Harmony ID만 해제한다.

`on`은 곡 밖에서 대상 스냅샷을 만들고 StutterFix* owner의 P/Q/T/F 수를 기록한다. 다른 모드·Unity·DOTween에 걸린 우리 패치도 포함하며 PatchHot 자신의 패치는 제외한다. 맵 로딩 이후 추가된 TileCull 등의 패치를 포함하려면 **맵을 열고 press 이전에 on**을 실행한다. 이후 새 패치는 다음 off/on 때만 반영된다. 켜진 상태에서 on은 아무 일도 하지 않는다. off/on은 새 측정을 시작하며 배열과 곡 시간을 초기화한다. `off`는 결과를 보존하여 그 뒤에도 state로 읽을 수 있다.

on에서 생성 wrapper와 Begin/End를 MethodHandle.GetFunctionPointer로 미리 컴파일한다(Mono에서 PrepareMethod는 쓰지 않는다). 호출 경로는 정적 long 배열과 스택 long __state만 사용한다. 반사/정렬/문자열/잠금/메모리 할당은 설치·state 명령에서만 한다. 측정 배열을 잠금 없이 안전하게 유지하기 위해 on을 실행한 Unity 주 스레드에서 Hitch.Playing일 때만 센다. **작업 스레드 호출은 제외**한다. 64번째마다 Stopwatch 두 번, 1~63회 대상은 시간 표본 없음으로 표시한다. 가장 앞 P/가장 뒤 Q로 원래 함수를 건너뛴 호출도 센다. 예외로 postfix에 도달하지 않은 호출은 호출 수에는 남지만 시간 표본에는 빠질 수 있다. `우리 패치 수`는 설치 당시 값이며 설정 켬 여부와 다르다.

대상별로 설치 때 생성하는 정적 wrapper에 슬롯 번호를 넣어 hot path 사전 조회를 없앴다. off/on에서 같은 MethodBase wrapper를 재사용한다. wrapper 타입은 동적 어셈블리에 남지만 패치는 Off/Unload에서 해제한다. 신규 대상·재로드마다 타입이 증가할 수 있으므로 반복 연구는 새 게임 프로세스로 하고 이 코드는 배포하지 않는다. 열린 제네릭/관리 IL 없는 대상은 제외 로그를 남긴다. 설치 실패는 조용히 성공 처리하지 않고 자기 ID 패치를 모두 롤백하여 명령 오류로 돌려준다.

호출별 시간에는 원래 함수, 우리 패치, 다른 패치, 안쪽 호출이 포함된다. 중첩 대상 시간 합계는 중복이므로 총 프레임 비용으로 더하지 않는다. 주기적 1/64 표본은 박자와 맞물릴 수 있고 짧은 함수는 timestamp·wrapper 비용이 비중을 차지한다. **순위는 후속 A/B 후보 선정용**이다. state는 정렬과 긴 로그를 만들므로 재생 중 실행하지 않는다. off 역시 대량 unpatch가 있으므로 곡 끝에서 실행한다. wasteprobe 등 다른 전면 계측과 동시에 켜지 않는다.

## 빌드 및 오프라인 검증

- PlayerAuto: `dotnet build -p:Edition=Player -p:AutoTestBuild=1 -v q --nologo`, 오류 0 / 기존 경고 25.
- Player: `dotnet build -p:Edition=Player -v q --nologo`, 오류 0 / 기존 경고 25.
- `tools/ilscan` Release 빌드: 오류 0 / 경고 0. `TYPES=PatchHot`로 Player DLL 0개 형식, PlayerAuto DLL 1개 형식 확인. Player의 WasteProbe도 0개.
- Player DLL에서 ILScan으로 AutoTest, FrameParts, UiProf, MoveProf, RenderVerify, SlowScan, StartProbe, DecoDiag, ScriptProbe, MergeProbe, AllocProbe, TimeProbe 형식이 **각 1개** 존재함을 확인했다. AutoTest/개발 진단은 소스 게이트와 실행 여부를 별도로 봐야 한다.
- 게임과 무관한 임시 .NET Framework 테스트에서 **게임의 로컬 0Harmony.dll**을 써서 prefix가 false로 원래 함수를 건너뛰는 대상 128호출→2표본, off 후 자기 ID 제거, 다시 on 64호출→1표본을 확인했다. Unity Mono에서의 실제 설치·JIT·FPS 비용은 Claude 시험이 남아 있다. .NET 8에서는 로컬 구버전 Harmony의 ReflectionHelper 초기화가 실패하여 Framework 런타임으로 검증했다.

## Claude 시험 순서

1. 기존 정식 DLL과 설정을 보관하고 PlayerAuto DLL 설치는 Claude가 수행한다. 다른 계측 파일(scriptprobe, startprobe-cold, uiprobe 등)과 wasteprobe를 끈 상태를 기록한다. 무거운 맵마다 새 프로세스로 시작한다.
2. 예시: `sf_run(steps=["auto on", "game D:/얼불춤 맵 파일/HELLO (BPM) 2026/level.adofai", "patchhot on", "press", "waitend 900", "patchhot state", "patchhot off", "patchhot state", "quit"], timeout_min=20, tag="patchhot-hello")`.
3. 호출 상위, 실제 표본 수, 0회 대상, 패치 수 K가 큰 대상을 정리한다. 대상 스냅샷이 맵 준비의 추가 설치를 포함하는지 로그를 확인한다. 곡 시작 전에 패치 설치/JIT가 끝났는지도 확인한다.
4. 같은 조건으로 PatchHot 끔 기준 판과 켬 판을 새 프로세스에서 비교해 **측정기 자체 FPS·최악 프레임·힙 증가**부터 확인한다. HELLO만으로 제거 판단하지 말고 Arche/Lost Requiem/Windflower의 이동·마스크·되감기·에디터 재시작 경로도 따로 확인한다.
5. 단독 기능 후보는 설정 매핑 표를 보고 A/B한다. LoadCache처럼 여러 기능을 한꺼번에 끄는 설정의 이득을 한 파일의 이득으로 쓰지 않는다. Main.Tk 등은 Claude가 계측 전용 분기 빌드를 만들고 비교한다. 화면/타일/장식 상태 같음을 함께 확인한다.
6. UMM Unload/재로드 뒤 `[패치 호출]` ID가 남지 않는지 확인하고 정식 DLL·기존 설정을 복원한다. 이후에만 삭제/합치기를 판단한다.
