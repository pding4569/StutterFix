## (1) 장식 떼기 제품화 — 메인 -0.2~0.3ms 확인됨

사실(측정): 게임은 장식 28,835개(Transform 약 14만)를 전부 `scrDecorationManager.transform` 밑에 둔다. 한 계층 안에서 하나라도 바뀌면 엔진 `TransformChangeDispatch::ScanAndHandleChangesJob` 이 계층 전체를 훑는다(메인 표본 2.9% + ClearJob 1.4% + 대기). 진단 `decodetach all`(DecoDetach.cs: 관리자의 직계 자식을 전부 `SetParent(null, true)`)로 Arche gBs 메인 3.49/3.37 → 3.21/3.18ms, UpdateAllRenderers 0.20 → 0.09ms. 한 번 떼는 데 160~170ms.
주의(측정): **원본 모드(GpuDeco 끔)에서는 손해**다(Arche 메인 10.0 → 11.3ms: 매 프레임 2만 8천 계층이 다 더러워짐). "움직인 것만 떼기"는 효과 없음(0.20 → 0.17). 그래서 **GpuDeco 가 켜져서 대부분의 장식을 맡았을 때만** 전부 뗀다.

할 일:
- 게임·모드 코드에서 장식의 부모 관계에 기대는 곳을 전부 찾는다. 이미 아는 것: `scrDecorationManager.ClearDecorations`(GetComponentsInChildren 으로 자식을 지움 → 떼어 둔 것도 지워야 함), 관리자 Awake 의 `foreach (Transform item in base.transform)`(scnGame 없을 때), 장식 만들기 `Instantiate(prefab, base.transform)`, `scrDecoration.cs:756` 의 `transform.parent`(프리팹 장식 이름). 그 밖에 `E:\StutterFixWork\decompiled\Assembly-CSharp` 전체와 이 모드(TightLate, ExitFix, DecoBatch, LeakGuard, Dormancy, GpuDeco 복귀 경로 등), 다른 모드 DLL(`...\Mods\Quartz`, `JALib`, `AdofaiGenBridge`, `YouTubeStream`)에서 `scrDecorationManager` 의 transform 자식/`GetComponentInParent<scrDecorationManager>`/`transform.root`/형제 순서를 쓰는 곳을 ilscan/ILSpy 로 찾는다.
- 설계: GpuDeco 활성화가 끝난 뒤(곡 재생 중) 직계 자식을 여러 프레임에 나눠 뗀다(프레임당 시간 예산 예: 1ms, 원래 형제 순서 기록). 되붙이는 때: GpuDeco 비활성화(CPU 복귀), 곡 끝/죽음/다시 하기/편집 복귀, `ClearDecorations` 직전(앞 패치), 맵 바뀜, Unload. 되붙일 때도 나눠서 하되, 부모 관계가 필요한 코드가 불리기 직전이면 그 자리에서 전부 끝낸다. 떼어 둔 동안 새로 만들어지는 장식·지워지는 장식 처리. 프리팹 장식(`scrPrefabDecoration`, 부모가 한 단계 더 있음)과 `SortingGroup` 은 구조를 깨지 않게.
- 검증 명령(자동 시험): 떼기 전/후/되붙인 뒤에 모든 장식 Transform 의 월드 위치·회전·크기·형제 순서·부모를 비교해 다른 개수를 로그(`decodetach verify`). 설정 이름 예: `GpuDecoDetach`(기본 false).
- 결과 문서에 찾은 의존 지점 목록과 각각의 처리, 남은 위험을 적는다.

## (2) GpuDeco 구간의 고정 GPU 비용

사실(측정, Arche 262초 정지 프레임, 2560x1417): GpuDeco 구간 전체의 GPU 시간 0.66ms(같은 장식을 원래 렌더러로 그리면 2.39ms). 그 0.66ms 중 **픽셀을 전부 바로 버려도(`sfdebug 3`) 0.47ms 가 남는다**. 텍스처 읽기는 0.05ms, 섞기 0.15ms 뿐이다. 즉 비용의 70%가 픽셀이 아니라 정점·삼각형·구간별 그리기다. 구간 535개, 소유 항목 약 2만 8,600개(형태 사각형으로 슬롯이 더 많음), 실제로 래스터되는 삼각형은 구간에서 약 1만 1천 개뿐이다. 정점 셰이더(`tools/gpudeco-lab/GpuDecoBatch.shader:114`)는 슬롯마다 `_CollapseVerts` 에서 60바이트를 읽는다.
Windflower 260초는 반대로 픽셀 쪽이 크다(구간 2.59ms 중 버리기만 0.82, 섞기 0.50, 텍스처 1.27).

할 일:
- 먼저 숫자를 로그에 남긴다(준비 때 한 번): 전체 슬롯 수, 구간별 슬롯 수 분포, 평균적으로 보이는 슬롯 비율(이미 있는 읽기/진단으로 구할 수 있으면).
- 후보를 실험실에서 재고(지난번 CompositeBench 방식의 GPU 시간 측정) 싼 것부터 넣는다:
  a. 정점 셰이더 조기 탈출: 위치(12바이트)만 먼저 읽어 숨은 슬롯(위치 0)이면 나머지 48바이트를 읽지 않고 퇴화 정점을 낸다.
  b. 숨은 슬롯을 인덱스에서 빼기: 구간마다 "보일 수 있는 슬롯"을 앞으로 모으는 방법(컴퓨트에서 구간 안 안정 정렬 압축 + 구간 메시의 인덱스 수를 GPU 가 정하게 — `DrawProceduralIndirect`/`RenderMeshIndirect` 로 구간을 그릴 수 있는지, 유니티 정렬(구간 렌더러의 정렬층·순서·동점 규칙)을 유지할 수 있는지 검토). 정렬을 못 지키면 하지 않는다.
  c. 구간 단위: 지금 `ApplySpanCulling` 이 하는 것(보이는 항목이 없는 구간 끄기)의 정확도와 비용, 한 프레임 늦는 읽기에 기대는지.
