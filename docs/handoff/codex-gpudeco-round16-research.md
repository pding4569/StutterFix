## 공식 자료에서 확인한 유사 사례

1. [Unity 6 배칭 설명](https://docs.unity3d.com/6000.0/Documentation/Manual/DrawCallBatching.html): 투명 물체는 먼저 뒤→앞 정렬하므로 배칭이 제한된다. 정적 배칭은 공통 VBO/IBO를 쓰며, 동적 배칭의 CPU 변환 비용이 드로우 자체보다 커질 수 있다고 명시한다. 우리 게임의 특정 함수가 원인이라는 증명은 아니다.
2. [Unity ETW 분석 사례,26~28쪽](https://docs.unity3d.com/2019.2/Documentation/uploads/ExpertGuides/Analyzing_your_game_performance_using_Event_Tracing_for_Windows.pdf): 작은 동적 물체가 많은 예제에서 렌더 스레드의 동적 배칭 비용과 메인의 렌더 큐 준비 비용을 스택으로 분리했다. 오래된 예제이며 현재 Unity6000 게임과 같은 버그라고 해석하지 않는다.
3. [Microsoft ExecuteCommandList](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-executecommandlist): TRUE는 컨텍스트 상태를 보존·복원한다. Unity 상태 보존을 제거하는 후보로 채택하지 않았다.
4. [Microsoft GetThreadTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadtimes): 제한 조회 권한으로 커널/사용자 CPU 누적 시간을 얻을 수 있다. 이 시간은 GPU 시간이나 잠든 시간을 뜻하지 않는다.
5. [Unity 2023.2 2D 정렬 설명](https://docs.unity3d.com/cn/2023.2/Manual/2DSorting.html): 명시 우선순위가 같은 렌더러의 마지막 동률 정렬은 내부 처리라고 설명한다. 현재 엔진의 내부 키 구현을 공개한 문서가 아니므로, Material ID/CRC나 `SameBucket`만으로 원래 순서를 복원했다고 가정하지 않는다.
