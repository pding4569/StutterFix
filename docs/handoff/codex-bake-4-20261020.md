# Codex 임무 bake-4: Tile/Camera 초기 배치 지원 (지원률의 최대 제한 해제)

2026-10-20. 작업 폴더 `E:\StutterFixWork\wt-bake` (브랜치 `codex/night-bake`, bake-3 커밋 위). 게임 실행·설치·커밋 금지. 결과 `docs/handoff/codex-bake-4-20261020-result.md` + `-o` 파일(10줄).

## 문제
bake-3 오프라인 추정(`docs/handoff/codex-bake-3-20261020-result.md`): Arche 소스 장식 28,835개 중 **초기 Global 이외 배치가 28,830개(99.98%)** — 사실상 전부 Tile(28,716, 99.59%) 또는 Camera/CameraAspect(114) 기준이다. 이 제한을 풀지 않으면 굽기 지원률이 0.017% 라 아무 쓸모가 없다. 이것만 풀면 파일상 후보가 23,522개(81.6%)로 늘어난다.

## 해야 할 것
1. **배치 의미 확정(코드 읽기, 게임 미실행)**: `scrDecoration.SetPlacementType`, `Setup`, `UpdatePosition`, `scrParallax.SetTrans`, `ffxMoveDecorationsPlus.StartEffect`(Global/LastPosition 갈래와 Tile 갈래의 `startPos`·목표 계산) 를 읽고 다음을 확정: (a) Tile 배치의 `startPos` 가 **맵 로드(Setup) 때 한 번 정해지는 정적 값인지**, 아니면 타일 위치를 매 프레임/효과 때 다시 읽는지(타일 이동 효과로 타일이 움직이면 장식이 따라가는지); (b) 목표 위치 `startPos + targetPos` 가 Tile 에서도 같은 식인지, 이동 효과의 `relativeTo`(Tile/Global/LastPosition/Camera 등)에 따라 달라지는 갈래; (c) Camera/CameraAspect 의 단위 변환(화면 비율·카메라 크기)이 시간에 따라 변하는지(카메라 줌 이벤트로 장식 위치가 바뀌는지); (d) 시차(parallax, `scrParallax`)와 Tile/Camera 의 관계(시차 100이면 카메라를 따라가는 경우 — `docs/` "연구22장" 참고). 정적이고 시간 독립적이면 현재 `scrDecoration.Setup` postfix 가 읽는 초기 스냅샷(실제 시작 위치)을 그대로 쓰면 되는지 판단.
2. **구현**: 정적으로 확인된 배치는 지원 목록에 넣는다(위치 채널의 기준은 Setup 직후 읽은 실제 위치 `startPos`). 동적(타일 이동을 따라가는 등)인 갈래는 **그 장식 전체를 제외 사유로 센다**(이유 문자열 구분, "Tile-동적" 등). `decobake verify` 지원 사유별 통계에 새 항목 추가. 오프라인 fixture 에 Tile/Camera 정적 예·동적 예(제외)를 추가.
3. **오프라인 지원률 재계산**: `tools/optimization/bake-support-estimate.py` 를 갱신해 새 규칙으로 Arche 파일상 후보 수와 사유별 표를 다시 낸다. 새 상위 5개 확장 제안(다음에 풀 사유: 이미지/원래크기/크롭/wrap 5,087개(17.6%) 등)을 코드 근거와 함께.
4. 빌드 3종(`-c Release`; `-p:Edition=Player`; `-p:Edition=Player -p:AutoTestBuild=1`) 오류 0 + LoadCheck. Player 제외 유지.
