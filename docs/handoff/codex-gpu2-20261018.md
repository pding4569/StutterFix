## Claude 가 잰 것 (Arche 곡 약 258~266초, 3440x1440, D3D11)

- gpuprobe: GPU 프레임 6.41ms 중 본 카메라 `Camera` 6.21ms, 다른 카메라 합 0.17ms, 켜진 필터 합 약 0.8ms(각 0.04~0.15).
- **같은 구간, 게임 화면 해상도 50%(LowRenderScale=50, 픽셀 1/4): Camera 4.96ms.** 픽셀이 1/4 이 돼도 20% 만 줄었다 → 채우기(overdraw)보다 **그리는 개수에 비례하는 비용**이 대부분(약 4.5ms 추정). 그 순간 보이는 이미지 장식 약 1,900~2,100개, 애니메이션 도는 장식 약 2,100개.
- 메인 스레드 10.2ms, 렌더 스레드 4.3ms (렌더 스레드도 그리기 호출 수에 비례 추정).
- gpucensus 첫 판이 이상하다: 본 카메라 후보 6개(행성·플래시), `excluded(... outside)=2695`. 장식이 화면 밖으로 분류된 것으로 보인다. TSV: `%LOCALAPPDATA%\StutterFix\gpu-census-20261018-213606-940.tsv`.

## 할 일

1. **gpucensus 고치기**: 본 카메라가 실제로 그리는 장식이 후보로 잡히게(화면 밖 판정·z/클립 평면·정렬층/컬링마스크·SpriteRenderer bounds 처리 확인). 원인을 결과에 적어라.
   추가 출력: 그리는 순서(renderQueue → sortingLayer → sortingOrder → 카메라 거리, 같은 값이면 Unity 규칙 추정)로 늘어놓았을 때
   - 연속해서 (재질 인스턴스, 주 텍스처, MaterialPropertyBlock 유무, 키워드) 가 같은 묶음 수 = **지금 배치 상한 추정**
   - 재질 인스턴스만 같게 하면(텍스처는 그대로) 묶음 수, 텍스처까지 하나(아틀라스 가정)면 묶음 수
   - 장식마다 재질이 인스턴스인지(공유인지), 어떤 셰이더·키워드, SpriteRenderer 인지 MeshRenderer 인지
   - 서로 다른 텍스처 수, 그 크기 분포
2. **GPU 기여 측정 도구** `gpuhide <그룹> <초>`: 그 그룹의 렌더러만 잠깐 forceRenderingOff(원래 값 저장·복원, 진단 전용, 화면이 바뀌는 것은 시험에서만)하고 그동안 gpuprobe 평균을 따로 낸다. 그룹: 장식 전체 / 장식 절반(인덱스 짝수) / 정렬층별 / 셰이더별 / 텍스처 긴 변 구간별 / 타일 / 행성·파티클. 같은 판에서 숨기기 전후도 재서 차이를 보고한다.
   이것으로 "장식 하나당 GPU 비용"을 숫자로 낸다(절반 숨김 차이 ÷ 숨긴 개수).
3. **줄일 방법 후보와 동일성 근거** (구현하지 말고 조사·설계만, 단 매우 확실하고 그림이 같은 것은 구현 가능):
   - Unity 내장 파이프라인에서 SpriteRenderer 동적 배치 조건(같은 재질·텍스처, MPB 없음 등)과 이 게임이 깨는 지점(IL: scrVisualDecoration 이 재질을 언제 인스턴스로 만드는지 — `material` getter, SetShader/키워드, ApplyColor 가 색을 정점색으로 쓰는지 MPB/재질로 쓰는지).
   - 장식들이 같은 셰이더·같은 키워드면 재질 공유로 배치가 살아나는지(같은 텍스처를 쓰는 연속 장식이 얼마나 있는지 1번 숫자로).
   - 텍스처 아틀라스(런타임 묶기)로 서로 다른 이미지를 한 텍스처에: 표본화 결과가 같으려면 무엇이 필요한지(가장자리 늘이기 패딩, Clamp 와 같은 결과, 필터 모드, 크기가 2의 배수가 아닐 때, 회전·크기 변환된 스프라이트), 메모리·로딩 비용. 앞서 투명 여백 크롭이 Bilinear 에서 9~31픽셀 달라 채택 0 이었던 것(docs/optimization-36.md "12 투명 여백")을 참고해 같은 함정을 피하는 조건을 적어라.
   - GPU 인스턴싱(Graphics.DrawMeshInstanced/SRP 아님) 대체 그리기는 정렬·투명 순서 때문에 그림이 바뀔 수 있는지.
   - 각 후보의 예상 절약(2번 측정이 나오면 그 숫자로 계산할 식), 위험, 구현 크기.
4. Claude 가 돌릴 명령 순서를 결과 파일에 적어라(앞 작업과 같은 형식, Arche 258초 근처, census 판과 gpuhide 판 분리).
