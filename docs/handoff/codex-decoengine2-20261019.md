결과: `docs/handoff/codex-decoengine2-20261019-result.md` (**apply_patch 로 UTF-8 BOM, 쓴 뒤 `Get-Content -Encoding UTF8` 로 한글 확인**), 한국어, 추측은 "추정". 빌드 셋(Dev/Player/PlayerAuto) 오류 0. 기본 끔 유지(`decoengine-on` 파일). 이전 결과 `docs/handoff/codex-decoengine-20261019-result.md` 와 `DecoEngine.cs`(커밋 467184c) 가 출발점.

## 실측 (Claude, Arche, 엔진 켬, 곡 252.8~273.8초 창)
- 정확성: `decoengine verify` 55만 5천 번 검사 불일치 0. 구조는 맞다.
- **그러나 엔진이 거의 아무것도 소유하지 못한다**: 창에서 소유 장식 약 20개 / 도는 장식 1,907개(`animstat`: 위치X·Y 1,786, 회전 1,848, 크기 1,610, **색 1,833**, 불투명도 9). 곡 전체 누계 입장 6,979회·복귀 6,156회, 탈락 280만 번 중 `rej` 분해(새 카운터; 순서 1색 alpha 변화 / 2불투명도 / 3기타키 / 4미시작·무한 / 5키 중복 / 6빈 / 7엔트리 없음 / 8자식 변경) = **1(색 alpha 변화) 2,725,261 (97%)**, 7(TightLate 엔트리 없음) 68,839, 2(불투명도) 14,594, 나머지 ≈0.
- 결과로 비용이 오히려 늘었다: 모드 애니메이션 갱신 2.52ms(엔진 끔 기준 1.87~1.91) + 관리자 LateUpdate 1.10ms(기준 1.04~1.06). 입장·복귀 반복(sync 176만)이 이득을 먹는다.
- 즉 지금 `Independent(r)` (키 9는 `CStart.a == CEnd.a && a >= .001 && CChange.a == 0` 일 때만 독립, 키 10도 상수일 때만)가 너무 좁다. Arche 색 기록은 대부분 알파가 변하거나 0을 지나는 페이드다.

## 할 일
1. **알파가 변하는 색(키 9)·불투명도(키 10) 기록을 가진 장식도 엔진이 소유하도록** 설계·구현한다. 핵심은 보임 판정(`GetVisible`/`rendererEnabled && rendererColor.a != 0`)이 바뀔 때 기존 경로 대비 **최종 Transform·필드 결과가 비트 동일**임을 증명하는 것:
   - 기존 경로의 순서(`DecoAnim.UpdatePrefix`가 기록을 만든 순서대로 처리, 위치 `OnUpdate`→`MoveApply.DeferTransform`/`SkipForLate`/`UpdateNow`는 그 순간 `GetVisible()` 로 "LateUpdate 에 맡김" 대 "즉시 씀"을 결정, 색 기록이 중간에 알파를 바꾸면 뒤 기록의 판정이 달라짐, `Dormancy`/`InvisibleSkip`/`ManagerLatePostfix` 보충 갱신)를 IL·코드로 전수 따라가 **알파가 0↔양수로 바뀌는 프레임에서 기존 경로와 엔진의 최종 값·쓰기 시점 차이**를 표로 정리한다. 차이가 관찰 가능한 경우(최종 Transform/필드가 다른 경우)와 관찰 불가능한 경우(어차피 Late 에서 같은 필드로 덮어씀)를 구분한다.
   - 가능한 설계 후보: (a) 색/불투명도 기록은 기존 경로 그대로 돌리고(독립 처리), 엔진은 위치·회전·크기를 매 프레임 보임 상태와 무관하게 필드까지 게시 + Late 에서 보임이면 TightLate 식으로 씀, 보이지 않으면 기존 경로가 하던 대로(즉시 쓰기 또는 안 쓰기)를 정확히 재현; (b) 알파가 0 을 지나는 프레임(전환 프레임)에만 그 장식을 임시로 기존 경로로 돌려보내고 다음 프레임 재입장(복귀 폭주 방지를 위해 전환이 드문 장식 위주; Arche 에서 전환 빈도를 실제 이벤트로 세어라: 색/불투명도 이벤트의 시작·끝 알파가 0 을 포함하는 비율). 어느 쪽이든 입장·복귀·sync 호출이 장식당 프레임당 O(1) 이고 해시 조회가 없어야 한다(지금 sync 176만·복귀 6천 번이 비용 원인).
   - 알파가 계속 0 보다 큰 구간이면 변하는 알파도 독립으로 허용해도 되는지 증명(보임 판정이 변하지 않으므로 순서 무관). 알파가 0 을 지나는 기록만 어려운 경우로 분리.
2. **엔트리 없음(rej 7) 68k 줄이기**: `TightLate.EngineEntry` 가 null 인 이유(`e.EngineRejected`, `LastFrame != frameCount-1`, 첫 프레임 등)를 분해해 카운터로 보이게 하고 줄일 수 있는 것은 줄인다.
3. **입장·복귀 비용 제거**: 한 번 입장한 장식은 새 효과가 와서 키가 늘어도(같은 키 재시작: `FastMove`→`NewRec`/`KillKey`) 복귀하지 말고 슬롯 교체로 처리하는 경로를 설계(현재 복귀 6,156 / 입장 6,979 로 거의 매번 풀림). 효과가 이어 오는 장식(Arche: 장식 하나가 8~188개 이벤트를 받음)이 핵심이므로, **같은 키의 Kill(true)+새 기록**을 엔진 안에서 처리(Kill(true) 의미 = 끝값 쓰기 후 FStart 를 현재 필드에서 읽는 것: `DecoAnim.KillKey`/`NewRec`/`Startup` 를 따라 정확히 재현).
4. 위 변경 후에도 `decoengine verify`(기존 참조 계산) 불일치 0, 소유 장식 수/프레임·기록 수/프레임·입장·복귀·`rej` 카운터가 `state` 에 보이게. 가능하면 **소유율**(= 엔진 소유 기록 / 도는 기록)을 `state` 에 직접 표시.
5. 마이크로 벤치(`decoengine bench`)에 알파 전환을 흉내 낸 장식 비율을 옵션으로.
6. 결과 문서에 Claude 가 돌릴 순서(Arche 창 252.8~273.8초 `fuse` + `decoengine state` 앞뒤 차이로 창 구간 소유율, 새 프로세스 ABBA, `decosig` 곡 끝 대조)를 적어라. 채택 기준: 모드 애니메이션 갱신 + 관리자 LateUpdate 합 ≤ 1.8ms(기준 2.9ms), verify 불일치 0, 소유율이 의미 있게 높음(목표 70%↑).
